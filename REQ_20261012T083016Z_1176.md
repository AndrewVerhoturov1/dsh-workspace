## User intent

Нужно установить реальную доступность и семантику счётчика записи кэша для Codex OAuth (обычные подписочные Codex-вызовы), не для платного OpenAI API по API key.

Вопрос задачи: можно ли получить из обычного Codex OAuth response фактическое число токенов, записанных в prompt cache, и каким документированным/поддержанным usage-полем оно передаётся? Нужен честный ответ, почему cache_write_tokens может быть явным 0 при большом cached_tokens; сам ноль не равен доказательству отсутствия реальных записей. Не вычислять записи из total input, uncached input, длины контекста или прироста cached tokens.

Проведи ОГРАНИЧЕННУЮ проверку открытой официальной документации OpenAI/Codex и общедоступных исходников официального клиента/provider schema. Учитывай дату актуальных источников и явно различай Codex OAuth private backend, публичный Responses API и сторонние SDK. Названия моделей сами по себе не доказательство тарифов/capability. Не обращаться к частным endpoints, не запускать запросы к провайдеру и ничего не реализовывать/публиковать.

Локальное наблюдение как неавторитетный для provider contract контекст, без передачи файлов/сессий/сообщений: адаптер SDK @earendil-works/pi-ai0.85.1 Codex Responses получает JSON events по SSE/WebSocket и shared terminal handler смотрит input_tokens_details.cached_tokens/cache_write_tokens. Уже проверен код: до terminal normalization SDK response.usage не меняет, raw numeric-presence сохранение происходит до ||0. Несколько обычных ответов имеют mapped cache_read positive и cache_write explicit numeric0. Это подтверждает путь текущего локального SDK, но НЕ подтверждает поддержку реального positive write counter провайдером. Синтетические positive4/7 проходят передачу и накопление11, не доказательство real capability.
