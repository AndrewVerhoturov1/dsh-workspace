## User intent



Нужно спроектировать максимально качественную современную веб-версию настольной игры Carcassonne для двух игроков в режиме local hotseat на одном устройстве.

Это **первый этап проекта**.

На этом этапе НЕ нужно реализовывать саму игру и НЕ нужно писать production-код.

Нужно провести глубокое исследование игры, точно формализовать правила и подготовить подробный технический, продуктовый, UX и визуальный план реализации, по которому на следующем этапе можно будет действительно построить игру.

Главная цель проекта в перспективе:

* полностью играбельная партия Carcassonne на двух игроков;
* local hotseat, без AI-ботов и без сетевого multiplayer;
* максимально точное соблюдение правил;
* современный очень качественный интерфейс;
* полноценное 3D-представление игрового поля;
* красивые тайлы, окружение, meeples, анимации, освещение и камера;
* удобство реальной длительной игры важнее декоративных эффектов;
* интерфейс должен ясно показывать допустимые действия и не заставлять игрока бороться с 3D;
* итог должен ощущаться как законченная premium digital board game, а не как техническое демо.

# 2. Формализуй правила как спецификацию для software implementation

Нам нужна не просто пересказанная инструкция настольной игры.

Преобразуй правила в точную спецификацию rule engine.

Разбери полный lifecycle партии:

* setup;
* определение первого игрока;
* состав tile supply;

* получение следующего tile;
* определение всех legal placements;
* вращение tile;
* размещение tile;
* определение доступных областей для meeple;

* ties;
* scoring;
* возврат meeples;

* исчерпание tiles;
* final scoring;
* farmers/fields, если они входят в выбранный ruleset;
* определение победителя;
* tie в итоговом счёте.

Особенно тщательно исследуй сложные edge cases:

* соединение двух или нескольких ранее независимых features;
* ситуация, когда после соединения на одном feature оказываются meeples обоих игроков;
* несколько meeples одного игрока на одном feature после merger;
* equal majority;
* одновременное завершение нескольких объектов одним tile;
* tile, принадлежащий сразу нескольким scoring features;
* возврат нескольких meeples после одного действия;
* ограничения размещения meeple на connected feature;
* monastery completion;
* field connectivity;
* farmer scoring;
* end-game scoring незавершённых объектов;
* любой другой реально важный edge case, обнаруженный в официальных правилах.

Если для River или Abbot правила отличаются, вынеси их отдельными модулями.

Нужно добиться такого уровня формализации, чтобы следующему разработчику не приходилось самостоятельно додумывать правила.
