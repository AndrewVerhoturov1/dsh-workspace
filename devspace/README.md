# Постоянная работа DevSpace через Tailscale Funnel

Установка: Windows, PowerShell 7.5+, Node, закреплённый DevSpace `1.1.0-beta.4`, Tailscale `1.104.1`.
Публичный адрес и OAuth остаются прежними. Сервер слушает только `127.0.0.1:7676`.
Сценарии не меняют allowedRoots: исходные `C:/ D:/ E:/ F:/ G:/` сохраняются вместе с ограничениями Windows ACL.

## Использование

В PowerShell 7:

```powershell
& 'C:/Users/Andrew/.dsh/devspace/status.ps1'
& 'C:/Users/Andrew/.dsh/devspace/start.ps1'
& 'C:/Users/Andrew/.dsh/devspace/stop.ps1'
```

`status.ps1` одним запуском показывает процесс с проверенной принадлежностью, локальный health/MCP/OAuth,
каждый публичный вход Funnel, задание Windows, последнюю неисправность и результат восстановления.
`stop.ps1` приостанавливает наблюдение до следующего `start.ps1`, дожидается штатной остановки сервера
и отключает только известный HTTPS 443 Funnel. Если есть дочерняя команда, остановка отклоняется.
Здоровый существующий процесс принимается под наблюдение без перезапуска.

## Автоматическое восстановление

Одно задание Windows `DSH DevSpace Supervisor` запускается при старте ОС, входе пользователя и повторным
триггером каждую минуту. Оно работает от владельца установки с **обычными правами**, тип входа S4U,
без сохранения пароля. Действующее наблюдение не дублируется (`IgnoreNew`), время работы не ограничено.
S4U не предоставляет Windows сетевые учётные данные и доступ к EFS; исходящий HTTPS их не требует.
Сценарий регулярно проверяет состояние, между проверками ждёт 60 секунд. После ошибки самого наблюдателя
Планировщик может запустить его повторно; бюджет перезапусков сервера хранится отдельно на диске.

* Отсутствующий сервер запускается при первой проверке. Зависший принадлежащий установке процесс — после двух неудачных проверок.
* PID проверяется вместе с временем создания, точным исполняемым файлом и точной командой этой установки.
  Чужой слушатель или процесс сохраняется. Повреждённый/устаревший runtime не разрешает останавливать чужой PID.
* Все операции жизненного цикла используют одну блокировку файла. Частичный запуск без слушающего порта
  также не создаёт второй сервер. Runtime записывается через временный файл и замену.
* После локального сбоя: максимум три попытки, паузы 1 и 5 минут, затем разомкнутая цепь.
* Внешний маршрут проверяется через публичный DNS-over-HTTPS и прямое подключение к каждому полученному
  публичному IPv4 с исходным TLS SNI и обычной проверкой сертификата. MagicDNS и `100.x` не используются.
  Это настоящий маршрут через публичный вход с данного ПК, но не независимый монитор из другой сети.
* На каждом входе проверяются health JSON, отказ MCP без токена с `WWW-Authenticate` и OAuth issuer.
  При недоступном публичном DNS результат `unknown`, автоматической перенастройки Funnel нет.
* Только отказ всех проверенных входов минимум 180 секунд и три последовательные проверки допускает
  перепубликацию **того же** маршрута 443. Максимум две попытки с паузой 15 минут. Если один вход работает,
  состояние `degraded`: рабочие соединения не обрываются ради ремонта остальных входов.
* При внешнем сбое локальный сервер не перезапускается. Tailscale service, другие порты, профиль и ключи
  автоматически не перезапускаются и не меняются. Отличающаяся конфигурация Funnel сохраняется.
* Бюджеты восстанавливаются только после десяти минут полностью исправных проверок. Повреждённый файл
  бюджета сохраняется, автоматический ремонт приостанавливается, чтобы не получить бесконечные перезапуски.

Штатный `tailscale set --unattended=true` разрешает работу после выхода из Windows. `funnel --bg`
сохраняет публикацию между перезапусками. Проверить настройки можно без выхода/перезагрузки;
фактическая работа до первого входа после reboot требует отдельного испытания.
Истечение node key Tailscale требует владельца: исходная дата `2027-04-09T15:55:28Z`.
Отключение срока действия ключа автоматически не выполняется.

## Команды, сеансы и OAuth

Используется исходный OAuth и SQLite DevSpace. Обновление refresh token транзакционное и одноразовое;
истёкший bearer получает 401. Фоновая проверка не читает пользовательские токены и не выдаёт проверку
наличия OAuth за подтверждение действительности токена конкретного чата. Это подтверждает реальный
авторизованный вызов соединителя.

Workspace привязывается к `openai/session`; параллельное открытие одной папки внутри одного чата
защищено исходным pending map. Независимые обращения не сериализуются глобально. Одна и та же
рабочая папка остаётся общим файловым пространством: противоречащие изменения одного файла надо согласовывать.

`prepare-runtime.mjs` добавляет единственное ограничение к точному известному `pi-tools.js`:
не более восьми одновременно выполняющихся вызовов Bash, без очереди и автоматического повтора.
Девятый отклоняется **до** запуска команды. Патч проверяет версию и SHA256 исходника, сохраняет оригинал
рядом как `.dsh-original`, повторное применение идемпотентно. Неизвестная версия/правка — отказ без перезаписи.
Это предел вызовов Bash, а не запрет дочерних процессов сборщика или явно запущенных пользователем фоновых программ.
Исходный предел одной команды — 300 секунд. Обёртка не вводит тайм-аут ответа короче этого предела.

Наблюдатель **никогда не повторяет MCP-команды**. Если соединение оборвалось после начала изменяющей команды,
результат может быть неизвестен вызывающей стороне. MCP/соединитель не дают этому серверу общего надёжного
ключа идемпотентности: гарантировать однократность произвольного повторного вызова другого чата нельзя.
Нужно сначала проверить результат операции, а не посылать её заново. Сторонние ограничения времени ответа
ChatGPT и доступность его соединителя не исправляются локальным перезапуском.

## Диагностика и границы выводов

`logs/requests.jsonl` фиксирует начало, окончание и обрыв HTTP-запроса, код и длительность, название инструмента.
Он не записывает тело запроса/ответа, команду, путь личного файла, заголовки, токены и текст исключений.
Максимум около 2 MiB плюс одна предыдущая копия; `logs/watchdog.jsonl` — 1 MiB плюс одна копия.
Технические stdout/stderr нового запуска обновляются при старте. Старые журналы прежнего запуска сохранены
в локальной резервной копии, в Git их нет.

Во время исходной диагностики 16–17 октября 2026 г. два вызова `open_workspace` через соединитель вернули
`UNAVAILABLE`, хотя сервер записал успешное выполнение инструмента. Для одного публичного IPv4 также
наблюдались тайм-ауты TCP/TLS при работающих других входах. Это доказывает перемежающийся отказ доставки,
но не доказывает конкретную причину в Tailscale или ChatGPT. Позже реальный вызов Bash через соединитель
успешно вернул версию Node без перезапуска исходного сервера.

[Tailscale #21114](https://github.com/tailscale/tailscale/issues/21114) описывает расследование потери
регистрации Funnel после control-plane reconnect. Оно совместимо с частью симптомов, но конкретная причина
на этом ПК не установлена: прежние журналы не фиксировали начало/обрыв запроса, daemon logs требуют прав.
Отдельный Windows [#21752](https://github.com/tailscale/tailscale/issues/21752) закрыт как дубликат:
разработчик связывает тот случай с обратным сетевым маршрутом и другим VPN; строки `no rules matched`
сами по себе не доказывают отказ. В [changelog 1.104.1](https://tailscale.com/changelog) нет объявленного
исправления потери регистрации Funnel, поэтому обновление или откат без доказательств не выполняются.

Официальные сведения: [Windows Unattended](https://tailscale.com/docs/how-to/run-unattended),
[постоянный Funnel --bg](https://tailscale.com/docs/reference/tailscale-cli/funnel),
[OpenAI: диагностика MCP](https://developers.openai.com/plugins/deploy/troubleshooting),
[OAuth](https://developers.openai.com/plugins/build/auth).

## Проверки и откат

```powershell
pwsh -NoProfile -File devspace/tests/lifecycle.tests.ps1
node --test devspace/tests/runtime.test.mjs
node devspace/tests/native.integration.mjs
node devspace/tests/bash-limit.integration.mjs
node devspace/tests/disconnect.integration.mjs
```

Испытания создают отдельные временные проекты, процессы, порт и OAuth SQLite. Сбой внешнего маршрута
имитируется в принятии решений, рабочий Funnel не отключается. Полный тест проверяет две минуты команды,
независимое чтение, параллельные workspace, сохранение токена/сеанса после рестарта, истечение и refresh.
Перезагрузка, выход из Windows, отключение интернета и намеренный отказ рабочего Funnel не выполняются.

Установка файлов выполняется из проверенного task worktree с резервной копией существующих сценариев.
`install-watchdog.ps1` использует штатное UAC и проверяет, что повышение не изменило пользователя.
Для отката: приостановить/отключить задание Планировщика, штатно остановить новый сервер после окончания
работы, вернуть сценарии из локальной копии и оригинальный `pi-tools.js.dsh-original`, затем запустить прежний
сервер. OAuth, SQLite, проекты, адрес и ключи не удаляются. Не использовать общий `funnel reset`.
