# Постоянная работа DevSpace через Tailscale Funnel

Установка: Windows, PowerShell 7.5+, Node, закреплённый DevSpace `1.1.0-beta.4`, Tailscale `1.104.1`.
Публичный адрес и OAuth остаются прежними. Сервер слушает только `127.0.0.1:7676`.
Сценарии не меняют allowedRoots: исходные `C:/ D:/ E:/ F:/ G:/` сохраняются вместе с ограничениями Windows ACL.

## Использование

В PowerShell 7:

```powershell
& 'C:/Users/Andrew/.dsh/devspace/status.ps1'
& 'C:/Users/Andrew/.dsh/devspace/start.ps1'
& 'C:/Users/Andrew/.dsh/devspace/stop.ps1'
```

`status.ps1` одним запуском показывает процесс с проверенной принадлежностью, локальный health/MCP/OAuth,
каждый публичный вход Funnel, задание Windows, последнюю неисправность и результат восстановления.
`stop.ps1` приостанавливает наблюдение до следующего `start.ps1`, дожидается штатной остановки сервера
и отключает только известный HTTPS 443 Funnel. Если есть дочерняя команда, остановка отклоняется.
Здоровый существующий процесс принимается под наблюдение без перезапуска.

## Автоматическое восстановление

Одно задание Windows `DSH DevSpace Supervisor` запускается при старте ОС, входе пользователя и повторным
триггером каждую минуту. Оно работает от владельца установки с **обычными правами**, тип входа S4U,
без сохранения пароля. Действующее наблюдение не дублируется (`IgnoreNew`), время работы не ограничено.
S4U не предоставляет Windows сетевые учётные данные и доступ к EFS; исходящий HTTPS их не требует.
Сценарий регулярно проверяет состояние, между проверками ждёт 60 секунд. После ошибки самого наблюдателя
Планировщик может запустить его повторно; бюджет перезапусков сервера хранится отдельно на диске.

* Отсутствующий сервер запускается при первой проверке. Зависший принадлежащий установке процесс — после двух неудачных проверок.
* PID проверяется вместе с временем создания, точным исполняемым файлом и точной командой этой установки.
  Чужой слушатель или процесс сохраняется. Повреждённый/устаревший runtime не разрешает останавливать чужой PID.
* Все операции жизненного цикла используют одну блокировку файла. Частичный запуск без слушающего порта
  также не создаёт второй сервер. Runtime записывается через временный файл и замену.
* После локального сбоя: максимум три попытки, паузы 1 и 5 минут, затем разомкнутая цепь.
* Внешний маршрут проверяется через публичный DNS-over-HTTPS и прямое подключение к каждому полученному
  публичному IPv4 с исходным TLS SNI и обычной проверкой сертификата. MagicDNS и `100.x` не используются.
  Это настоящий маршрут через публичный вход с данного ПК, но не независимый монитор из другой сети.
* На каждом входе проверяются health JSON, отказ MCP без токена с `WWW-Authenticate` и OAuth issuer.
  При недоступном публичном DNS результат `unknown`, автоматической перенастройки Funnel нет.
* Только отказ всех проверенных входов минимум 180 секунд и три последовательные проверки допускает
  перепубликацию **того же** маршрута 443. Максимум две попытки с паузой 15 минут. Если один вход работает,
  состояние `degraded`: рабочие соединения не обрываются ради ремонта остальных входов.
* При внешнем сбое локальный сервер не перезапускается. Tailscale service, другие порты, профиль и ключи
  автоматически не перезапускаются и не меняются. Отличающаяся конфигурация Funnel сохраняется.
* Бюджеты восстанавливаются только после десяти минут полностью исправных проверок. Повреждённый файл
  бюджета сохраняется, автоматический ремонт приостанавливается, чтобы не получить бесконечные перезапуски.

Штатный `tailscale set --unattended=true` разрешает работу после выхода из Windows. `funnel --bg`
сохраняет публикацию между перезапусками. Проверить настройки можно без выхода/перезагрузки;
фактическая работа до первого входа после reboot требует отдельного испытания.
Истечение node key Tailscale требует владельца: исходная дата `2027-04-09T15:55:28Z`.
Отключение срока действия ключа автоматически не выполняется.

## Команды, сеансы и OAuth

Используется исходный OAuth и SQLite DevSpace. Обновление refresh token транзакционное и одноразовое;
истёкший bearer получает 401. Фоновая проверка не читает пользовательские токены и не выдаёт проверку
наличия OAuth за подтверждение действительности токена конкретного чата. Это подтверждает реальный
авторизованный вызов соединителя.

Workspace привязывается к `openai/session`; параллельное открытие одной папки внутри одного чата
защищено исходным pending map. Независимые обращения не сериализуются глобально. Одна и та же
рабочая папка остаётся общим файловым пространством: противоречащие изменения одного файла надо согласовывать.

`prepare-runtime.mjs` сохраняет ограничение точного известного `pi-tools.js`:
не более восьми одновременно выполняющихся вызовов Bash, без очереди и автоматического повтора.
Девятый отклоняется **до** запуска команды. Патч проверяет версию и SHA256 исходника, сохраняет оригинал
рядом как `.dsh-original`, повторное применение идемпотентно. Неизвестная версия/правка — отказ без перезаписи.
Это предел вызовов Bash, а не запрет дочерних процессов сборщика или явно запущенных пользователем фоновых программ.
Исходный предел одной команды — 300 секунд. Обёртка не вводит тайм-аут ответа короче этого предела.

Для новых пишущих заданий Postman добавлен инструментальный учёт в `pi-tools.js` и `server.js`.
Первый `open_workspace` с адресом `postman-writer:<bridgeJobId>` связывает существующий private Host
binding с `openai/session`, разрешённым корнем и отдельным поколением исполнения. Без такого binding
нет положительного native proof. После отзыва старого канала его будущие обращения отклоняются;
новая разрешённая попытка может получить отдельное поколение/папку без возврата прав старого REQ.
Обычный буквальный путь не заменяет этот адрес для пишущего Postman-задания.

Обычный DevSpace без проверенного Postman binding использует исходный executor `createBashTool`:
Postman helper не выбирается по одному ALS-store, workspace/cwd или совпадению пути. Ограничение восьми
одновременных Bash-вызовов и исходный предел команды 300 секунд сохраняются.

На проверенной Windows x64 отдельный read-only `ordinary-process.ps1` наблюдает полный список живых
PID, родителей и точных времён создания. Node diagnostics связывает исходный ChildProcess с активным
вызовом без подмены executor. До запуска фиксируется исходный список, а после завершения handler/root
наблюдатель подтверждает новый снимок по адресному ticket/ack: старые данные в канале не считаются
снимком после команды. Если возможных потомков нет, временная запись очищается и в `otherTools`, и в
durable `untrackedRoots`; короткая команда не требует ручного разблокирования. `exitCode:0` сам по себе
этого не доказывает. Живой detached-потомок удерживает пересекающуюся область для нового Postman writer;
после его фактического завершения native observation автоматически снимает это ограничение.

Новый shared-write Bridge получает `POSTMAN_TASK_CONTEXT_BUSY` до создания REQ/очереди, если ordinary
writer ещё активен. После подтверждённого окончания обычный повтор допускается. Чтение и независимые
папки доступны; обычные DevSpace write/edit/Bash не получают общего запрета из-за своего фонового сервера.
Приватный `/ordinary-admission` только наблюдает native state и не останавливает процессы.

Это ограниченное наблюдение, а не полная история ETW или изоляция ОС. Новый живой процесс с потерянной
цепочкой родителей консервативно считается возможным потомком. Ошибка snapshot/layout/канала, потеря
контроллера и старые неотслеживаемые корни оставляют `EXIT_UNPROVEN` только для пересекающейся записи
Postman. Такой UNKNOWN не превращается в active=0 после restart; безопасный выход — действительно новая
изолированная папка. Если недоступен сам сохранённый список корней, Host не подтверждает допуск записи
в общую папку. На неподдерживаемой платформе positive native absence не обещается.

Проверка Host binding отделена от вызова upstream handler: его исходные исключения, provider errors и
структурированный `isError:true` сохраняются. Host-отказы ownership/scope/root/revoke выполняются до handler;
публичный диагностический журнал не получает исходные сообщения исключений или приватное содержимое.

На Windows `writer-process.ps1` помещает Postman-запуск в Job Object до исполнения команды.
Короткая foreground-команда и whole-tree settlement — разные факты: положительный proof требует
нулевого числа процессов всего дерева, включая detached descendants. Для намеренного сервера/watcher
исполнитель использует существующий MCP Bash с `execution:'background'`, получает ID и состояние
работающего задания. `execution:'status'` с `job_id` проверяет его; без ID показывает только свои задания.
`execution:'stop'` требует точного ID и отдельного адресного намерения. Scope/generation и права старого
REQ проверяются; новый запуск не получает прав от наличия чужого ID. `postman_app` Worker не подменяет
этот маршрут ChatGPT DevSpace.

Завершение основной команды, тайм-аут ожидания, UI Stop и перезапуск Host не выключают фоновое приложение
и не означают whole-tree settlement. При неизвестном ответе запуска сначала запроси status, не повторяй
команду. Native-владение и адресная остановка отделены от ожидания ответа. Неизвестное завершение
helper/runtime не считается доказательством. Private loopback controller выдаёт Host факты exact
owner/REQ/root/branch/generation; `postman_bridge_status({bridge_job_id,reconcileWriter:true})`
снимает residual только после revoke, native settlement и проверки других writers. Release не меняет
файлы, не является PASS и сохраняется в current/retired task registry. Legacy/untracked задания,
потерянный runtime и неподдерживаемая платформа остаются `EXIT_UNPROVEN`: можно читать прежнюю
область или работать отдельно. UI Stop, browser exit и свободный порт недостаточны. Учёт scoped
native-команд не превращает произвольный Bash в файловую песочницу и не доказывает остановку
несвязанных внешних процессов ОС.

Сохранённые обычные Worker/Sol той же области, включая retired members, также не получают
physical proof от одного `idle`/закрытия сессии: их возможные native потомки этим механизмом
не отслеживались. При таких соседях release остаётся непроверенным, доступна новая изолированная
папка. Пересекающийся app job без native terminal также удерживает ресурс.

Именованный Job Object удерживает отдельный фиксированный процесс-владелец: выход Node-контроллера
не закрывает его native handle. Новый контроллер может найти собственный ID и адресно остановить
задание по сохранённому scope/generation, но потерянный общий учёт не восстанавливается как positive proof.
Сохранённый native hold защищает только пересекающуюся папку и после restart; снимается после durable release.

Патчер проверяет версию/SHA всех трёх upstream-файлов (`pi-tools.js`, `server.js`, `tool-surfaces/claude.js`)
до изменений и сохраняет оригиналы. Эти source-изменения
не устанавливают новый runtime и не перезапускают действующий сервер.

Наблюдатель **никогда не повторяет MCP-команды**. Если соединение оборвалось после начала изменяющей команды,
результат может быть неизвестен вызывающей стороне. MCP/соединитель не дают этому серверу общего надёжного
ключа идемпотентности: гарантировать однократность произвольного повторного вызова другого чата нельзя.
Нужно сначала проверить результат операции, а не посылать её заново. Сторонние ограничения времени ответа
ChatGPT и доступность его соединителя не исправляются локальным перезапуском.

## Диагностика и границы выводов

`logs/requests.jsonl` фиксирует начало, окончание и обрыв HTTP-запроса, код и длительность, название инструмента.
Он не записывает тело запроса/ответа, команду, путь личного файла, заголовки, токены и текст исключений.
Максимум около 2 MiB плюс одна предыдущая копия; `logs/watchdog.jsonl` — 1 MiB плюс одна копия.
Технические stdout/stderr нового запуска обновляются при старте. Старые журналы прежнего запуска сохранены
в локальной резервной копии, в Git их нет.

Во время исходной диагностики 16–17 октября 2026 г. два вызова `open_workspace` через соединитель вернули
`UNAVAILABLE`, хотя сервер записал успешное выполнение инструмента. Для одного публичного IPv4 также
наблюдались тайм-ауты TCP/TLS при работающих других входах. Это доказывает перемежающийся отказ доставки,
но не доказывает конкретную причину в Tailscale или ChatGPT. Позже реальный вызов Bash через соединитель
успешно вернул версию Node без перезапуска исходного сервера.

[Tailscale #21114](https://github.com/tailscale/tailscale/issues/21114) описывает расследование потери
регистрации Funnel после control-plane reconnect. Оно совместимо с частью симптомов, но конкретная причина
на этом ПК не установлена: прежние журналы не фиксировали начало/обрыв запроса, daemon logs требуют прав.
Отдельный Windows [#21752](https://github.com/tailscale/tailscale/issues/21752) закрыт как дубликат:
разработчик связывает тот случай с обратным сетевым маршрутом и другим VPN; строки `no rules matched`
сами по себе не доказывают отказ. В [changelog 1.104.1](https://tailscale.com/changelog) нет объявленного
исправления потери регистрации Funnel, поэтому обновление или откат без доказательств не выполняются.

Официальные сведения: [Windows Unattended](https://tailscale.com/docs/how-to/run-unattended),
[постоянный Funnel --bg](https://tailscale.com/docs/reference/tailscale-cli/funnel),
[OpenAI: диагностика MCP](https://developers.openai.com/plugins/deploy/troubleshooting),
[OAuth](https://developers.openai.com/plugins/build/auth).

## Расхождение схемы и обновление установленного MCP

Диагностика 17 октября 2026 г., база `origin/main`:
`306aa13075acc89f75e1b434ed5586dfb3c01ef7`. Исходный `prepare-runtime.mjs` уже добавлял
`execution`, `job_id`, необязательный `command` и структурированный ответ фонового задания.
Но в установке `C:/Users/Andrew/.dsh/devspace` этот патч не был применён целиком:

| Установленный файл | SHA256 | Фактическое содержимое |
| --- | --- | --- |
| `dist/pi-tools.js` | `c0f0fcfe63117092a0c81cf6588c50d9db9e4e516e74948469feafcfec8e22d7` | Только старый предел восьми вызовов; без `dshWriters.background` |
| `dist/server.js` | `0c7601c4be6b9d3a53ef7b4d672f43a3b728914cf10f255fdaed6c6cd849269a` | Исходный npm-файл; без привязки Host writer |
| `dist/tool-surfaces/claude.js` | `6fd9cb01bd4efcee55a457e310ae58530c92cd67fd623db274ba9f59d4bcf8f8` | Исходная регистрация Bash: обязательный `command`, без `execution`/`job_id` |

Пути в таблице относятся к `node_modules/@waishnav/devspace`. Настроен режим `claude`.
Настоящий OAuth + `tools/list` в изолированной копии этого пакета воспроизвёл старую схему;
такую же схему видит действующий соединитель ChatGPT. После подготовки копии тот же `tools/list`
возвращает enum `foreground|background|status|stop`, `job_id`, только `workspace_id` в `required`
и структурированные поля задания. Производственные OAuth и SQLite для этого не изменялись.

Доказанная причина — неприменённая подготовка runtime, а не один лишь кэш соединителя.
Прежний runner принимал такую частичную установку и успешно отвечал на `/healthz`.
Один перезапуск старых файлов не исправляет схему. Теперь runner до создания listener, журналов
и writer control выполняет **проверку без записи**. Он не устанавливает патч автоматически.
Проверка требует exact известных исходников всех трёх файлов и полного результата подготовки;
неизвестные изменения сохраняются с отказом.

Ложный retry Host воспроизведён на двух реальных русскоязычных ответах: слово `timeout` было
именем параметра в описании схемы. Прежняя проверка искала его во всём ответе, а выражение для
неподдерживаемой схемы не распознавало `execution:'status' не поддерживается текущей схемой`.
Замена только имени `timeout` прекращала retry. Теперь категория берётся из кода ошибки или явной
строки ошибки (`CAPABILITY_UNAVAILABLE: ...` / `CAPABILITY_UNAVAILABLE — ...`), а не из таблиц и
обычного текста. Русское сообщение о несовместимости, ошибки авторизации и `NEED_DECISION`
требуют решения; настоящие временные MCP-сбои сохраняют до трёх новых попыток с отдельными REQ.

### Процедура развёртывания — только после отдельного разрешения

PR сам по себе не изменяет работающие Host/MCP. Ниже описано будущее окно обслуживания;
в диагностике эти stop/copy/start и Refresh **не выполняются**. Host с исправленным классификатором
также нужно отдельно установить штатным способом из принятого SHA; исходники не заменяют код уже
загруженного процесса. VPN, Tailscale, URL, OAuth и `preview` для этого обновления не меняются.

1. Выбрать проверенный exact SHA и отдельный source worktree с этим изменением. Перед остановкой
   дождаться завершения активных MCP-вызовов и подтверждённого выхода всех собственных фоновых
   деревьев Postman. UNKNOWN/unproven writer — блокер обслуживания; не убирать lease/revocation,
   не завершать процессы по имени и не подменять доказательство свободным портом.
2. Из **source worktree**, не из прежней установки, проверить состояние без записи:

   ```powershell
   $source = '<проверенный source worktree>/devspace'
   $install = 'C:/Users/Andrew/.dsh/devspace'
   node "$source/prepare-runtime.mjs" $install --check
   ```

   Для описанной старой установки ожидается `DevSpace runtime patch required`, код 1, без изменений.
   `Unexpected upstream/patched source` — остановка и разбор отличий, не разрешение перезаписи.
3. Штатно остановить только DevSpace: `pwsh -NoProfile -File "$install/stop.ps1"`.
   Сценарий приостанавливает watchdog, проверяет идентичность PID и выполняет drain.
   При отказе/занятости остановиться; не обходить его `Stop-Process`, ручным kill или удалением state.
4. Сохранить в отдельную локальную папку резервную копию **точных установленных байтов** следующих
   файлов и уже существующих `.dsh-original`: `prepare-runtime.mjs`, `server-runner.mjs`,
   `writer-runtime.mjs`, `runtime-identity.mjs`, `writer-process.ps1`, `ordinary-process.ps1` и три `dist`-файла из таблицы.
   Сохранить перечень SHA256. Не удалять OAuth SQLite, config/auth, каналы Host, проекты и данные заданий.
5. Скопировать из выбранного source worktree шесть перечисленных `.mjs`/`.ps1`-сценариев, затем:

   ```powershell
   node "$install/prepare-runtime.mjs" $install
   if ($LASTEXITCODE -ne 0) { throw 'Подготовка не завершена; запуск запрещён.' }
   node "$install/prepare-runtime.mjs" $install --check
   if ($LASTEXITCODE -ne 0) { throw 'Runtime не готов; запуск запрещён.' }
   pwsh -NoProfile -File "$install/start.ps1"
   pwsh -NoProfile -File "$install/status.ps1"
   ```

   Патчер принимает исходный пакет, известный старый limiter и уже подготовленные файлы;
   повторная подготовка идемпотентна. Все входные SHA проверяются **до первой записи**.
   Не переносить готовые patched `dist` из тестового каталога: импорты содержат абсолютные пути,
   поэтому подготовка выполняется именно в `$install`.
6. Проверить реальный `tools/list` через авторизованный MCP Inspector на прежнем публичном `/mcp`
   (или уже авторизованным клиентом): enum четырёх режимов, `job_id`, необязательный `command`,
   выходные `native_job_id/state/jobs`. Пароли и bearer не переносить в команды чата/журналы.
   Затем выполнить в ChatGPT **Refresh** метаданных этого custom MCP и начать **новую беседу**.
   [Официальная процедура OpenAI](https://developers.openai.com/plugins/deploy/connect-chatgpt#refresh-metadata)
   требует обновления метаданных после изменения схемы. Полное удаление и повторная OAuth-привязка
   не являются обязательным шагом при прежних URL/auth; рассматривать их только если Refresh всё ещё
   показывает старую схему. В этой задаче обновление живого соединителя не проверяется и не выполняется.
7. В новой разрешённой Host-owned Postman-сессии открыть **собственный** `postman-writer:<bridgeJobId>`
   и проверить короткий безвредный `execution:'background'`, затем `status` и `stop` с полученным
   точным `native_job_id`. У обычного workspace без writer binding эти режимы закономерно возвращают
   `WRITER_BINDING_REQUIRED`; это не признак старой схемы. Проверить отсутствие лишнего Send/повтора
   старого REQ и завершение только собственного дерева.

При неуспехе сохранить диагностику, не повторять неизвестно выполненные команды. Для отката в том же
согласованном idle-окне восстановить все восемь точных файлов и состояние их резервных копий из шага 4,
затем штатно запустить прежнюю установку. `.dsh-original` содержит npm-оригинал, а не обязательно
предыдущий установленный limiter: один этот файл не заменяет полный снимок для отката.

## Проверки и откат

```powershell
pwsh -NoProfile -File devspace/tests/lifecycle.tests.ps1
node --test devspace/tests/runtime.test.mjs
node devspace/tests/native.integration.mjs
node devspace/tests/bash-limit.integration.mjs
node devspace/tests/disconnect.integration.mjs
node devspace/tests/background.integration.mjs
node --test devspace/tests/writer-parent-exit.test.mjs
node --test devspace/tests/error-propagation.test.mjs
node --test devspace/tests/ordinary-census.test.mjs
node --test devspace/tests/ordinary.integration.mjs
node --test devspace/tests/ordinary-parent-exit.test.mjs
```

Испытания создают отдельные временные проекты, процессы, порт и OAuth SQLite. Сбой внешнего маршрута
имитируется в принятии решений, рабочий Funnel не отключается. Полный тест проверяет две минуты команды,
независимое чтение, параллельные workspace, сохранение токена/сеанса после рестарта, истечение и refresh.
Перезагрузка, выход из Windows, отключение интернета и намеренный отказ рабочего Funnel не выполняются.

Установка файлов выполняется из проверенного task worktree с резервной копией существующих сценариев.
`install-watchdog.ps1` использует штатное UAC и проверяет, что повышение не изменило пользователя.
Для отката: приостановить/отключить задание Планировщика, штатно остановить новый сервер после окончания
работы, вернуть точные установленные сценарии и три patched-файла из локальной копии, затем запустить прежний
сервер. OAuth, SQLite, проекты, адрес и ключи не удаляются. Не использовать общий `funnel reset`.
