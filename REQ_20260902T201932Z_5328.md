# POSTMAN TASK

user_intent:
Луна, сделай небольшую правку **Postman trigger contract**.

## Цель

Сделать `@Postman` официальным и максимально явным trigger для Direct Postman.

После изменения канонический пользовательский вызов:

```text
@Postman <задача>
```

Например:

```text
@Postman сделай калькулятор в древне-японском стиле
```

или:

```text
@Postman в postman-check.html замени текст кнопки
```

Главный смысл:

> Если пользователь начинает implementation-запрос с `@Postman`, Luna обязана сначала загрузить `delegate-via-postman` и не имеет права начинать самостоятельную реализацию до загрузки этого skill.

Это небольшая правка инструкций. **Не менять Direct Postman transport, browser pipeline, applicator или runtime DSH.**

## Новый канонический trigger

В разделе Trigger явно зафиксировать:

```text
@Postman <user intent>
```

как **предпочтительный и канонический trigger**.

Например:

```text
@Postman сделай простой калькулятор.
@Postman создай страницу проверки.
@Postman измени существующий файл согласно этому запросу.
```

## Жёсткое правило

Добавить максимально явно:

```text
Если исходное пользовательское сообщение начинается с `@Postman`,
это однозначный explicit Postman trigger.

До загрузки этого skill Luna не должна выполнять implementation-действия:
glob по task-файлам,
read implementation-файлов,
edit,
write,
создание исходников,
выбор архитектуры,
implementation shell-команды,
frontend/design skills.

Первым task-specific действием должен быть вызов:
skill(delegate-via-postman)
```

После загрузки skill используется существующий golden path:

```text
exact user intent
→ one canonical REQ
→ one Direct Postman invocation
→ RESULT_DURABLE
→ deterministic applicator
→ tests
→ Git/PR
```

## Удаление transport marker из intent

Для:

```text
@Postman сделай калькулятор
```

payload для Ч1 должен быть:

```text
сделай калькулятор
```

То есть удалить только префикс:

```text
@Postman
```

и окружающий пробел.

Остальной user intent сохранять буквально по смыслу.

Не добавлять собственные требования.

# 3. Старые triggers оставить совместимыми

Не ломать существующую совместимость.

Можно оставить:

```text
Postman, ...
Через Postman ...
Используй Postman ...
```

как explicit legacy triggers.

Но в skill должно быть ясно:

```text
canonical / preferred:
@Postman ...

legacy-compatible:
Postman, ...
Через Postman ...
Используй Postman ...
```

То есть для новых пользовательских запросов основной синтаксис — `@Postman`.
