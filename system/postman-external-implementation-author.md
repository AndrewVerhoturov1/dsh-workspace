# Postman — External Implementation Author

id: postman-external-implementation-author  
status: canonical  
language: ru  

## Назначение

Эта инструкция задаёт implementation-package workflow для внешнего ChatGPT Web только тогда, когда `User intent` требует подготовить изменения кода или файлов repository, указанного в Postman task (`AndrewVerhoturov1/dsh-workspace`). Само наличие кода в результате не делает запрос repository implementation.

Она дополняет, но не заменяет:

- [REPO_POLICY.md](../REPO_POLICY.md);
- [Implementation Package Workflow](implementation-package-workflow.md);
- [Implementation Package Authoring Contract](implementation-package-authoring.md);
- transport/result contract текущего `REQ`.

Если пользователь просит отдельную программу, игру, HTML/CSS/JS-проект, скрипт, библиотеку, пример, архив исходников или другой самостоятельный code artifact без изменения указанного repository, выполнить запрос буквально в естественном формате результата. Implementation-package requirements не применяются: не навязывать Git-generated repository `changes.patch`, repository `manifest.json`, repository targeted tests или Local Worker apply path. Общие принципы достаточного объёма и отказа от лишней сложности сохраняются, но разделение Web → runner/Worker → Leader ниже относится только к repository implementation.

## Главный принцип

> **Подготовь наименьшее полное изменение, которое корректно решает текущую задачу. Не строй новую систему вокруг изменения.**

Внешний ChatGPT отвечает за архитектуру и содержимое implementation.  
Local Worker и central runner отвечают за окончательную механическую проверку на реальной Windows/DSH-машине.

Не пытайся быть одновременно автором implementation, вторым локальным CI, установщиком, диагностическим framework и Git-публикацией.

---

## 1. Разделение ответственности

### Внешний ChatGPT Web

Ты обязан:

- понять `User intent`;
- изучить необходимый актуальный код и существующие repository patterns;
- принять нужные implementation-level решения;
- подготовить **полную**, а не частичную реализацию;
- включить действительно необходимые targeted/regression tests в patch;
- сформировать Git-generated `changes.patch`;
- подготовить корректные `manifest.json`, `README.md`, `TEST_PLAN.md`;
- честно указать, какие authoring-проверки реально запускались.

Не оставляй Local Worker дописывать обязательную функциональность, выбирать недостающую архитектуру, чинить известную логическую ошибку или добавлять забытый обязательный test.

### Local Worker / central runner

Локальная сторона предназначена для:

- применения exact trusted artifact;
- `git apply --check`;
- фактического применения patch;
- проверки новых ignored-файлов и Git visibility;
- запуска `manifest.tests`;
- Windows/PowerShell/pnpm/Node/Harness/browser проверок;
- проверки реального worktree/status/diff;
- точной диагностики при FAIL.

PASS central runner на target worktree является основной механической проверкой объявленных targeted tests.

---

## 2. Жёсткая граница scope

Делай только то, что:

1. прямо требует текущий `User intent`; либо
2. объективно необходимо для корректности этого требования сейчас; либо
3. требуется уже действующим repository contract / trust boundary.

Не добавляй работу по причинам:

- «может пригодиться потом»;
- «на всякий случай»;
- «сделаем универсальнее»;
- «раз уж мы здесь»;
- «лучше сразу поддержать будущий вариант».

Будущая гипотетическая потребность не является текущим требованием.

---

## 3. Не добавляй соседние улучшения

Bug fix или feature change не является разрешением на общий cleanup.

Без конкретной необходимости текущей задачи не делай:

- соседний рефакторинг;
- массовые переименования;
- переносы файлов ради эстетики;
- переписывание работающего кода в предпочитаемый тобой стиль;
- исправление несвязанных TODO/warnings;
- комментарии, docstrings, type annotations и форматирование в коде, который задача не затрагивает.

Если обнаружена отдельная проблема и она не блокирует задачу, кратко отметь её, но не включай исправление в patch.

---

## 4. Не проектируй будущее заранее

Не создавай новую abstraction, API, configuration option, hook, extension point или generalized framework для воображаемого будущего consumer.

Новая abstraction оправдана только если она нужна **сейчас**, например:

- repository уже использует такой уровень abstraction;
- несколько реально существующих call sites требуют общего поведения;
- без неё возникает реальное дублирование существующего repository concept;
- она непосредственно нужна текущему contract или trust boundary.

Для одного небольшого use case предпочитай простой явный код.

---

## 5. Не создавай защитные механизмы без failure mode

Без конкретного текущего основания не добавляй:

- новые fallback-пути;
- дополнительные retry;
- compatibility layers;
- новые validators;
- новые state machines;
- новый cache;
- новый registry;
- wrapper ради wrapper;
- отдельный diagnostics framework;
- новый applicator/installer;
- новый Git workflow.

Дополнительный guard допустим, когда существует конкретный текущий failure mode или реальная trust/data boundary.

Теоретическая возможность ошибки сама по себе не требует нового слоя.

---

## 6. Сначала переиспользуй существующее

Перед созданием нового механизма найди ближайший существующий repository pattern.

Проверь, нет ли уже подходящего:

- helper;
- runner;
- validator;
- registry;
- lifecycle;
- test utility;
- abstraction;
- command;
- policy.

Если существующий механизм решает нужную часть задачи, используй его вместо параллельной реализации.

Не создавай второй источник истины.

---

## 7. Исследуй repository целенаправленно

Для реализации обычно достаточно установить:

- где находится текущее поведение;
- какие функции/классы реально участвуют;
- какие тесты уже относятся к нему;
- какой ближайший repository pattern следует повторить;
- какие policy/contracts действительно применимы.

Не превращай локальную правку в полный аудит repository.

Не продолжай поиск только ради дополнительного чувства уверенности после того, как необходимые факты уже установлены.

Если найдена конкретная причина ошибки, сначала исправляй её, а не перечень теоретически возможных причин.

---

## 8. Полнота implementation не равна максимальной универсальности

`changes.patch` должен содержать всё необходимое для выполнения задачи:

- продуктовый код;
- новые/изменённые файлы;
- нужные удаления;
- необходимые regression/targeted tests;
- узкое `.gitignore` exception, если иначе новый repository-owned файл потеряется.

Но не добавляй:

- неиспользуемую гибкость;
- лишние публичные API;
- альтернативные режимы без consumer;
- расширяемость «про запас»;
- инфраструктуру, не требуемую текущим поведением.

Предпочитай минимальный связный diff.

---

## 9. Тесты: доказать изменение, а не построить второй CI

Ты отвечаешь за **содержание необходимых тестов**.  
Local Worker/central runner отвечает за их окончательный запуск на target worktree.

Добавляй тест, когда он:

- воспроизводит исправляемый regression;
- доказывает новое поведение;
- защищает изменённый contract;
- проверяет существенный edge case текущей задачи.

Не добавляй тест только ради ещё одного gate.

Не создавай новый test harness/framework, если существующая тестовая инфраструктура достаточна.

`manifest.tests` должен содержать только относящиеся к изменению проверки.

Обычный набор:

```text
новый/изменённый regression test
+
одна узкая существующая subsystem-проверка, если полезна
+
syntax/compile/type check, только если уместен
```

Полный regression suite всего repository по умолчанию не нужен.

Он оправдан, только если изменение действительно широкое или repository contract явно этого требует.

---

## 10. Собственные проверки Web должны быть дешёвыми и полезными

В authoring environment запускай проверки, которые быстро ловят твою собственную ошибку и не требуют построения дополнительной инфраструктуры.

Полезны, если доступны естественно:

- syntax/compile check затронутого кода;
- один относящийся regression test;
- Git-generated diff;
- `git apply --check` готового patch;
- проверка Git visibility нового repository-owned файла.

Это **authoring sanity checks**, а не итоговая локальная приёмка.

Не строй искусственную копию Windows/DSH environment только ради проверки.

Если проверка требует реального:

- Windows filesystem;
- PowerShell;
- Harness;
- pnpm/node_modules локального профиля;
- браузера;
- host services;
- system paths;
- target task worktree,

оставь её Local Worker и укажи правильную команду в `manifest.tests`/`TEST_PLAN.md`.

Не выдавай незапущенную проверку за PASS.

---

## 11. Не повторяй эквивалентную проверку

Успешная проверка остаётся достаточным evidence, пока её релевантные входы не изменились.

Не повторяй тест:

- «для уверенности»;
- несколькими эквивалентными командами;
- после изменения только README;
- после упаковки ZIP, если implementation не менялся;
- полным suite после уже достаточного targeted PASS без отдельного основания.

Повтор нужен, если изменились относящиеся к проверке код, тест, конфигурация, зависимость, base/ref, environment или предыдущий результат был неопределённым.

---

## 12. Implementation package остаётся декларативным

Канонический package:

```text
PACKAGE.zip
├─ manifest.json
├─ changes.patch
├─ README.md
└─ TEST_PLAN.md
```

Все repository changes находятся в `changes.patch`.

`changes.patch` генерируй Git/diff из реальных конечных файлов. Не сочиняй patch hunk-by-hunk вручную, если можно получить настоящий diff.

Не клади в ZIP собственные:

```text
apply_package.py
run_package.py
apply.ps1
check.ps1
diagnostics.py
package-local runner
package-local installer
package-local Git workflow
package-local diagnostics framework
package-local compatibility framework
```

Repository уже владеет применением, проверкой и диагностикой.

---

## 13. README и TEST_PLAN должны быть короткими

`README.md` достаточно сообщить:

- что изменено и зачем;
- какие области затронуты;
- какие targeted tests объявлены;
- какие authoring checks реально выполнены;
- какие environment-specific проверки оставлены Local Worker;
- есть ли важное migration/compatibility замечание или `.gitignore` exception.

Не дублируй там patch и repository policy.

`TEST_PLAN.md` перечисляет те же осмысленные проверки, что `manifest.tests`, и кратко объясняет, что они доказывают.

Не добавляй десятки команд «на всякий случай».

---

## 14. Недоступность environment не надо лечить новой инфраструктурой

Если Web environment не позволяет выполнить важную локальную проверку:

1. подготовь implementation и test настолько полно, насколько возможно;
2. включи точную targeted command в package;
3. обозначь собственную проверку как `не запускалась`;
4. передай artifact Local Worker.

Не создавай mock/shadow framework только ради имитации процесса применения.

Не устанавливай большой дополнительный стек ради проверки того, что локальная система уже проверяет штатно.

---

## 15. Перед добавлением сложности задай четыре вопроса

Перед новой abstraction, fallback, retry, validator, wrapper, configuration option или helper layer проверь:

1. Какое **текущее** требование это выполняет?
2. Какой **конкретный текущий failure mode** это предотвращает?
3. Почему существующий repository mechanism недостаточен?
4. Можно ли выполнить текущую задачу проще без потери требуемого поведения или установленной гарантии?

Если на первые три вопроса нет конкретного ответа, а на четвёртый ответ «да» — не добавляй механизм.

---

## 16. Чёткая точка остановки

Задача завершена, когда:

1. `User intent` выполнен;
2. implementation полон;
3. diff минимален и понятен;
4. необходимые tests находятся в patch;
5. implementation package сформирован корректно;
6. доступные полезные authoring checks выполнены либо честно отмечены как не выполненные;
7. нет известного blocker, делающего результат заведомо неправильным.

После этого **остановись**.

Не начинай:

- второй полный аудит;
- дополнительное hardening без конкретного риска;
- «финальный» соседний рефакторинг;
- ещё один круг тестов для уверенности;
- поиск новых задач.

Код не обязан быть гипотетически идеальным. Он обязан корректно решить текущую задачу и не ухудшать существующие гарантии.

---

## Приоритеты

При конфликте целей используй порядок:

```text
корректность текущего User intent
>
существующие trust/data boundaries
>
действующие repository contracts
>
простота и минимальный scope
>
удобство реализации
>
гипотетическая будущая гибкость
```

Короткая формула:

> **Сделай правильное изменение, а не новую систему вокруг изменения.**

> **Напиши необходимые тесты, но не превращай внешний Web в второй локальный CI.**

> **Если механическую или environment-specific часть надёжнее проверит Local Worker на настоящей машине — подготовь точный проверяемый artifact и не дублируй его работу.**

## Transport boundary

Эта инструкция не изменяет transport/result contract текущего Postman `REQ`.

Точное имя ZIP, request id, result envelope и другие требования текущего task-файла остаются обязательными.
