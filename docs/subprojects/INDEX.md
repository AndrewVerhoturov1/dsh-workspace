# Подпроекты DSH

Подпроект — это долговременный контекст отдельного направления работы внутри `dsh-workspace`.
Он нужен, чтобы следующий агент или новый чат быстро понял цель, текущее состояние, следующий шаг,
принятые решения и границы работы без чтения всей истории репозитория.

## Модель

Подпроект не является задачей, `REQ`, веткой или Pull Request.

```text
подпроект
→ несколько отдельных задач
→ несколько REQ при необходимости
→ несколько временных task branches / PR
```

Ветки и PR остаются временными по `REPO_POLICY.md`; долговременная память направления хранится в документах подпроекта.

## Когда создавать подпроект

Создавать подпроект стоит, если направление:

- состоит из нескольких отдельных задач или этапов;
- будет продолжаться в разных чатах или сессиях;
- имеет решения и ограничения, которые нужно помнить дальше;
- требует ограниченного набора документов и путей для чтения;
- имеет понятный текущий фокус и следующий шаг.

Не создавать подпроект для разовой маленькой правки, одиночного бага или одной короткой задачи.

## Структура

Каждый подпроект хранится отдельно:

```text
docs/subprojects/<id>/
├─ SUBPROJECT.md
└─ JOURNAL.md
```

`SUBPROJECT.md` — единственный канонический источник текущего состояния подпроекта.

`JOURNAL.md` — короткая история только существенных решений и этапов. Он не заменяет `SUBPROJECT.md` и не должен превращаться в лог каждого commit или теста.

## Содержимое SUBPROJECT.md

Минимально фиксируются:

- `id`;
- `status`;
- дата обновления;
- цель;
- текущий фокус;
- следующий шаг;
- границы;
- что прочитать сначала;
- основные пути;
- текущие принятые решения.

Допустимые статусы v1:

```text
active
planned
paused
completed
archived
```

## Порядок чтения

Подпроект не переопределяет глобальные правила репозитория.

Порядок приоритета:

```text
AGENTS.md
→ REPO_POLICY.md
→ канонический workflow/contract затронутой подсистемы
→ SUBPROJECT.md конкретного подпроекта
→ task-specific документы
```

Не читать все подпроекты подряд. Если текущая задача явно относится к одному существующему подпроекту, читать только его контекст и необходимые связанные документы.

## Журнал

В `JOURNAL.md` добавлять только события, которые полезны будущему исполнителю:

- важное решение;
- завершённый этап;
- изменение направления;
- существенная проверка принятого результата;
- закрытие, пауза или архивирование подпроекта.

Формат одной записи:

```text
дата + короткое название
что изменилось
почему
результат
```

Не копировать туда сырые логи, полные отчёты тестов и микрошаги.

## Регистрация подпроекта

1. Создать `docs/subprojects/<id>/`.
2. По шаблону `_TEMPLATE.md` создать `SUBPROJECT.md` и `JOURNAL.md`.
3. Добавить подпроект в таблицу ниже.
4. При изменении текущего состояния обновлять `SUBPROJECT.md`.
5. При существенном событии добавлять короткую запись в `JOURNAL.md`.

## Принцип v1

Версия v1 намеренно остаётся Markdown-only: без `subproject.json`, генераторов, отдельного CI и обязательных скриптов проверки. Автоматизация добавляется только если реальное использование покажет, что ручной формат перестал быть достаточным.
