# DSH Agent Orchestration — MVP

## Статус документа

Этот документ фиксирует согласованную границу MVP плагина DSH Agent Orchestration.

MVP должен быть **маленьким вертикальным срезом будущей системы**, а не временным прототипом с другой логикой.

Главная цель MVP:

> Пользователь визуально собирает команду настоящих DSH-агентов, сохраняет её, выбирает эту команду в обычном чате DSH, запускает и наблюдает, как агенты работают, общаются и выполняют формальные поручения.

---

# 1. Основные принципы MVP

## 1.1. DSH остаётся владельцем агентов

Плагин не создаёт собственный параллельный движок агентов.

Каждый `AgentNode` в запущенной команде должен соответствовать настоящему агенту DSH и настоящей DSH Session.

DSH отвечает за:

- самих агентов;
- DSH Sessions;
- модельные вызовы;
- инструменты и другие доступные возможности;
- состояние отдельного агента;
- остановку и продолжение работы агента.

Плагин отвечает за:

- схему команды;
- иерархию;
- связи общения;
- задачи;
- состояние запуска команды;
- визуальное управление;
- привязку AgentNode к DSH Agent / Session в конкретном запуске.

---

## 1.2. Пользователь задаёт структуру команды

В MVP агенты сами не:

- создают новых агентов;
- удаляют агентов;
- меняют иерархию;
- меняют связи общения;
- перестраивают граф.

Структуру задаёт пользователь через визуальный редактор.

---

## 1.3. Подчинение и общение — разные понятия

Нельзя считать, что одна линия на графе автоматически означает всё сразу.

Нужно различать:

### Authority

Кто является начальником агента.

### Communication

Кто кому может отправлять сообщения.

### Task

Кто кому формально поручил работу.

Даже если интерфейс MVP делает это визуально просто, внутри системы эти понятия не должны смешиваться.

---

## 1.4. Пользователь может открыть любого агента

Пользователь — абсолютный оператор команды.

Из редактора команды можно открыть настоящий обычный чат DSH любого запущенного агента.

Внутренние ограничения общения агентов не ограничивают пользователя.

---

# 2. Главный пользовательский сценарий

Первый рабочий сценарий MVP должен выглядеть примерно так.

1. Пользователь открывает **Agent Team Editor**.
2. Создаёт новую схему команды.
3. Добавляет:
   - Lead;
   - Developer;
   - Researcher.
4. Настраивает каждого агента.
5. Соединяет агентов отношениями подчинения и общения.
6. Выбирает Lead как **Entry Agent**.
7. Система проверяет схему.
8. Пользователь сохраняет команду.
9. Пользователь открывает новый обычный чат DSH.
10. Нажимает **Use Agent Team**.
11. Выбирает сохранённую команду.
12. Запускается новый `TeamRun`.
13. Для AgentNode создаются или подключаются реальные DSH Agents / Sessions.
14. Обычный чат пользователя становится главным каналом общения с Entry Agent.
15. Пользователь пишет Lead цель.
16. Lead может:
    - написать подчинённому обычное сообщение;
    - создать для подчинённого формальную Task.
17. Developer или Researcher выполняет работу.
18. На графе в реальном времени видно состояние агентов.
19. Пользователь может открыть настоящий DSH Chat любого участника.
20. Исполнитель завершает Task и возвращает результат начальнику.
21. Пользователь может поставить команду на паузу, продолжить или остановить.
22. Схему можно позже снова загрузить и использовать для нового запуска.

Если этот сценарий работает надёжно, MVP считается состоявшимся.

---

# 3. Что входит в MVP

# 3.1. Отдельный нодовый редактор

Нужен отдельный большой интерфейс, а не маленькая боковая панель.

По способу взаимодействия ориентир — ComfyUI.

Минимальные возможности Canvas:

- создание Agent Node;
- удаление Agent Node;
- drag & drop;
- pan;
- zoom;
- сетка;
- соединение нод;
- удаление связей;
- выбор ноды;
- выбор связи;
- сохранение схемы;
- загрузка схемы.

В MVP на Canvas существует только один полноценный тип ноды:

> `AgentNode`

Служебные ноды пока не нужны.

---

# 3.2. Agent Node

Карточка агента на Canvas должна быть компактной.

Пример:

```text
┌─────────────────────┐
│ Backend Developer   │
│ GPT-5.6 Sol · High  │
│ ● Running           │
└─────────────────────┘
```

Основные настройки открываются в большом Inspector справа.

Минимальные настройки агента:

- отображаемое имя;
- техническое имя;
- роль / описание;
- модель;
- уровень рассуждений;
- системный промт;
- доступные возможности / Capabilities.

У агента также должен быть внутренний стабильный ID, который пользователь обычно не видит.

Пример:

```text
Display name:
Backend Developer

Technical name:
backend_developer

Internal ID:
agent_01...
```

Переименование агента не должно ломать связи и историю.

---

# 3.3. Capabilities агента

Не ограничивать модель конфигурации понятием `Tools`.

В интерфейсе лучше использовать более общее понятие:

> **Capabilities / Доступы**

В будущем сюда могут входить:

- Tools;
- Skills;
- MCP;
- Files;
- Repositories;
- Network;
- внешние сервисы;
- другие ограничения.

В MVP нужно показывать и применять только те возможности, которые реально поддерживает текущий DSH.

Запреты должны применяться программно, а не только через текст системного промта.

---

# 3.4. Inspector справа

При выборе AgentNode справа открывается большой Inspector.

Пример структуры:

```text
Agent

Name
Technical name
Role
Model
Reasoning
Capabilities
System prompt

Runtime
Status
Parent
Current task

[ Open Chat ]
```

Inspector является основным местом редактирования настроек выбранного агента.

---

# 3.5. Настоящий DSH Agent и постоянная Session

После запуска команды AgentNode становится связан с настоящим DSH Agent.

```text
AgentNode
    ↓
AgentRuntime
    ↕
DSH Agent
    ↕
DSH Session
```

В рамках одного `TeamRun` агент должен сохранять одну продолжаемую Session.

То есть:

- Lead написал Developer;
- Developer выполнил Task;
- пользователь открыл его чат;
- Lead снова написал Developer;

это всё тот же агент с той же историей в рамках данного запуска.

Сохранённая схема команды при этом не должна навечно владеть одной конкретной Session.

Новый запуск команды создаёт новый `TeamRun`.

---

# 3.6. Open Chat

У каждого запущенного AgentNode должна быть кнопка:

> **Open Chat**

Она открывает обычный настоящий DSH Chat соответствующей Session.

Плагин не создаёт отдельную поддельную систему пользовательских чатов внутри редактора.

---

# 3.7. Иерархия подчинения

MVP поддерживает отношение:

```text
Parent → Child
```

Пример:

```text
        Lead
       /    \
      ↓      ↓
Developer  Researcher
```

Правила:

- у агента максимум один непосредственный родитель;
- у родителя может быть несколько детей;
- циклы запрещены;
- должен существовать один Entry Agent / корневой агент для основного пользовательского канала.

Подчинение означает организационную власть и право формально поручать работу.

---

# 3.8. Общение между агентами

Общение должно быть отдельной настройкой от подчинения.

Например:

```text
Developer ↔ Researcher
```

может означать разрешённое общение без отношения начальник / подчинённый.

Для MVP пользователь должен иметь возможность задавать разрешённое направление общения.

Минимально:

```text
Lead → Developer
Developer → Lead
```

В Inspector выбранной связи можно показывать:

```text
Authority:
Lead is parent of Developer

Communication:
✓ Lead → Developer
✓ Developer → Lead
```

Все сообщения должны проходить через слой плагина, который:

1. знает отправителя;
2. знает получателя;
3. проверяет разрешение;
4. сохраняет сообщение;
5. доставляет его в DSH Session адресата.

---

# 3.9. Минимальная система Messages

Не каждое взаимодействие является Task.

Должно существовать обычное сообщение между агентами.

Минимально сообщение хранит:

```text
from
to
text
time
status
```

Например:

```text
Lead → Researcher

"Какую версию библиотеки мы сейчас используем?"
```

Это обычное сообщение, не Task.

---

# 3.10. Минимальная система Tasks

MVP должен содержать простую формальную Task.

Task означает:

> один агент формально поручил другому выполнить работу.

Пример:

```text
Task:
Исправить падение auth-тестов

Created by:
Lead

Assigned to:
Developer

Status:
Working
```

Минимальные данные Task:

- кто создал;
- кому назначено;
- цель;
- опционально критерий готовности;
- статус;
- результат.

Минимальные состояния:

```text
Created
Working
Completed
Failed
Cancelled
```

Не каждое сообщение превращается в Task.

---

# 3.11. TaskAttempt

Пользователю в MVP не требуется отдельный интерфейс TaskAttempt.

Но внутри системы Task и конкретное выполнение Task должны быть разными сущностями.

```text
Task
  └── TaskAttempt #1
```

Для MVP достаточно ограничения:

> одна Task — одна попытка.

Это оставляет правильную границу для будущих:

- retry;
- reassign;
- recovery;
- отмен;
- защиты от запоздавших результатов старой попытки.

---

# 3.12. Завершение Task

Когда исполнитель закончил работу, он должен иметь системное действие вроде:

```text
complete_task(result)
```

После этого плагин:

1. завершает текущий TaskAttempt;
2. завершает Task;
3. сохраняет результат;
4. сообщает результат начальнику;
5. обновляет состояние в интерфейсе.

Оркестратор не должен автоматически выбирать исполнителю следующую работу.

Следующее действие решает начальник.

---

# 3.13. Entry Agent

В каждой схеме выбирается один главный агент:

> **Entry Agent**

Обычно это Lead.

Схема:

```text
USER
  │
  ▼
Lead
 ├── Developer
 └── Researcher
```

Именно через Entry Agent пользователь по умолчанию взаимодействует с командой.

Других агентов пользователь всё равно может открыть напрямую через Open Chat.

---

# 3.14. Use Agent Team в обычном DSH Chat

В новом обычном чате DSH должна быть функция:

> **Use Agent Team**

После нажатия пользователь выбирает сохранённую схему:

```text
Choose team

○ Software Team
○ Research Team
○ Coding Team
```

После выбора:

- создаётся новый `TeamRun`;
- запускаются агенты;
- этот обычный DSH Chat становится главным пользовательским каналом данного TeamRun;
- сообщения пользователя получает Entry Agent.

Это один из центральных пользовательских сценариев MVP.

---

# 3.15. Validate

Перед запуском схема обязательно проверяется.

Validate можно запускать отдельной кнопкой или автоматически при Start.

Минимальные проверки:

- существует Entry Agent;
- нет циклов иерархии;
- у агента не более одного родителя;
- связи указывают на существующие ноды;
- технические имена не конфликтуют;
- выбранные модели доступны;
- обязательные настройки заполнены;
- разрешения / Capabilities не содержат очевидно невозможных комбинаций;
- возможно создать необходимые DSH Agents / Sessions.

Ошибки делятся минимум на:

```text
ERROR
WARNING
```

При наличии блокирующей ошибки Start запрещён.

---

# 3.16. TeamRun

Сохранённая схема и конкретный запуск — не одно и то же.

Например:

```text
Software Team
```

— это сохранённая схема.

А:

```text
Software Team
Run #14
```

— конкретный живой запуск.

`TeamRun` должен знать:

- какую версию схемы запустили;
- какие AgentNode существуют в этом запуске;
- какие DSH Sessions им соответствуют;
- текущее состояние команды;
- сообщения;
- Tasks;
- TaskAttempts.

Полноценный интерфейс истории запусков в MVP не обязателен.

Но сама сущность TeamRun обязательна.

---

# 3.17. Start / Pause / Resume / Stop

MVP должен поддерживать управление всей командой.

## Start

```text
START
```

- проверяет схему;
- создаёт TeamRun;
- создаёт / подключает DSH Agents;
- связывает AgentNode с DSH Sessions;
- переводит Run в RUNNING.

## Pause

```text
RUNNING
→ PAUSING
→ PAUSED
```

Минимальная мягкая пауза:

- перестать выдавать новую работу;
- не запускать новые модельные ходы;
- дать уже начавшимся операциям прийти в безопасное состояние;
- перейти в PAUSED.

## Resume

```text
PAUSED
→ RUNNING
```

Продолжает существующий TeamRun.

## Stop

```text
RUNNING / PAUSED
→ STOPPED
```

Останавливает текущий TeamRun.

В MVP **не требуется** полноценное редактирование живой схемы на Pause.

Полный сценарий:

```text
Pause
→ Edit
→ Validate
→ Resume
```

остаётся следующим этапом.

---

# 3.18. Live Status на Canvas

На AgentNode должен отображаться runtime-статус в реальном времени.

Минимально:

```text
Not started
Idle
Running
Paused
Error
Stopped
```

Дополнительно, если DSH предоставляет данные, можно показывать:

```text
Current task:
Fix auth tests
```

или:

```text
Last action:
files.read
```

Пользователь должен, просто посмотрев на Canvas, понимать:

- кто работает;
- кто ждёт;
- кто остановлен;
- кто упал с ошибкой.

---

# 3.19. Сохранение и загрузка схем

Пользователь должен иметь возможность:

```text
New
Save
Save As
Open
```

Сохраняются:

- AgentNodes;
- настройки агентов;
- Authority-связи;
- Communication-связи;
- Entry Agent;
- layout Canvas.

---

# 4. Team Definition и Team Layout

Эти сущности нужно разделить сразу.

## TeamDefinition

Содержит смысл команды:

```text
Agents
Agent configuration
Authority relations
Communication permissions
Entry Agent
Team settings
```

## TeamLayout

Содержит только отображение:

```text
node positions
viewport
zoom
visual state
```

Перемещение ноды по Canvas не должно считаться изменением поведения команды.

---

# 5. Минимальный интерфейс MVP

Для первого MVP достаточно нескольких основных областей.

## 5.1. Agent Team Editor

Большой Canvas.

## 5.2. Inspector

Большая правая панель свойств выбранной ноды или связи.

## 5.3. Run Controls

```text
Validate
Start
Pause
Resume
Stop
```

## 5.4. Activity

Небольшая панель текущей активности.

Минимально:

```text
Tasks
Messages
```

Пример:

```text
TASK-12  Developer   Working
TASK-11  Researcher  Completed
```

Полноценный отдельный Task Graph в MVP не нужен.

## 5.5. DSH Chat integration

В обычном новом чате:

```text
Use Agent Team
```

и выбор сохранённой схемы.

---

# 6. Что существует внутри системы, но не должно усложнять UI

Пользователю не обязательно знать внутренние термины архитектуры.

Но под капотом должны существовать правильные границы:

```text
TeamDefinition
TeamLayout
TeamRun

AgentNode
AgentRuntime

Message

Task
TaskAttempt
```

Этого достаточно для MVP.

---

# 7. Что НЕ входит в MVP

Следующие возможности сознательно откладываются.

## Tasks

Не входят:

- Task Dependency Graph;
- сложные Task Contracts;
- retry UI;
- reassign;
- автоматический scheduler;
- priorities;
- deadlines;
- evidence;
- сложные правила завершения.

## Responsibility

Пока не реализуется полноценная передача ответственности:

```text
"возьми эту область под своё управление"
```

В MVP достаточно обычного поручения работы.

## Decisions

Не входят:

- Decision;
- Approval Policy;
- архитектурные approval gates;
- пользовательские подтверждения как отдельная подсистема.

## Await

Не входят:

- AwaitSet;
- ALL / ANY / N-of-M;
- сложный Wake Scheduler.

## Artifacts и память

Не входят:

- Artifact Store;
- Artifact Versioning;
- общая память проекта;
- semantic search;
- Knowledge nodes;
- автоматическая сборка контекста из материалов.

## Служебные ноды

Не входят:

- Router;
- Queue;
- Condition;
- Approval Node;
- Memory Node;
- Resource Node;
- Tool Node;
- MCP Node;
- Skill Node.

## Динамическая структура

Не входят:

- создание агентов самими агентами;
- удаление агентов агентами;
- изменение связей агентами;
- автоматические GraphPatch;
- live topology editing.

## Pause / Edit / Resume

В MVP есть Pause и Resume.

Но нет полноценного изменения структуры живого TeamRun между ними.

## Recovery

Не требуется полноценное аварийное восстановление всего Run после падения DSH.

Но данные MVP не должны существовать только в оперативной памяти.

## Analytics

Не входят:

- стоимость;
- бюджеты;
- глубокая аналитика;
- timeline;
- сложные метрики;
- несколько режимов визуализации графа.

## Import / Export

Не являются обязательными для первого MVP:

- экспорт команды;
- импорт команды;
- marketplace шаблонов;
- fork / clone workflow.

---

# 8. Границы, которые нужно сохранить уже сейчас

Даже если функции ещё не реализованы, MVP не должен закрывать путь к ним.

## 8.1. Task и TaskAttempt разделены

Чтобы позже добавить retry и reassign.

## 8.2. Authority и Communication разделены

Чтобы позже разрешить сложные peer-to-peer каналы.

## 8.3. TeamDefinition и TeamLayout разделены

Чтобы визуальные изменения не меняли смысл схемы.

## 8.4. TeamDefinition и TeamRun разделены

Чтобы одну схему можно было запускать многократно.

## 8.5. AgentNode и AgentRuntime разделены

Чтобы сохранённая нода не была жёстко привязана к одной Session навсегда.

## 8.6. Конфигурация агента расширяемая

Она не должна навсегда сводиться к:

```text
name
model
prompt
```

## 8.7. Capabilities — общая сущность

Не проектировать права исключительно как список Tools.

## 8.8. Состояние команды хранит программа

Критические факты не должны существовать только в prompt / context Lead.

# 9. Что должно считаться готовым MVP

MVP можно считать успешным, если стабильно работает следующий тест.

## Setup

Пользователь создаёт:

```text
        Lead
       /    \
Developer  Researcher
```

Настраивает модели, prompts и Capabilities.

Lead назначен Entry Agent.

Схема успешно проходит Validate и сохраняется.

## Start

Пользователь открывает новый DSH Chat.

Выбирает:

```text
Use Agent Team
→ Software Team
```

Создаётся TeamRun.

У каждого AgentNode появляется настоящая DSH Session.

## Work

Пользователь пишет Lead:

> Разберись, почему приложение падает.

Lead создаёт Task для Developer.

Lead может отдельно написать Researcher сообщение.

Developer начинает работать.

На Canvas видно:

```text
Lead        Idle
Developer   Running
Researcher  Running
```

## Inspection

Пользователь нажимает Developer:

```text
Open Chat
```

и попадает в настоящий DSH Chat этого агента.

## Completion

Developer завершает Task.

Результат сохраняется и приходит Lead.

Lead решает, что делать дальше.

Оркестратор самостоятельно не назначает Developer следующую задачу.

## Control

Пользователь может:

```text
Pause
Resume
Stop
```

## Reuse

Сохранённую схему можно открыть снова и запустить как новый TeamRun.

# 10. Итоговая граница MVP

В MVP входят:

1. отдельный Agent Team Editor;
2. ComfyUI-подобный Canvas;
3. AgentNode;
4. Inspector справа;
5. основные настройки агента;
6. расширяемая модель Capabilities;
7. настоящий DSH Agent / Session на AgentNode во время Run;
8. Open Chat;
9. Authority;
10. Communication;
11. Message Bus;
12. минимальная система Messages;
13. минимальная система Tasks;
14. внутренний TaskAttempt;
15. Entry Agent;
16. Use Agent Team в обычном DSH Chat;
17. Validate;
18. TeamRun;
19. Start;
20. Pause;
21. Resume;
22. Stop;
23. live status нод;
24. Save / Load Team;
25. раздельные TeamDefinition и TeamLayout.

Главный критерий MVP:

> Это уже должна быть настоящая работающая команда DSH-агентов, а не просто визуальная схема и не набор одноразовых субагентов.
