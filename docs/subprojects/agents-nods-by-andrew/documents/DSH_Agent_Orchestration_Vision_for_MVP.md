# DSH Agent Orchestration — зафиксированное видение для проектирования MVP

> Этот документ фиксирует уже принятые продуктовые решения.
> При проектировании MVP их не нужно заново переосмысливать без явной причины.
> MVP может реализовывать только часть возможностей, но не должен противоречить этим принципам.

## 1. Что это за система

Нужен плагин для DSH, который позволяет визуально собирать и запускать команды ИИ-агентов.

Это не только «несколько субагентов» и не только граф задач.

В конечном виде система должна поддерживать:

- иерархические команды агентов;
- общение между агентами;
- задачи и зависимости;
- пользовательские подтверждения;
- разные права и ограничения;
- сохранение и восстановление запусков;
- изменение схемы на паузе;
- служебные узлы и более сложные схемы работы.

## 2. DSH остаётся владельцем самих агентов

Каждый AgentNode должен соответствовать настоящему агенту DSH и настоящему DSH Session.

Плагин не должен создавать второй параллельный движок агентов.

DSH отвечает за:

- агента;
- сеанс;
- модель;
- вызовы модели;
- инструменты;
- остановку;
- продолжение сеанса.

Плагин добавляет:

- команду;
- иерархию;
- связи;
- задачи;
- ответственность;
- сообщения;
- решения;
- ожидания;
- общее состояние запуска;
- визуальное управление.

## 3. Схему задаёт пользователь

Пользователь создаёт и меняет состав команды.

В базовой модели агенты сами не меняют структуру команды.

В будущем можно разрешить агентам предлагать изменения или создавать временных агентов, но это отдельное расширение.

## 4. Иерархия

У каждого агента не более одного непосредственного начальника.

Несколько начальников у одного агента не предполагается.

Понятие «подчиняется» имеет единые правила для всей системы. Не нужно на каждой линии отдельно задавать собственный набор полномочий начальника.

## 5. Подчинение и общение — разные вещи

Нужно различать:

- иерархию (Authority);
- разрешённое общение (Communication);
- зависимости задач (Task Dependencies).

Равные агенты могут общаться, если это разрешено.

Но равный агент не должен формально назначать задачу другому равному агенту вместо его начальника.

## 6. Пользователь — абсолютный оператор

Пользователь может открыть любого агента и перейти в его обычный чат DSH.

Внутренние ограничения общения агентов не ограничивают пользователя.

Пользователь может вмешаться в работу любого агента.

## 7. Настройки агента

Конфигурация должна быть максимально полной, но разумной.

Нужно учитывать как минимум:

- имя и роль;
- системный промт;
- модель;
- поставщика модели;
- уровень усилий рассуждения;
- ограничение ответа;
- бюджет контекста;
- инструменты;
- Skills;
- MCP;
- лимиты и права;
- приоритет;
- время ожидания;
- повторные попытки;
- возможные бюджеты и ограничения расходов.

Если DSH или поставщик модели реально позволяет управлять полезной настройкой, система по возможности должна её поддерживать.

## 8. Универсальные права

Права должны применяться программой, а не только текстом системного промта.

Нужны белые и чёрные списки.

В будущем единая система прав должна уметь ограничивать не только Tools / Skills / MCP, но и:

- файлы;
- репозитории;
- сеть;
- внешние сервисы;
- секреты;
- общение;
- работу с задачами;
- делегирование;
- материалы;
- память;
- опасные действия;
- расходы.

Запрет имеет приоритет над разрешением.

## 9. Task не обязателен для каждого действия

Не вся работа должна превращаться в формальную задачу.

Старший агент сам решает:

- достаточно обычного сообщения или просьбы;
- либо нужна формальная Задача (Task).

## 10. Старшие агенты декомпозируют работу

Руководитель может разбивать цель на части.

Подчинённый руководитель может дальше разбивать свою часть работы по собственной ветке.

## 11. Поручение и передача ответственности различаются

Нужно различать:

- «сделай эту работу и верни мне результат»;
- «возьми эту область под своё управление и сам организуй работу ниже».

Это разные операции.

## 12. Следующую работу выбирает начальник

Если подчинённый закончил задачу:

1. результат получает начальник;
2. начальник оценивает его;
3. начальник решает, что делать дальше;
4. при необходимости назначает следующую работу.

Оркестратор не должен автоматически выбирать подчинённому следующую готовую задачу.

Он может только хранить зависимости, отмечать готовность и будить начальника.

## 13. Формальные зависимости задач нужны

Система должна знать, какая задача зависит от какой.

Если зависимость не завершена, система должна считать последующую работу заблокированной.

Но «задача стала готова» не означает «автоматически назначить её агенту».

## 14. Полноценная Задача (Task)

Формальная задача должна иметь возможность хранить:

- цель;
- область работы;
- критерии готовности;
- необходимые результаты;
- обязательные доказательства;
- зависимости;
- ответственного;
- правила завершения.

## 15. Задача и Попытка (TaskAttempt) различаются

Одна логическая задача может иметь несколько попыток.

Это нужно для:

- ошибок;
- повторов;
- отмены;
- переназначения;
- восстановления;
- защиты от запоздавших результатов старой попытки.

## 16. Важные решения могут требовать пользователя

Нужна общая политика подтверждений (Approval Policy).

Например:

- важная архитектура → пользователь;
- опасное действие → пользователь;
- превышение бюджета → пользователь;
- обычная рабочая деталь → агент.

Существенные архитектурные решения должны иметь возможность обязательного подтверждения пользователем.

## 17. Ожидание и пробуждение

Агент может системно ждать нужное событие.

Когда оно приходит, система автоматически пробуждает агента.

Нужны также составные ожидания (AwaitSet):

- ждать все результаты;
- ждать любой;
- ждать N из M.

## 18. Пауза, изменение, продолжение

Обязательный сценарий:

RUNNING → PAUSE → PAUSED → EDIT → VALIDATE → RESUME → RUNNING

На паузе пользователь может менять:

- агентов;
- связи;
- модели;
- промты;
- права;
- настройки;
- схему работы.

Система должна безопасно обработать уже существующие задачи, попытки, ожидания и удалённых агентов.

## 19. Запуск должен восстанавливаться

Team Run должен переживать закрытие и повторный запуск DSH.

Нужно по возможности восстанавливать:

- агентов и их Session;
- задачи;
- попытки;
- сообщения;
- решения;
- ожидания;
- материалы;
- схему;
- историю.

## 20. Несколько уровней сохранения

Полезно различать:

- Team Template — шаблон команды;
- Team Definition — конкретная настроенная схема;
- Workflow / Scenario — схема вместе с логикой работы;
- Team Run — конкретный живой запуск;
- Team Layout — расположение элементов на холсте.

## 21. Визуальный интерфейс

Нужен большой отдельный графический интерфейс в духе ComfyUI.

Нужны разные режимы просмотра:

- иерархия;
- общение;
- задачи;
- зависимости задач;
- живое состояние;
- ожидания;
- подтверждения;
- материалы.

Не нужно показывать всё одновременно.

## 22. Служебные узлы

В будущем граф не должен ограничиваться только агентами.

Возможны:

- Router;
- Queue;
- Condition;
- Approval / Gate;
- Memory / Knowledge;
- Resource;
- Tool / MCP / Skill;
- другие служебные узлы.

## 23. Состояние команды не должно жить только в памяти моделей

Модель рассуждает, но программа хранит факты.

Устойчиво должны храниться:

- задачи;
- попытки;
- сообщения;
- решения;
- ожидания;
- материалы;
- версия схемы;
- состояние запуска.

Контекст агента считается рабочей памятью, а не единственным хранилищем истины.

## 24. Главное правило проектирования MVP

MVP можно сильно сократить по функциям.

Но нельзя строить временную архитектуру, которая по смыслу противоречит этим принципам и потом потребует полностью менять модель системы.

То есть MVP должен быть маленьким вертикальным срезом конечной системы, а не отдельным одноразовым прототипом с другой семантикой.
