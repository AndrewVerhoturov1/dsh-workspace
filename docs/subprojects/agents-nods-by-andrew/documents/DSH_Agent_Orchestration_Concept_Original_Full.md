# DSH Agent Orchestration — концепция системы и идеи из Orca

> Статус документа: **рабочая концепция**.  
> Цель: зафиксировать идеи до перехода к проектированию архитектуры и реализации.  
> На этом этапе документ описывает **что мы хотим получить** и **какие решения стоит позаимствовать у Orca**, но не фиксирует окончательный технический дизайн.

---

# 1. Какую систему мы хотим построить

## 1.1. Общая идея

Нужен плагин для DeepSeek Harness, который превращает DSH в среду для построения и запуска **команд ИИ-агентов**.

Пользователь должен иметь возможность визуально собрать команду из нескольких агентов, задать каждому роль, модель, уровень усилий, ограничения, системный промт, доступные инструменты и правила общения, после чего запустить всю эту структуру как единую работающую систему.

Ключевой принцип:

**это не просто несколько субагентов и не просто граф задач.**

Нужна полноценная система, в которой существуют:

- агенты;
- иерархия подчинения;
- разрешённые каналы общения;
- задачи;
- попытки выполнения задач;
- сообщения между агентами;
- точки принятия решений;
- состояние всей команды;
- сохранённые схемы;
- история запусков;
- возможность поставить команду на паузу, изменить схему и продолжить работу.

При этом всё должно работать **внутри одного DSH**.

---

## 1.2. Почему единый DSH — важная часть идеи

В Orca оркестратор управляет разными внешними программами: Claude Code, Codex, OpenCode и другими CLI-агентами.

У каждого такого агента:

- собственный процесс;
- собственная сессия;
- собственные настройки;
- собственная система разрешений;
- собственный способ показывать состояние;
- собственный способ продолжать разговор;
- собственный способ завершать работу.

Из-за этого Orca вынуждена строить большой слой совместимости.

В нашем случае этого делать не нужно.

Все агенты должны быть **нативными агентами DSH**.

То есть базовая схема должна быть такой:

```text
                 DSH
                  │
        ┌─────────┼─────────┐
        │         │         │
      Agent     Agent     Agent
        │         │         │
     Session   Session   Session
        │         │         │
      Inbox     Inbox     Inbox
```

DSH уже знает состояние своих агентов, управляет их сессиями, очередями сообщений, модельными запросами, инструментами и остановкой.

Поэтому наш плагин не должен заново изобретать собственный «мини-DSH».

Он должен хранить только то, чего DSH сам по себе не знает:

- структуру команды;
- отношения подчинения;
- разрешения на общение;
- задачи;
- владение задачами;
- попытки выполнения;
- решения;
- правила планирования;
- состояние общего запуска.

---

# 2. Основная сущность — агент

Каждая визуальная нода на схеме представляет отдельного настоящего DSH Agent.

У агента должна быть собственная постоянная сессия.

Агент не должен пересоздаваться с нуля на каждую маленькую задачу.

Пример:

```text
Developer
   │
   ├─ задача 1
   ├─ задача 2
   ├─ вопрос от Tester
   └─ задача 3
```

Это всё тот же Developer с той же сессией и своей историей.

---

## 2.1. Настройки каждого агента

Для каждого агента пользователь должен иметь возможность задавать как минимум:

### Основное

- имя;
- описание;
- роль;
- системный промт;
- положение в иерархии.

### Модель

- поставщик модели;
- модель;
- уровень усилий рассуждения;
- максимальный размер ответа;
- ограничение на используемый объём контекста.

### Инструменты

- белый список;
- чёрный список;
- набор инструментов DSH;
- отдельные ограничения на опасные операции.

### Skills

- разрешённые Skills;
- запрещённые Skills.

### MCP

- разрешённые MCP-серверы;
- разрешённые инструменты внутри MCP;
- запрещённые MCP-инструменты.

### Общение

- родитель;
- дочерние агенты;
- равные агенты, которым можно писать;
- агенты, от которых можно принимать сообщения;
- возможность писать пользователю напрямую.

## 2.2. `AgentDefinition → AgentNode → AgentRuntime`

После изучения `limuyang2/agent-team` полезно жёстко разделить переиспользуемую конфигурацию агента, его место в конкретной схеме и живое исполнение.

```text
AgentDefinition
      ↓ snapshot + node overrides
AgentNode
      ↓ bind
AgentRuntime / DSH Session
```

`AgentDefinition` — переиспользуемый шаблон роли. `AgentNode` — зафиксированный экземпляр этой конфигурации внутри конкретной ревизии `TeamDefinition`. `AgentRuntime` — уже живое состояние: `sessionId`, runtime status, текущая работа и фактически применённая конфигурация.

Изменение общей `AgentDefinition` **не должно незаметно менять уже работающие AgentNode**. Для существующей команды изменение применяется явно через новую ревизию/`GraphPatch`.

Для модели и reasoning полезно также различать три уровня факта:

```text
requested  — что попросила схема
resolved   — что реально выбрал DSH после defaults/fallback/policy
actual     — что подтверждено runtime/session/provider telemetry
```

Если `actual` не записан, интерфейс должен показывать «неизвестно», а не подставлять предполагаемое значение по умолчанию.

# 3. Белые и чёрные списки возможностей

Права агента должны применяться **кодом DSH/плагина**, а не только системным промтом.

Плохо:

```text
Ты Tester.
Пожалуйста, не изменяй файлы.
```

Хорошо:

```text
Tester

files.read     ✓
files.search   ✓
tests.run      ✓

files.write    ✕
github.write   ✕
postman        ✕
```

Если возможность запрещена, модель не должна:

1. видеть её как доступный инструмент;
2. иметь возможность вызвать её обходным способом.

Чёрный список должен иметь приоритет над белым.

Условная логика:

```text
реальные возможности агента
=
доступные возможности DSH
∩ разрешённые
− запрещённые
```

## 3.1. Возможности Agent и права конкретной делегации — разные вещи

Из All in Luna стоит перенять не идею «дочерний агент всегда слабее родителя», а более точный принцип: **конкретная делегация может только сужать полномочия, выданные для текущей работы**.

Например Developer в принципе умеет `files.write`, `shell` и `github.write`, но для `TASK-51` получает только:

```text
DelegationGrant
├─ read  src/auth/**
├─ write src/auth/**
├─ tests.run
├─ github.write  ✕
└─ postman       ✕
```

Тогда эффективные возможности попытки определяются примерно так:

```text
effective capabilities
= DSH capabilities
∩ Agent policy
∩ Team policy
∩ DelegationGrant
− deny
```

Если исполнитель делегирует часть этой задачи ниже, новый grant не может расширить полученный им scope. Это **ограничение конкретной цепочки работы**, а не требование делать постоянные возможности дочернего AgentNode подмножеством возможностей родителя.

В MVP `DelegationGrant` не обязательно делать отдельной большой сущностью: он может быть частью `TaskAttempt`/назначения, если сохраняются его точная версия и история.

# 4. Три разных графа

Одна из важнейших идей системы: нельзя смешивать все связи в один тип стрелки.

Нам нужны как минимум три независимых графа.

---

## 4.1. Граф подчинения

Показывает, кто кем управляет.

```text
Director
   │
   ▼
Engineering Lead
   │
   ▼
Backend Lead
   │
   ▼
Developer
```

Это отношение власти и ответственности.

Родитель может:

- ставить задачи;
- получать результаты;
- отменять работу;
- менять приоритет;
- запрашивать состояние;
- делегировать работу дальше по дереву.

---

## 4.2. Граф общения

Показывает, кто с кем имеет право разговаривать.

Например:

```text
Developer <────> Researcher
Tester ────────> Developer
```

Это не означает подчинение.

Developer и Researcher могут быть равными агентами.

Граф общения должен существовать отдельно от иерархии.

---

## 4.3. Граф зависимостей задач

Это уже не структура агентов, а структура работы.

```text
Исследование
     │
     ▼
Проектирование
     │
     ▼
Реализация
   /       \
  ▼         ▼
Тесты    Проверка
```

То есть:

- граф агентов отвечает на вопрос **«кто кем управляет?»**;
- граф общения отвечает **«кто с кем может разговаривать?»**;
- граф задач отвечает **«что от чего зависит?»**.

Эти три понятия нельзя смешивать.

## 4.4. Валидатор TeamDefinition

Графический редактор не должен быть просто рисовалкой. Перед сохранением значимых изменений, применением изменений к живой команде и особенно перед запуском отдельный слой должен проверять схему.

Примеры блокирующих ошибок:

```text
ERROR: цикл в иерархии подчинения
ERROR: два стартовых агента
ERROR: связь указывает на несуществующий AgentNode
ERROR: выбранная модель / MCP / Skill недоступны
```

Примеры предупреждений:

```text
WARNING: Reviewer не имеет канала связи с Developer
WARNING: contextBudget выше допустимого окна выбранной модели
```

Проверка должна быть самостоятельной подсистемой:

```text
TeamDefinition
      │
      ▼
TeamValidator
   ├─ errors
   └─ warnings
```

Запуск разрешается только при отсутствии блокирующих ошибок.

---

# 5. Стартовый агент и пользователь

В каждой схеме должен быть один специальный агент, через которого команда по умолчанию общается с пользователем.

Пример:

```text
USER
 │
 ▼
Team Lead
 ├─ Architect
 ├─ Researcher
 └─ Developer
```

Пользователь пишет Team Lead.

Team Lead организует работу команды.

Остальные агенты не должны автоматически начинать писать в основной пользовательский чат.

При необходимости отдельному агенту можно явно разрешить прямое общение с пользователем.

---

# 6. Общение агентов

Агенты не должны напрямую получать произвольный доступ друг к другу.

Все сообщения должны проходить через общий слой маршрутизации.

```text
Agent A
   │
   ▼
Message Bus
   │
   ├─ проверка разрешения
   ├─ проверка адресата
   ├─ запись сообщения
   └─ доставка
   │
   ▼
Agent B
```

Оркестратор должен знать:

- кто отправитель;
- кто получатель;
- разрешено ли им общаться;
- к какой задаче относится сообщение;
- какой у сообщения тип;
- было ли оно доставлено;
- было ли оно обработано.

---

## 6.1. Типы сообщений

Не вся связь должна быть обычным текстовым сообщением.

Нужны типизированные сообщения, например:

```text
TASK
QUESTION
ANSWER
REPORT
STATUS
ESCALATION
DECISION_REQUIRED
```

В интерфейсе названия могут быть полностью русскими.

Типизация нужна для того, чтобы оркестратор мог реагировать на события программно, не спрашивая модель, что означал её текст.

## 6.2. Жизненный цикл сообщения

После изучения NanmiCoder AgentTeams полезно фиксировать не только само сообщение, но и его жизненный цикл.

Минимально:

```text
QUEUED
  ↓
DELIVERED
  ↓
CONSUMED
```

Дополнительно:

```text
DISCARDED
ANSWERED
```

где это применимо.

Важно различать:

- сообщение надёжно принято системой;
- сообщение попало во входящую очередь агента;
- агент действительно потребил его в своём ходе;
- вопрос получил ответ.

Сообщение также может быть привязано к конкретным `Task` и `TaskAttempt`, чтобы устаревшая подсказка от старой попытки не попала в новую.

---

# 7. Задача и попытка выполнения — разные сущности

Это одна из самых важных идей, которую стоит перенять у Orca.

Есть логическая задача:

```text
TASK-17
Проверить безопасность API
```

Но задача может выполняться несколько раз.

```text
TASK-17
 ├─ ATTEMPT-1 → Tester A → ошибка
 ├─ ATTEMPT-2 → Tester B → отменён
 └─ ATTEMPT-3 → Tester C → успешно
```

Задача остаётся одной и той же.

Попытки меняются.

Это нужно для:

- повторных запусков;
- ошибок;
- остановок;
- переназначения другому агенту;
- восстановления после сбоя;
- защиты от запоздавших результатов.

Если старая попытка завершилась после того, как уже началась новая, её результат не должен случайно завершить задачу.

---

# 8. Владение задачей и передача ответственности

Нужно различать два действия.

## 8.1. Поручить выполнение

Родитель остаётся ответственным.

```text
Lead
 │
 └─ поручил Developer
```

Developer выполняет работу и возвращает результат Lead.

---

## 8.2. Передать ответственность

Ответственность переходит ниже по иерархии.

```text
Director
   │
   ▼
Engineering Lead
```

Director говорит:

> Возьми на себя подсистему авторизации.

Теперь Engineering Lead сам может:

- разбить цель на задачи;
- назначить исполнителей;
- общаться со своими детьми;
- собрать итог.

Это важно, если мы хотим настоящую многоуровневую иерархию, а не одного главного агента с большим числом прямых подчинённых.

## 8.3. Handoff, поручение, ownership и изменение цели не должны смешиваться

LoopX и All in Luna хорошо показывают опасную границу: передача информации сама по себе ничего не передаёт.

```text
REPORT / context handoff
≠ DELEGATE
≠ TRANSFER_OWNERSHIP
≠ CHANGE_GOAL
```

Если Developer передал Lead результат и артефакты, это не меняет владельца задачи. Если Lead переслал этот пакет другому Agent, это не означает передачу ответственности. Если Agent предложил расширить цель, это не меняет `TaskContract` или цель команды без отдельной разрешённой операции.

Для многоуровневой иерархии полезен и второй принцип: **локальная сложность остаётся локальной**. Родительскому уровню не нужно автоматически получать все tool logs и внутренние сообщения поддерева; наверх поднимается структурированный handoff — результат, blockers, evidence и вопросы, требующие решения выше.

# 9. Точки принятия решений

Не каждый вопрос должен быть обычным сообщением.

Если дальнейшая работа реально зависит от ответа, нужен отдельный объект решения.

Пример:

```text
DECISION-12

Вопрос:
Какой вариант API выбрать?

Варианты:
A — сохранить старый формат
B — перейти на новый формат

Решает:
Architect

Блокирует:
TASK-18
```

Пока решение не принято:

```text
TASK-18 = BLOCKED
```

Решение может принимать:

- родительский агент;
- конкретно назначенный агент;
- пользователь.

В визуальном интерфейсе это может быть отдельная карточка или специальная нода.

# 10. Состояние агента

Полезно разделить два типа состояния.

## 10.1. Реальное состояние DSH Agent

То, что происходит с агентом как с исполняемым объектом:

```text
RUNNING
IDLE
INACTIVE
FAILED
```

Это должно по возможности браться напрямую из DSH.

---

## 10.2. Рабочее состояние

То, что агент делает относительно команды:

```text
UNASSIGNED
QUEUED
WORKING
WAITING_MESSAGE
WAITING_DECISION
BLOCKED_DEPENDENCY
DONE
```

Пример:

```text
Tester

Состояние DSH:
IDLE

Рабочее состояние:
WAITING_DEPENDENCY

Причина:
TASK-31 ждёт TASK-29
```

Так интерфейс будет намного понятнее, чем один общий индикатор «зелёный/серый».

## 10.3. `IDLE` не означает «агент свободен»

Это важный вывод из NanmiCoder AgentTeams.

DSH Agent может находиться в состоянии `idle`, но при этом всё ещё владеть незавершённой задачей и действующей попыткой.

Например:

```text
DSH state:
IDLE

Work state:
WAITING_MESSAGE

Task:
TASK-42

Attempt:
ATTEMPT-7
```

Такому агенту нельзя автоматически выдавать новую задачу только потому, что его модельный ход закончился.

Поэтому планировщик должен проверять **оба слоя состояния**:

```text
можно выдать новую работу
=
DSH Agent доступен
+
у агента нет действующей незавершённой попытки
+
нет более приоритетного входящего сообщения
```

# 11. Контекст агента

У каждого агента должна быть своя отдельная сессия и свой контекст.

Пользователь должен иметь возможность задавать бюджет контекста.

Например:

```text
Architect   120k
Developer    80k
Researcher   50k
Tester       30k
```

Это не означает изменение физического максимума модели.

Это ограничение, установленное нашей системой.

Позже можно добавить правила:

```text
budgetTokens
reserveOutputTokens
compactAt
```

При приближении к пределу агент может получать сокращённое представление старой истории.

При этом нужно всегда различать:

```text
контекст конкретного агента
≠
состояние всей команды
```

Структура команды, задачи и владение не должны существовать только внутри модельного контекста.

## 11.1. Контекст — рабочий кэш, а не память системы

После отдельного разбора памяти этот принцип нужно сделать жёстче:

> **Контекст агента считается ненадёжным рабочим буфером. Никакой критически важный факт не должен существовать только внутри prompt/history конкретного агента.**

Модель может:

- забыть старую деталь;
- пройти compaction;
- получить урезанный контекст;
- быть перезапущена;
- сменить Session;
- потерять часть недавнего reasoning при аварии.

Поэтому настоящая память складывается из устойчивых объектов:

```text
TeamRun state
Tasks / TaskAttempts
Messages
Decisions
Artifacts
Event Journal
DSH Session log
```

А перед конкретным ходом строится небольшой `TaskContextPacket`, содержащий только необходимое для текущей работы.

## 11.2. Не тащить всю память в prompt

Наличие информации в памяти команды не означает, что её надо автоматически отправить модели.

Правильнее:

```text
Memory / Artifact Store
        ↓
   relevance/filter
        ↓
 small context manifest
        ↓
      Model
```

Например вместо полного содержимого трёх больших документов модель может получить:

```text
Relevant artifacts:
ART-12  Architecture decision      18 KB
ART-31  Failed test report          6 KB
ART-44  API research               42 KB
```

и прочитать только те артефакты, которые действительно нужны.

# 12. Схема команды и запуск — разные сущности

Нужно различать шаблон команды и конкретный её запуск.

## Team Definition

Например:

```text
Software Team v4
```

Содержит:

- ноды агентов;
- связи;
- модели;
- промты;
- разрешения;
- правила общения;
- настройки.

## Team Run

Конкретный запуск схемы:

```text
Run #184
```

Содержит:

- снимок версии схемы;
- DSH Session ID каждого агента;
- задачи;
- попытки;
- сообщения;
- решения;
- историю событий;
- ошибки;
- использование ресурсов.

Это позволит одной схемой пользоваться много раз.

## 12.1. Стадии схемы до запуска

После изучения NanmiCoder AgentTeams стоит явно разделить проектирование схемы и её исполнение.

Рекомендуемый жизненный цикл определения команды:

```text
DRAFT
  ↓
VALIDATED
  ↓
APPROVED
  ↓
RUNNING
```

То есть редактирование нод, связей, моделей и разрешений само по себе **не должно запускать агентов**.

Перед запуском система должна проверить как минимум:

- существование выбранных моделей;
- корректность иерархии;
- отсутствие запрещённых циклов;
- наличие стартового агента;
- корректность каналов общения;
- существование Tools / Skills / MCP, указанных в политике;
- отсутствие конфликтующих или невозможных ограничений;
- возможность создать необходимые DSH Sessions.

Только после успешной проверки и явного запуска создаётся `TeamRun`.

Это важный принцип из NanmiCoder AgentTeams: сначала строится и проверяется план, и только потом создаются живые участники и начинается выполнение.

# 13. Версии схемы

Схемы должны иметь версии.

```text
Software Team v12
```

Запущенная команда работает на конкретной версии.

Если пользователь ставит её на паузу и меняет схему:

```text
v12
 ↓ pause
редактирование
 ↓
v13
 ↓ resume
```

Нужно сохранять информацию, какая версия действовала в какой момент.

## 13.1. Ревизии и защита от конфликтов

У `TeamDefinition` должна быть числовая ревизия. Любое смысловое изменение применяется относительно конкретной версии:

```text
revision = 17
expectedRevision = 17
```

Если к моменту сохранения документ уже стал `revision = 18`, изменение не должно молча перетирать более новую схему. Это особенно важно, если изменения могут одновременно исходить от пользователя, импортируемого шаблона или управляющего агента.

## 13.2. GraphPatch

Изменения структуры лучше представлять не произвольной перезаписью JSON, а структурированным объектом:

```text
GraphPatch
├─ author
├─ baseRevision
├─ reason
└─ operations[]
```

Например:

```text
+ add AgentNode Security Reviewer
+ add authority Engineering Lead → Security Reviewer
+ add communication Developer ↔ Security Reviewer
```

Для первой версии безопасная цепочка:

```text
Agent proposes GraphPatch
        ↓
Validator
        ↓
Preview
        ↓
User approves
        ↓
Apply
```

Агент не должен незаметно переписывать живую организационную структуру.

## 13.3. Опубликованная ревизия должна быть неизменяемой

Из `agent-dag-workflow` и `dsh_workflow` стоит перенять более строгую границу между редактируемым Draft и тем, что уже использовалось в Run.

```text
DRAFT revision N
      ↓ validate / approve
PUBLISHED revision N   ← immutable
      ↓
TeamRun references exact revision
```

После запуска нельзя «исправить» опубликованную ревизию задним числом. Любое смысловое изменение создаёт следующую ревизию. `TeamRun` должен хранить точную ссылку на использованную ревизию и, желательно, semantic/content hash.

Это даёт однозначный ответ на вопрос: **какая именно схема реально исполнялась?** Повторное открытие, восстановление и аудит старого Run не должны зависеть от текущего состояния редактируемого шаблона. `TeamLayout` при этом остаётся вне semantic hash.

# 14. Пауза, продолжение и остановка

Нужен общий жизненный цикл команды.

Минимально:

```text
STOPPED
RUNNING
PAUSING
PAUSED
STOPPING
FAILED
```

## Мягкая пауза

Предпочтительный режим:

1. перестать выдавать новую работу;
2. не запускать новые ходы;
3. дать текущим операциям завершиться;
4. дождаться безопасного состояния;
5. перейти в PAUSED.

Важно формализовать это как **закрытие publication gate**. Задача может уже быть `READY` или ждать свободного слота concurrency/semaphore, но если она ещё не передана в DSH на исполнение, после запроса Pause она стартовать не должна.

После этого пользователь может менять схему.

## Немедленная остановка

Использовать нативную отмену DSH для активных агентов.

По возможности не уничтожать ещё не обработанные сообщения и устойчивые сессии.

# 15. Изменение схемы во время паузы

Во время PAUSED пользователь должен иметь возможность:

- добавить агента;
- удалить агента;
- поменять родителя;
- изменить разрешённые связи;
- поменять модель;
- поменять уровень усилий;
- изменить ограничения инструментов;
- добавить или убрать Skill;
- добавить или убрать MCP;
- изменить системный промт;
- изменить бюджет контекста.

После применения создаётся новая версия схемы.

Для некоторых изменений, например радикальной смены системного промта, интерфейс должен позволять выбрать:

```text
сохранить старую сессию
или
начать новую сессию этого агента
```

# 17. Отдельное большое окно

Такой интерфейс слишком большой для обычной боковой панели.

В DSH нужна кнопка:

```text
Agent Team
```

которая открывает отдельное большое окно или рабочую поверхность.

В основном интерфейсе DSH можно оставить компактный индикатор:

```text
Team: RUNNING
8 agents

```

По нажатию открывается полноценный редактор и наблюдение за командой.

## 17.1. TeamLayout отдельно от TeamDefinition

После изучения `dsh-Visual-Workflow` стоит явно разделить смысловую схему и её раскладку на холсте.

`TeamDefinition` содержит поведение:

```text
agents
authorityEdges
communicationEdges
policies
models
prompts
permissions
```

`TeamLayout` содержит только представление:

```text
positions
group boxes
collapsed state
viewport
zoom
visual ordering
```

Перемещение карточки на холсте не должно создавать новую смысловую версию команды.

```text
NODE_MOVED = визуальное изменение
AUTHORITY_EDGE_ADDED = смысловое изменение
AGENT_MODEL_CHANGED = смысловое изменение
```

Такой подход упрощает версии, сравнение схем, историю и живое редактирование.

# 18. Что DSH уже умеет и не нужно дублировать

Нужно максимально использовать нативные возможности DSH.

DSH уже предоставляет:

- Agent;
- Session;
- Inbox;
- состояние running/idle;
- события жизненного цикла;
- отмену;
- ожидание idle;
- продолжение сохранённых агентов;
- передачу сообщений;
- настройки provider/model/reasoning/maxTokens;
- ограничение инструментов;
- системные промты;
- продолжаемых субагентов.

Поэтому наш плагин не должен создавать второй параллельный механизм исполнения агента.

Основной принцип:

> Если DSH уже является источником истины о состоянии агента, наш плагин читает это состояние, а не дублирует его.

# 19. Разбор Orca: почему она сложнее нашей системы

Orca должна управлять разными внешними CLI-агентами.

Например:

```text
Orca
 ├─ Claude Code
 ├─ Codex
 ├─ OpenCode
 └─ другие
```

Каждый из них — отдельная программа со своими:

- настройками;
- процессом;
- терминалом;
- разрешениями;
- сессиями;
- командами;
- особенностями восстановления;
- способом сообщать состояние.

Поэтому Orca вынуждена иметь слой совместимости:

```text
Orca
 ↓
терминал
 ↓
CLI конкретного производителя
 ↓
адаптеры / hooks / служебные команды
 ↓
модель
```

В нашей системе:

```text
Оркестратор
 ↓
DSH Agent
```

Поэтому многие части Orca нам можно сильно упростить.

---

# 20. Что у Orca нам НЕ нужно копировать

## 20.1. Определение состояния через терминал

Orca должна различать:

```text
терминал жив
≠
агент внутри жив
```

У нас DSH знает состояние своего Agent напрямую.

Поэтому не нужно строить сложную систему догадок по терминалам.

---

## 20.2. Ручные сигналы «я жив»

Orca заставляет внешних исполнителей периодически отправлять специальный сигнал.

Это нужно, потому что Orca находится снаружи.

У нас лучше использовать реальные события DSH.

Например:

```text
последнее событие: tool/start
инструмент: tests
время: 14:31:06
```

Если событий давно нет, можно показать:

```text
возможно завис
```

Но не объявлять автоматически, что агент умер.

---

## 20.3. Служебные shell-команды для общения

Orca приходится обучать внешние CLI:

```text
orca orchestration send ...
orca orchestration ask ...
orca orchestration check ...
```

У нас это не нужно.

Сообщение должно передаваться напрямую:

```text
Agent A
 ↓
Message Bus
 ↓
Agent B.inbox
```

---

## 20.4. Разные способы продолжения разных CLI

Orca должна знать, как продолжить Claude Code, Codex, OpenCode и другие программы.

У нас главный устойчивый идентификатор — DSH Session ID.

```text
AgentNode
 ↕
DSH Session
```

Это значительно проще.

---

## 20.5. Разные системы разрешений внешних CLI

У каждого внешнего инструмента собственные правила.

У нас права нужно реализовывать через единый слой DSH.

---

## 20.6. Большую часть управления процессами и терминалами

Нам не нужно превращать оркестратор в диспетчер процессов операционной системы.

Жизненный цикл агента должен максимально оставаться ответственностью DSH.

---

# 21. Что у Orca обязательно стоит перенять

Несмотря на то что её технический слой нам не нужен, сама дисциплина оркестрации у Orca очень сильная.

---

## 21.1. Разделение Task и Attempt

Это нужно перенять почти напрямую.

```text
Task
 ├─ Attempt 1
 ├─ Attempt 2
 └─ Attempt 3
```

Задача описывает работу.

Попытка описывает конкретное исполнение этой работы конкретным агентом.

---

## 21.2. Строгая принадлежность результата

Результат должен быть связан с:

```text
taskId
attemptId
agentId
```

Оркестратор проверяет:

```text
Task существует?
Attempt существует?
Attempt ещё действующий?
Этот Agent владеет Attempt?
```

Только после этого результат может изменить состояние задачи.

---

## 21.3. Состояние работы хранится вне памяти модели

Lead не должен «помнить», кто чем занимается.

Это должна знать система.

```text
TASK-15
owner = Developer
attempt = ATTEMPT-3
status = IN_PROGRESS
```

Модель думает.

Система хранит факты.

---

## 21.4. Устойчивая система сообщений

Нужно хранить не только текст, но и жизненный цикл сообщения.

Минимально:

```text
QUEUED
DELIVERED
CONSUMED
```

Для вопросов можно добавить:

```text
ANSWERED
```

Это позволит корректно восстанавливаться после перезапуска и видеть, действительно ли агент обработал сообщение.

---

## 21.5. Типизированные сообщения

Полезно перенять идею Orca, что завершение задачи, вопрос и обычная информация — это разные события.

Например:

```text
TASK_ASSIGNED
QUESTION
ANSWER
TASK_COMPLETED
TASK_FAILED
ESCALATION
DECISION_REQUIRED
```

---

## 21.6. Точки принятия решений

Очень сильная идея Orca.

Решение должно быть отдельным объектом, который может блокировать задачу и иметь конкретного владельца.

Это намного лучше обычного сообщения:

> Что будем делать?

---

## 21.7. Разделение поручения и передачи ответственности

В многоуровневой системе это необходимо.

Поручение:

```text
сделай и верни результат мне
```

Передача ответственности:

```text
возьми эту область под своё управление и сам организуй работу ниже
```

Без этого иерархия агентов будет декоративной.

---

## 21.8. Не считать молчание доказательством смерти

У Orca очень хороший принцип:

> отсутствие сигнала не доказывает, что исполнитель умер.

У нас источник наблюдения точнее, но принцип всё равно нужен.

Если DSH Agent долго не создаёт событий:

```text
UNKNOWN / POSSIBLY_STUCK
```

не равно:

```text
FAILED
```

Для FAILED должно быть положительное подтверждение ошибки или завершения.

---

## 21.9. Явная судьба агента после работы

Завершение задачи не означает уничтожение агента.

После работы агент может:

```text
получить новую задачу
остаться ожидающим
быть временно выгружен
быть завершён
```

Для долгоживущих команд это важно.

---

## 21.10. Отдельный общий запуск

У Orca есть общий Run.

У нас тоже нужен TeamRun.

Он объединяет:

- версию схемы;
- агентов;
- задачи;
- попытки;
- сообщения;
- решения;
- события;
- итог.

# 23. Важный принцип: технические идентификаторы лучше скрывать от модели

```text

CLI-команды
правила heartbeat
правила завершения
```

```text
Backend Lead

- отправить сообщение;

```


Это уменьшает количество технического мусора в контексте и делает систему надёжнее.

# 24. Предварительная модель ядра

После разбора задач, визуального слоя и памяти ядро системы уже шире первоначальных семи сущностей:

```text
TeamDefinition
TeamLayout
TeamRun

AgentDefinition
AgentNode
AgentRuntime

Task
TaskContract
TaskAttempt

Message
Decision
AwaitSet

Artifact
ArtifactVersion
ArtifactLink

GraphPatch
Event
```

`AwaitSet` — программная точка объединения нескольких результатов без пробуждения управляющей модели после каждого отдельного события.

`Artifact*` — долговременная предметная память команды.

`Event` — журнал фактов для аудита и восстановления, но не единственный способ читать текущее состояние.

DSH при этом остаётся владельцем:

```text
Agent
Session
Inbox
model execution
tool execution
cancellation
continuation
```

```text
                       │

┌──────────────────────────────────────────────┐
│                    DSH                       │
│                                              │
│  Agent                                       │
│  Session                                     │
│  Inbox                                       │
│  status                                      │
│  cancel / whenIdle                           │
│  provider / model / reasoning                │
│  tools                                       │
│  skills                                      │
│  MCP                                         │
│  system prompt                               │
│  LLM execution                               │
└──────────────────────────────────────────────┘
```

Главный принцип:

> **Не строить внутри DSH маленькую копию Orca. Взять у Orca строгую модель управления работой, но выбросить слой приспособления к внешним CLI-агентам.**

Orca хорошо показывает, **как организовывать работу**.

DSH уже решает, **как существует и выполняется сам агент**.

Именно на пересечении этих двух идей должна строиться наша система.

---


# 26. Разбор NanmiCoder AgentTeams

NanmiCoder AgentTeams — один из самых полезных практических референсов для нашей системы, потому что он уже решает значительную часть задач **нативно внутри DSH**.

Если Orca показывает хорошую дисциплину управления работой в мире внешних CLI-агентов, то NanmiCoder AgentTeams показывает, как похожие идеи можно реализовать на настоящих DSH Agents и продолжаемых DSH Sessions.

Его архитектура нам не подходит целиком, потому что она строится вокруг одного Captain и плоского списка участников. Но механика работы команды, задач, попыток, сообщений и планировщика очень близка к тому, что нам нужно.

---

# 27. Базовая модель NanmiCoder AgentTeams

Упрощённо система выглядит так:

```text
Пользователь
    │
    ▼
 Captain
    │
 ┌──┼──────────────┐
 ▼  ▼              ▼
A   B              C

+ общий список задач
+ зависимости задач
+ устойчивые почтовые ящики
+ планировщик
+ постоянные DSH Sessions участников
```

Текущая пользовательская сессия DSH становится Captain.

Участники создаются как **continutable DSH subagents** — то есть каждый имеет собственную устойчивую DSH Session и может получать несколько задач в разные моменты времени.

Это совпадает с нашей основной идеей:

```text
AgentNode
   ↕
DSH Session
```

Один AgentNode должен быть долгоживущим агентом, а не одноразовым вызовом модели.

---

# 28. План до запуска

Одна из сильнейших идей NanmiCoder AgentTeams — разделение планирования и исполнения.

Сначала строится черновик:

```text
состав команды
+
роли
+
задачи
+
зависимости
+
назначения
```

но реальные участники ещё не обязаны быть запущены.

Пользователь может:

- посмотреть план;
- вернуть его на изменение;
- утвердить;
- отказаться.

Только после явного `Approve & Run` начинается выполнение.

Для нашего визуального редактора это почти обязательная модель:

```text
DRAFT
  ↓
VALIDATE
  ↓
APPROVED
  ↓
CREATE / RESUME AGENTS
  ↓
RUNNING
```

Это защищает от ситуации, когда простое перемещение или соединение нод случайно запускает дорогую работу.

---

# 29. Перед запуском нужно проверять всю схему

NanmiCoder AgentTeams проверяет выбранные маршруты моделей до того, как окончательно создаст живую команду.

В нашей системе проверка должна быть шире.

Перед `Run` следует проверять:

```text
модели
иерархию
communication edges
Tools
Skills
MCP
system prompts
контекстные бюджеты
ограничения
стартового агента
валидность TeamDefinition
```

Главный принцип:

> Лучше отказать до запуска, чем создать частично работающую команду и обнаружить проблему после появления нескольких живых Sessions.

---

# 30. Событийный планировщик

NanmiCoder AgentTeams не заставляет участников постоянно опрашивать общий список задач.

Он использует реальные события DSH.

Основная идея:

```text
Agent стал доступен
        │
        ▼
Scheduler
        │
        ├─ есть более приоритетное сообщение?
        │       └─ доставить сообщение
        │
        └─ есть ready-задача?
                └─ назначить задачу
```

Планировщик также запускается при изменениях графа задач:

```text
task completed
task created
task reassigned
dependency unlocked
resume
```

Это правильный подход и для нашей системы.

Нам нужен **событийный планировщик**, а не циклический опрос.

---

# 31. Одна активная задача на агента по умолчанию

NanmiCoder AgentTeams не даёт одному member одновременно владеть несколькими незавершёнными задачами.

Для первой версии нашего плагина это очень разумное ограничение:

```text
concurrencyPerAgent = 1
```

При этом разные агенты могут работать параллельно.

Например:

```text
Developer A → TASK-10
Developer B → TASK-11
Tester      → TASK-12
```

но:

```text
Developer A
 ├ TASK-10
 └ TASK-13
```

одновременно — нет.

Это упрощает:

- контекст;
- владение;
- отмену;
- повтор;
- паузу;
- понимание состояния пользователем.

Если позже появится реальная потребность, параллелизм одного агента можно будет расширить отдельно.

---

# 32. `idle` и владение работой — разные вещи

NanmiCoder AgentTeams правильно учитывает, что DSH Agent может стать `idle`, но всё ещё владеть открытым `TaskAttempt`.

Например:

```text
Agent:
idle

Task:
in_progress

Attempt:
active
```

В такой ситуации агент не считается автоматически свободным для новой задачи.

Он может:

- ждать дополнительного сообщения;
- продолжить ту же попытку;
- получить уточнение;
- быть явно переназначен.

Это важное правило для нашего планировщика:

> новая задача выдаётся не просто «idle агенту», а агенту, у которого нет действующей открытой работы.

---

# 33. Устойчивая почта как часть планировщика

В NanmiCoder AgentTeams сообщения — не отдельный декоративный чат.

Они встроены в жизненный цикл исполнения.

Сообщение хранит:

```text
id
from
to
content
time

taskId?
attemptId?

deliveredAt?
readAt?
discardedAt?
```

Особенно полезны две идеи.

## 33.1. Доставка и потребление различаются

```text
QUEUED
  ↓
DELIVERED
  ↓
CONSUMED
```

Это позволяет точно понимать:

- сообщение сохранено;
- сообщение доставлено в DSH Agent;
- агент действительно включил его в свою работу.

## 33.2. Сообщение может принадлежать конкретной попытке

Например:

```text
TASK-17
ATTEMPT-3
```

Если Attempt 3 уже аннулирован, старое сообщение не должно автоматически влиять на Attempt 4.

Для нас это особенно важно при переназначении задач и редактировании живой команды.

---

# 34. Сообщения должны иметь приоритет над новой работой

Если агент освободился, но у него уже есть ожидающее сообщение, логично сначала обработать его.

Пример:

```text
Developer стал idle

Inbox:
"Исправь результат предыдущей задачи перед продолжением"
```

В этот момент нельзя сразу выдавать новую независимую задачу.

Базовый порядок для планировщика может быть таким:

```text
1. Проверить управляющие сообщения.
2. Проверить вопросы/ответы текущей работы.
3. Проверить действующий TaskAttempt.
4. Только затем искать новую ready-задачу.
```

---

# 35. Контекст задачи должен собираться из релевантных результатов

NanmiCoder AgentTeams передаёт исполнителю не всю историю Captain, а специально собранный пакет:

```text
цель команды
+
описание задачи
+
контракт задачи
+
результаты завершённых зависимостей
+
текущая попытка
```

Результаты зависимостей ограничиваются по размеру, чтобы случайно не заполнить весь контекст агента.

Это очень полезный принцип для нашей системы.

Контекст новой задачи должен строиться как:

```text
Task context
=
task definition
+
relevant dependency outputs
+
necessary team metadata
+
relevant messages
```

а не:

```text
вся история всех агентов команды
```

Это напрямую связано с будущей системой Context Budget.

---

# 36. Безопасное переназначение — процесс, а не смена `owner`

NanmiCoder AgentTeams не рассматривает переназначение задачи как простое:

```text
owner = B
```

Вместо этого нужно:

```text
1. аннулировать старую попытку;
2. закрыть допуск старого исполнителя;
3. прервать его текущую работу при необходимости;
4. дождаться согласованного состояния;
5. создать новую попытку;
6. назначить нового исполнителя.
```

Условно:

```text
TASK-42
owner=A
attempt=7

   ↓ reassign

REASSIGNING

   ↓

owner=B
attempt=8
```

Это очень важно для нашей будущей функции Pause → Edit → Resume.

При изменении схемы нельзя просто перепривязать ноду. Нужно корректно мигрировать существующую работу.

---

# 37. Безопасное удаление агента

Удаление участника у NanmiCoder AgentTeams также не является обычным удалением записи.

Правильная последовательность:

```text
1. запретить выдачу новой работы;
2. аннулировать активную попытку;
3. обработать или вернуть незавершённые задачи;
4. прервать активный Agent turn;
5. дождаться успокоения;
6. перераспределить работу;
7. сохранить историю участника;
8. убрать его из активной команды.
```

Для нашей системы это означает, что удаление AgentNode во время паузы должно иметь явную миграционную семантику.

Вместо физического исчезновения из истории разумно использовать состояние вроде:

```text
RETIRED
```

Agent больше не участвует в текущей схеме, но его Session, задачи и история остаются доступными для просмотра.

---

# 38. Холодное восстановление отличается от обычного `idle`

NanmiCoder AgentTeams различает две ситуации.

## Живой процесс

Агент `idle`, но за ним числится открытая попытка.

Значит, автоматически создавать новую попытку нельзя.

## Полный перезапуск DSH

На диске осталась незавершённая попытка, но старого процесса уже нет.

Это уже другой случай: работа может считаться «застрявшей после холодного восстановления», и система может создать новую попытку согласно правилам восстановления.

Для нас это очень полезное различие:

```text
runtime idle
≠
cold-recovered stale attempt
```

Процедура восстановления `TeamRun` после полного перезапуска должна быть отдельной частью архитектуры.

## Неопределённый внешний side effect нельзя слепо повторять

`agent-dag-workflow` хорошо формализует ещё один случай восстановления: процесс мог упасть **после** внешней мутации, но **до** надёжной фиксации результата. Например при `github.write`, публикации, deploy или другой операции с побочным эффектом.

В таком случае нельзя автоматически считать действие ни успешным, ни неуспешным:

```text
TaskAttempt / Action
status = UNCERTAIN | NEEDS_ATTENTION
```

Сначала нужно восстановить доказательство фактического состояния внешней системы либо получить явное решение `retry / fail / accept`. Слепой повтор может создать двойной PR, повторную публикацию или другую дублированную мутацию.

Для чистых read-only операций и заведомо идемпотентных действий это правило можно ослаблять политикой конкретного Tool.

---

# 39. Участники не должны расходовать модель, когда им нечего делать

В NanmiCoder AgentTeams постоянный участник не означает постоянный запрос к модели.

Если агенту нечего делать, его Session может просто существовать без активного LLM-запроса.

```text
Agent существует
≠
Agent сейчас тратит токены
```

Это критически важно для нашей идеи больших схем.

Команда может содержать, например:

```text
25 AgentNode
```

но одновременно реально работать будут только 4–6, если этого требует текущая работа.

---

# 40. Quality Gates: полезна идея, но не конкретный конвейер

NanmiCoder AgentTeams имеет развитую систему задач типа:

```text
requirements
implementation
verification
review
repair
integration
```

и машинно проверяемые условия завершения.

Например задача может иметь:

```text
objective
acceptance
inScope
outOfScope
verify
```

а при завершении агент должен предоставить:

```text
acceptanceResults
commandsRun
changedPaths
```

Это хороший принцип:

> Завершение серьёзной задачи должно определяться не только свободным текстом модели.

Но конкретный конвейер разработки ПО не следует встраивать в ядро нашей универсальной системы.

Вместо этого стоит сделать более общий механизм:

```text
Task Contract
```

Например:

```text
objective
acceptance criteria
required evidence
completion policy
scope
```

Тогда разные TeamDefinition смогут задавать свои правила:

```text
Coding Team
Research Team
Legal Team
Content Team
```

без изменения ядра оркестратора.

---

# 41. `halted` и `escalated` — разные состояния

NanmiCoder AgentTeams полезно различает:

```text
HALTED
```

человек явно остановил команду,

и:

```text
ESCALATED
```

автоматическая логика дошла до предела и больше не может безопасно продолжать без решения сверху.

Эту идею стоит перенести.

Для нас это может выглядеть так:

```text
PAUSED
STOPPED
FAILED
NEEDS_ATTENTION
```

или отдельным флагом эскалации.

Главное — не считать ситуацию «автоматика требует решения» равной команде, которую пользователь сознательно остановил.

---

# 42. Архив вместо уничтожения

После завершения NanmiCoder AgentTeams сохраняет историю команды.

Это правильная модель и для нас.

`TeamRun` после окончания должен переходить в архивное состояние:

```text
RUNNING
  ↓
COMPLETED / STOPPED / FAILED
  ↓
ARCHIVED
```

В архиве должны оставаться:

- snapshot TeamDefinition;
- Agent Runtime records;
- Session ID;
- задачи;
- попытки;
- сообщения;
- решения;
- события;
- результаты;
- ошибки.

Сохранённый `TeamDefinition` при этом остаётся отдельным reusable объектом и может быть запущен снова.

---

# 43. Что из NanmiCoder AgentTeams стоит перенять почти напрямую

На текущем этапе список выглядит так:

1. **Разделение планирования и исполнения**  
   `DRAFT → VALIDATED → APPROVED → RUNNING`.

2. **Постоянный Agent ↔ DSH Session**  
   Один агент команды живёт через несколько задач.

3. **Task + TaskAttempt**  
   Задача и конкретная попытка выполнения — разные сущности.

4. **Аннулирование старой попытки перед новой**  
   Старый результат никогда не должен завершить новую попытку.

5. **Событийный планировщик**  
   Реагировать на изменения DSH и задач, а не постоянно опрашивать состояние.

6. **`concurrencyPerAgent = 1` по умолчанию**  
   Один агент — одна активная рабочая попытка.

7. **`idle` не означает «свободен»**  
   Нужно учитывать рабочее состояние и TaskAttempt.

8. **Устойчивая почта**  
   Сообщения переживают перезапуски.

9. **Разделение доставки и потребления сообщения**  
   `queued → delivered → consumed`.

10. **Привязка сообщений к TaskAttempt**  
    Устаревшее сообщение не должно влиять на новое поколение работы.

11. **Приоритет коммуникации над новой задачей**  
    Сначала разобраться с текущей работой, затем выдавать новую.

12. **Передача результатов зависимостей ограниченным пакетом**  
    Не засорять контекст всей историей команды.

13. **Безопасное переназначение**  
    Переназначение — многошаговый переход состояния.

14. **Безопасное удаление агента**  
    Drain/revoke/reassign/stop до исключения из активной схемы.

15. **Отдельная логика холодного восстановления**  
    Не путать живой idle Agent и оставшуюся после рестарта попытку.

16. **Idle agents не делают лишних LLM-запросов**  
    Большая команда не должна означать большой постоянный расход.

17. **Архив TeamRun**  
    История работы никогда не уничтожается вместе с активной командой.

18. **Общий механизм Task Contract**  
    Вдохновлён Quality Gates, но без жёсткой привязки к разработке ПО.

---

# 44. Что из NanmiCoder AgentTeams не стоит переносить

## 44.1. Один Captain как абсолютный центр

Nanmi:

```text
Captain
├─ A
├─ B
└─ C
```

Наша система:

```text
Director
├─ Research Lead
│  └─ Researcher
└─ Engineering Lead
   ├─ Backend Lead
   │  └─ Developer
   └─ QA Lead
      └─ Tester
```

Управление должно быть многоуровневым.

## 44.2. Плоский `members[]`

Все наши агенты, включая стартового Lead, должны быть одинаковыми `AgentNode`.

Иерархия задаётся связями, а не особым скрытым Captain.

## 44.3. Жёстко прошитый software quality pipeline

Конкретные `requirements → implementation → review` должны быть надстройкой, а не ядром.

## 44.4. Большой набор низкоуровневых инструментов для модели

Если технический `taskId`, `attemptId`, `agentId` можно определить из контекста вызова, лучше не заставлять модель передавать их вручную.

Модель должна видеть более простой интерфейс:

```text
complete_task
send_message
ask
report_blocker
delegate
```

а плагин сам подставляет внутреннюю идентичность попытки.

## 44.5. Один `team.json` как окончательная модель хранения

Для нашей более сложной системы лучше отдельно рассмотреть:

```text
canonical snapshot
+
append-only event journal
```

а не заранее повторять файловую модель Nanmi.

---

# 45. Место NanmiCoder AgentTeams в нашей архитектуре

Если Orca для нас — источник логической дисциплины, то NanmiCoder AgentTeams — главный референс того, как эту дисциплину реализовать **нативно внутри DSH**.

Условно:

```text
ORCA
│
│  Task / Attempt / ownership / reliable coordination
│
▼
логические идеи

DSH
│
│  Agent / Session / Inbox / runtime status / cancellation
│
▼
низкоуровневый фундамент

NanmiCoder AgentTeams
│
│  scheduler / durable team / attempts / mailbox / recovery
│
▼
практический мост

НАШ ПЛАГИН
│
└─ иерархический Agent Graph
   + communication graph
   + richer AgentDefinition
   + live editable topology
```

NanmiCoder AgentTeams не является готовой основой нашего продукта целиком, но его `scheduler`, работа с попытками, сообщения, восстановление и безопасные переходы состояния — одни из наиболее ценных готовых решений, которые стоит изучать на уровне исходного кода.

---

# 46. Разбор dsh-Visual-Workflow

`GZX2211/dsh-Visual-Workflow` — один из самых полезных референсов для **визуального слоя, модели графа и связи UI с runtime**.

По внешней форме он очень близок к нашей задумке:

```text
большой холст
+ ноды
+ типизированные связи
+ Inspector
+ живое состояние
+ шаблоны
+ запуски
```

Но его исполнительная модель нам подходит значительно хуже. Главное различие:

```text
Visual Workflow:
Graph → Parent Agent интерпретирует граф → wf_run_node → Child Agent
```

Наша система должна работать так:

```text
TeamDefinition → Control Plane → Scheduler → DSH Agents
```

То есть у Visual Workflow стоит заимствовать **редактор, модель данных, синхронизацию и отображение runtime**, но не превращать Lead LLM в главный планировщик.

---

# 47. Холст и модель редактора

Плагин имеет полноценный node-based редактор:

- перемещение нод;
- перемещение холста;
- масштабирование;
- `fitView`;
- фокус на конкретной ноде;
- соединение портов;
- временную линию при соединении;
- выбор ноды и линии;
- подсветку выполнения;
- группы;
- изменение размеров групп;
- undo/redo.

Ноды отображаются как HTML-карточки, связи — отдельным SVG-слоем. Сам код самописного холста необязательно копировать: для нас важнее предметная модель и UX, а конкретный графический движок можно выбрать отдельно.

# 50. Типизированные связи и порты

Одна из сильнейших идей Visual Workflow — разные линии имеют разные значения:

```text
flow
context
database
```

Для нас конкретные типы будут другими, но принцип обязателен. Минимально:

```text
Authority Edge
Communication Edge
```

А граф зависимостей задач существует отдельно.

Visual Workflow также использует разные физические порты (`flow-in`, `ctx-in`, `db-in`, `flow-out`, `ctx-out`). Для нас возможны отдельные порты либо режим соединения, но тип связи должен быть определён **до** её создания, а не угадываться моделью позднее.

Из Knotline стоит взять небольшой, но полезный UI-паттерн: если между двумя типами нод допустимо несколько разных отношений, после соединения показывать **Relation Composer** с конечным списком разрешённых смыслов, а не угадывать связь по жесту. Например `Lead → Reviewer` может означать authority или только communication. Выбор пользователя сразу создаёт типизированный edge.

---

# 51. Template → Instance → Run

Очень сильная продуктовая модель:

```text
Template
   ↓
Instance
   ↓
Run
```

Для нас это превращается в:

```text
AgentTemplate → AgentNode
TeamDefinition → TeamRun
```

Шаблон можно использовать много раз; конкретный экземпляр команды может развиваться независимо; каждый запуск хранит собственный snapshot и runtime-историю.

---

# 52. Канонический документ как источник истины

Visual Workflow хранит настоящий документ графа с `nodes[]`, `lines[]` и `revision`. Холст является только его проекцией.

Это полностью совпадает с тем, что нужно нам:

```text
              TeamDefinition
                /        \\
               /          \\
          Canvas          Runtime
```

Редактор и runtime не должны иметь две независимые версии истины.

Правильные потоки:

```text
TeamDefinition → Canvas Projection
TeamDefinition → Runtime Projection
TeamRun + DSH Runtime → Live Canvas Overlay
```

---

# 53. Геометрия отдельно от поведения

Visual Workflow уже различает чисто визуальные и смысловые изменения. При сравнении схем он игнорирует положение нод и размеры групп, но считает изменением конфигурацию ноды и смысловые связи.

Для нас это надо формализовать сильнее:

```text
TeamDefinition = поведение
TeamLayout = представление
```

Нужен и семантический diff:

```text
Visual Change ≠ Semantic Change
```

Это важно для версий, истории, GraphPatch и live editing.

---

# 54. Undo/Redo, dirty-state и ревизии

В редакторе есть история снимков графа (`past[] / future[]`) и точное понимание, совпадает ли текущая схема с последней сохранённой. Это нужно перенять.

Также документ имеет `revision`, а запись может выполняться с `expectedRevision`. Это защищает от конкурентных изменений:

```text
User opened revision 20
Agent proposed patch for revision 20
User saved revision 21
Agent patch for 20 → CONFLICT
```

Такой механизм обязателен, если менять схему смогут и пользователь, и агенты.

---

# 55. GraphPatch

Visual Workflow уже реализует структурированные операции над графом:

```text
create_node
remove_node
update_node_data
connect
disconnect
create_group
set_group_members
```

Для нас это хороший фундамент `GraphPatch`.

В первой версии агент должен только **предлагать** изменение:

```text
Agent → GraphPatch → Validator → Preview → User approval → Apply
```

Особенно это важно для изменений иерархии, прав, MCP и удаления агентов.

---

# 56. Постоянный DSH Agent за нодой

Visual Workflow связывает ноду с постоянным DSH Agent по ключу примерно `sessionId + flowId + nodeId`. Повторный запуск ноды может отправить следующую задачу тому же Agent вместо создания нового.

Это практически совпадает с нашей моделью:

```text
AgentNode
   ↕
persistent DSH Session
```

AgentNode не должен быть одноразовым вызовом модели.

---

# 57. Подпись конфигурации агента

Плагин вычисляет подпись из параметров, которые влияют на состав агента:

```text
system prompt
provider
model
reasoning
tools
preset
group prompt
```

Если подпись не изменилась, Agent переиспользуется. Если изменилась — создаётся новый.

Сама идея подписи полезна, но автоматическая политика пересоздания для нас слишком грубая. Изменения нужно классифицировать:

```text
можно применить к существующей Session
требует restart
требует fork
требует решения пользователя
```

---

# 58. RunSnapshot отдельно от TeamDefinition

Visual Workflow правильно не хранит runtime-статус в постоянном графе. Есть отдельный `RunSnapshot` с состояниями нод, попытками, временем и результатами.

Для нас аналогично:

```text
TeamDefinition = что команда собой представляет
TeamRun = что происходит в конкретном запуске
```

Живые `RUNNING/IDLE/TASK/ATTEMPT` не должны записываться в TeamDefinition.

---

# 59. Холст одновременно редактор и монитор

Visual Workflow накладывает runtime-состояние поверх тех же нод. Это нужно перенять.

Наша AgentNode может показывать:

```text
model / reasoning
DSH state
work state
current Task
current Attempt
context usage
last activity
```

Подробности открываются в Inspector.

---

# 60. Live editing и принцип «прошлое заморожено»

Visual Workflow умеет менять будущую часть графа во время Run. Завершённые ноды и уже использованные связи блокируются, активная часть ограничена, а будущее можно менять.

Принцип очень сильный:

```text
completed area = immutable
active area = constrained
future area = editable
```

Но для первой версии нашей системы безопаснее:

```text
RUNNING → PAUSING → PAUSED → EDIT → VALIDATE → APPLY REVISION → RESUME
```

Потому что у нас меняется не только workflow, но и authority, communication, TaskAttempt ownership, Skills, MCP и Session identity.

Идею редактируемого будущего стоит оставить для более поздней версии.

---

# 61. Группы

Visual Workflow имеет `GroupNode`, внутри которой несколько агентов могут работать параллельно. Для нас группы полезны как визуальные отделы:

```text
Engineering
┌──────────────────────┐
│ Engineering Lead     │
│ Backend Developer    │
│ QA                   │
└──────────────────────┘
```

Но группа не должна автоматически определять полномочия. Источником authority остаются явные `AuthorityEdge`.

---

# 62. Состояние ожидания совместной работы

В Visual Workflow участник группы после своего результата может оставаться доступным для последующего общения (`armed`), а не сразу считаться полностью завершённым.

Для нас это полезная идея рабочего состояния вроде:

```text
WAITING_COLLABORATION
```

Агент завершил текущий ход, но остаётся участником активной совместной работы.

---

# 63. Proxy Node

Visual Workflow позволяет нескольким визуальным карточкам ссылаться на одного runtime Agent. Для линейного workflow это удобно, но в организационной схеме может запутать идентичность агента.

Поэтому в authority-графе один Agent должен иметь одну каноническую AgentNode. Если понадобится повторная визуальная ссылка, она должна явно выглядеть как ссылка, а не как новый агент.

---

# 64. Ресурсные и служебные ноды

Visual Workflow показывает полезную будущую идею: ресурс тоже может быть нодой (`File`, `Database`).

В нашей системе позже возможны:

```text
MCP Node
Skill Node
Knowledge Node
Workspace Node
Queue Node
Router Node
User Gate Node
Decision Node
```

Но MVP не должен перегружаться. Сначала нужны `AgentNode`, authority, communication и task system.

---

# 65. Decision/User Gate вместо Pause Node

В Visual Workflow `Pause Node` является частью workflow. У нас пауза относится к `TeamRun` целиком.

Но отдельная нода решения может быть полезна:

```text
Architect
    │
    ▼
◇ USER DECISION
    │
    ▼
Developer
```

Это хорошо сочетается с `Decision` из Orca.

---

# 66. Валидатор графа

Visual Workflow имеет отдельный слой проверки, который знает допустимые типы связей, циклы, ссылки, группы и структурные ограничения.

Для нас `TeamValidator` должен применяться:

```text
при сохранении
при GraphPatch
перед запуском
при Pause → Edit → Resume
при импорте схемы
```

Валидатор является частью доменной модели, а не только интерфейса.

---

# 67. Главный недостаток: Parent Agent управляет графом

В Visual Workflow граф не является полностью исполняемой машинной схемой. При запуске Parent Agent получает описание графа и сам вызывает `wf_run_node(nodeId)`.

```text
Graph
  ↓
Parent LLM
  ↓
wf_run_node
  ↓
Child Agent
```

Для нашей системы это неправильный фундамент.

Точное состояние и переходы должен контролировать обычный код:

```text
Task DAG
+ TaskAttempt
+ Scheduler
```

Модель может решать содержательные вопросы, но не должна быть единственным хранителем механики исполнения.

---

# 68. Условные переходы не должны зависеть только от догадки LLM

Visual Workflow имеет условные линии `pass / fail / content`, но Parent Agent семантически решает, какую ветку выбрать.

Для критических переходов нам лучше иметь структурированные результаты:

```text
review.verdict = pass
decision = approved
```

и обычный код открывает соответствующую ветку.

---

# 69. Двусторонняя синхронизация UI/runtime

Сам принцип очень полезен:

```text
User edits TeamDefinition
        ↓
validate
        ↓
apply revision
        ↓
runtime sees new definition
```

и обратно:

```text
DSH Agent state
+ TeamRun state
+ Task state
        ↓
UI projection
```

При этом визуальный слой не должен становиться вторым источником истины.

# 70. Что из Visual Workflow стоит перенять

1. Большой node-based редактор.
2. Строгие типы нод.
3. Строгие типы связей.
4. Inspector для выбранной ноды/связи.
5. `Template → Instance → Run`.
6. Канонический документ схемы.
7. Отдельный runtime snapshot.
8. Ревизии и `expectedRevision`.
9. Undo/Redo/dirty tracking.
10. `TeamLayout` отдельно от смысловой схемы.
11. Семантический diff.
12. Валидатор графа.
13. Постоянный DSH Agent за AgentNode.
14. Подпись runtime-конфигурации AgentNode.
15. Живые статусы поверх нод.
16. `GraphPatch`.
17. Визуальные группы.
18. Run lock для конфликтующих запусков/редактирования.
19. Идею «завершённое прошлое неизменно» для будущего live editing.
20. Возможность в будущем показывать ресурсные и decision-ноды.

---

# 71. Что из Visual Workflow не стоит переносить

1. Parent Agent как главный планировщик.
2. Flow Graph как замену Task DAG.
3. Критические условия, определяемые только LLM.
4. Плоскую модель Parent → Agents.
5. Автоматический restart Agent при любом изменении подписи.
6. Свободное live editing без общей паузы в первой версии.
7. Proxy Node как обычную часть authority-графа.
8. Полное копирование самописного SVG canvas без отдельной оценки графического движка.


Эти проекты хорошо дополняют друг друга.

# 74. Память команды, артефакты и экономия модельных вызовов

Память нужно проектировать исходя из неприятного, но полезного предположения:

> **Модельный контекст ненадёжен и дорог.**

Поэтому нельзя строить систему так, чтобы важное состояние жило в голове Lead или в длинной переписке конкретного Agent.

Правильная схема:

```text
                   НАСТОЯЩАЯ ПАМЯТЬ
          ┌──────────────────────────────┐
          │ TeamRun state                │
          │ Tasks / Attempts             │
          │ Messages / Decisions         │
          │ Artifacts / Links            │
          │ Event Journal                │
          │ DSH Sessions                 │
          └──────────────┬───────────────┘
                         │
                  Context Builder
                         │
                         ▼
                bounded working set
                         │
                         ▼
                       Model
```

Контекст конкретного агента — это только текущий рабочий набор поверх этой памяти.

# 75. Четыре слоя памяти

## 75.1. Структурированное состояние оркестратора

Самая надёжная память:

```text
TeamRun
Task
TaskAttempt
Message
Decision
AgentRuntime
GraphRevision
AwaitSet
```

Для чтения и изменения этих объектов модель вообще не должна быть обязательна.

Например факт:

```text
TASK-42
status = WORKING
owner = Developer
attempt = 3
```

должен знать обычный код.

## 75.2. Artifact Store

Всё содержательное, что команда создала или получила в ходе работы:

```text
research
architecture
patch
test report
log
dataset
JSON
image
source bundle
external document snapshot
```

Это основная долговременная предметная память TeamRun.

## 75.3. Нативная DSH Session

DSH Session остаётся владельцем истории конкретного агента:

```text
user / assistant messages
tool calls
tool results
compaction events
runtime history
```

Нашему плагину не нужно копировать весь transcript в собственную БД.

В наших сущностях достаточно сохранять устойчивую привязку:

```text
AgentRuntime.sessionId
```

и ссылки на Session там, где это помогает аудиту.

## 75.4. Working Context

Это небольшой набор, реально отправляемый модели на текущем ходу:

```text
роль
текущая Task
acceptance criteria
нужные Decisions
новые Messages
короткий список релевантных Artifacts
небольшой recent tail Session
```

Он может быть потерян и восстановлен из устойчивых слоёв выше.

# 76. Artifact как отдельная доменная сущность

Артефакт не должен быть просто путём к случайному файлу.

Минимальная модель:

```text
Artifact
├ id
├ logicalKey?
├ type
├ title
├ scope
├ createdByAgentId
├ createdBySessionId
├ teamRunId
├ taskId?
├ attemptId?
├ decisionId?
├ createdAt
├ currentVersionId
└ status
```

Содержимое хранится через отдельные `ArtifactVersion`:

```text
ArtifactVersion
├ id
├ artifactId
├ version
├ contentHash
├ storageRef
├ mimeType
├ sizeBytes
├ createdAt
├ summary
├ preview
├ metadata
└ provenance
```

Разделение `Artifact` и `ArtifactVersion` позволяет иметь устойчивую логическую сущность и неизменяемые версии её содержимого.

---

# 77. Артефакты должны быть неизменяемыми по версиям

Не стоит физически перезаписывать старый результат.

Вместо:

```text
architecture.md
перезаписали
```

лучше:

```text
ART-17
 ├ v1
 ├ v2
 └ v3 ← current
```

или логически:

```text
ART-17-v1
    ↓ superseded_by
ART-17-v2
```

Это даёт воспроизводимость.

Можно точно установить:

```text
TASK-42 / ATTEMPT-3
использовал ART-17 version 2
```

даже если позже документ был обновлён.

# 79. Scope и права доступа к артефактам

Не каждый артефакт обязан автоматически быть частью памяти всей команды.

Можно ввести:

```text
PRIVATE
TASK
SUBTREE
TEAM
PROJECT
```

### PRIVATE

Личный рабочий материал конкретного Agent.

### TASK

Доступен участникам конкретной Task/Attempt.

### SUBTREE

Доступен определённой ветке authority-графа, например всему Engineering.

### TEAM

Доступен всем агентам текущего TeamRun.

### PROJECT

Сохраняется как долгосрочное знание и может использоваться в будущих TeamRun.

По умолчанию Run-артефакт **не должен автоматически превращаться в вечную память проекта**.

Продвижение в `PROJECT` лучше делать явно:

```text
Run Artifact
     ↓ promote
Project Knowledge
```

# 81. Где физически хранить память и артефакты

Предварительно наиболее разумная схема:

```text
DSH
└─ native Session persistence

Our plugin data root
├─ orchestrator.sqlite
└─ blobs/
   └─ sha256/
      ├─ 00/
      ├─ 01/
      └─ ...
```

## SQLite

Хранит небольшие структурированные данные и связи:

```text
team_definitions
team_revisions
team_layouts
team_runs
agent_runtime

tasks
task_attempts
messages
decisions
await_sets

artifacts
artifact_versions
artifact_links

events
```

SQLite здесь удобен потому что нам нужны:

- транзакции;
- точные связи;
- фильтрация;
- индексы;
- локальная работа без отдельного сервера;
- восстановление после аварии.

Для активного процесса логично использовать WAL-режим, если он не конфликтует с окружением Host.

## Blob Store

Хранит большие неизменяемые данные:

```text
large text
logs
patches
images
binary files
raw reports
serialized datasets
```

Адресовать их лучше по хешу содержимого:

```text
sha256:<hash>
```

Это автоматически даёт дедупликацию.

Два ArtifactVersion могут ссылаться на один физический blob.

---

# 82. Почему не хранить большие артефакты прямо в SQLite

Большие бинарные и текстовые результаты удобнее отделить от метаданных.

Преимущества:

- БД остаётся небольшой и быстро индексируется;
- можно дедуплицировать одинаковое содержимое;
- проще отдавать потоковый preview/download;
- проще хранить большие логи и изображения;
- можно отдельно реализовать GC;
- запись Artifact metadata остаётся дешёвой.

Маленькие значения можно хранить inline как оптимизацию, но это деталь реализации, а не семантика модели.

---

# 83. Атомарное сохранение Artifact

Создание артефакта должно переживать падение процесса без полусохранённого состояния.

Рекомендуемый порядок:

```text
1. Получить/создать содержимое.
2. Посчитать contentHash.
3. Записать blob во временный файл.
4. fsync + atomic rename в content-addressed path.
5. Открыть SQLite transaction.
6. Insert ArtifactVersion.
7. Insert ArtifactLink / provenance.
8. При необходимости изменить TaskAttempt / Task.
9. Append Event.
10. COMMIT.
```

Если SQL-транзакция не дошла до commit, максимум останется сиротский blob, который позже можно удалить GC.

Гораздо опаснее обратная ситуация, когда БД ссылается на содержимое, которое физически не было надёжно записано.

# 84. Event Journal и текущие таблицы нужны одновременно

Не стоит делать чистый event sourcing единственным способом узнать текущее состояние.

Лучше:

```text

+

```

Текущие таблицы отвечают быстро:

```text

```

Журнал хранит историю:


Это даёт аудит и восстановление без необходимости пересобирать всё состояние из миллионов событий при каждом чтении.

# 85. Большие tool results должны автоматически превращаться в Artifact

Это одна из самых важных функций для экономии контекста.

Плохой путь:

```text
shell returned 800 KB
       ↓
800 KB попали в Session/context
```

Правильнее:

```text
Tool Result
   │
   ├ small
   │   └─ обычный model-facing result
   │
   └ large
       ├─ full content → Artifact Store
       └─ model sees:
          ART-341
          size
          short preview
          deterministic metadata
```

Например:

```text
Tests failed: 17 failures.
Full output: ART-341
Preview: ...
```

Порог должен быть настраиваемым по типу данных.

---

# 86. Summary артефакта не должен требовать отдельного LLM-вызова

Автоматически запускать отдельного «Summarizer Agent» после каждого результата слишком дорого.

Приоритет источников краткого описания:

```text
1. Структурированные deterministic metadata.
2. Summary, которое producer Agent вернул в том же рабочем ходе.
3. Простая программная выжимка/preview.
4. Отдельный LLM-summary только если он действительно нужен.
```

Примеры model-free summary:

### Git patch

```text
12 files changed
+418 / -91
paths: ...
```

### Test report

```text
128 passed
3 failed
exitCode=1
```

### Log

```text
size=4.2MB
errorCount=37
head/tail preview
```

Это экономит отдельные запросы модели.

# 89. Поиск по памяти сначала без embeddings

На первом этапе не стоит автоматически превращать каждый transcript и Artifact в vector database.

У нас уже есть точные структурированные связи:

```text
Task → Artifact
Attempt → Artifact
Decision → Task
Agent → Task
Artifact → Artifact
```

Поэтому порядок поиска лучше такой:

```text
1. exact ID
2. relation filters
3. scope/type/time filters
4. tags/metadata
5. SQLite FTS full-text
6. semantic/vector search — позже, если возникнет реальная необходимость
```

Это дешевле, воспроизводимее и не требует модельных вызовов.

# 90. PTC как основной механизм экономии вызовов модели

PTC хорошо совпадает с нашей архитектурой.

Главная цель:

> **Один содержательный ход модели должен уметь выполнить много механических действий без промежуточных LLM round-trip.**

Плохо:

```text
Model
→ read
→ Model
→ search
→ Model
→ read
→ Model
→ tests
→ Model
```

Лучше:

```text
Model
   ↓
run_code
   ├ read several artifacts
   ├ search files
   ├ filter results
   ├ execute tests
   ├ save artifact
   └ return compact result
   ↓
Model receives only useful final output
```

PTC особенно полезен для:

- batch reading;
- фильтрации;
- циклов;
- нескольких API/tool calls;
- поиска;
- Git;
- тестов;
- преобразования данных;
- параллельных независимых read-only операций.

---

# 91. Важный принцип PTC: скрытая память внутри `run_code` не нужна

Каждый PTC-run должен восприниматься как отдельное вычисление.

Не следует строить долгосрочную память на переменных скрытого постоянного REPL/kernel.

Если данные должны пережить вызов:

```text
write Artifact
update Task/Attempt
send Message
resolve Decision
append Event
```

То есть:

> **Модель думает. PTC выполняет. Система помнит.**

---

# 92. Высокоуровневый PTC-friendly SDK оркестратора

Не стоит давать агенту десятки мелких технических инструментов оркестрации.

Лучше небольшой стабильный набор высокоуровневых возможностей, например:

```text
artifact_list / artifact_search / artifact_read / artifact_write
message_send
decision_request
task_commit
```

Технические:

```text
taskId
attemptId
agentId
teamRunId
```

по возможности подставляются Host автоматически из контекста вызова.

Это уменьшает prompt/schema-шум и вероятность ошибки модели.

---

# 93. Лестница минимизации model calls

Каждое действие должно проходить через такой мысленный фильтр:

```text
Можно решить обычным кодом?
        │
       YES
        ↓
   0 model calls

       NO
        ↓
Можно выполнить механическую работу одним PTC-run?
        │
       YES
        ↓
   1 model call

       NO
        ↓
Нужно новое содержательное рассуждение модели
        ↓
 additional model call
```

Новый LLM-вызов оправдан только тогда, когда требуется **новое смысловое решение**, а не простой цикл, ожидание, маршрутизация или обработка структурированных данных.

---

# 94. Wake Scheduler: экономить нужно не только tool calls, но и пробуждения агентов

В multi-agent системе основной расход может возникнуть от бесконечного общения:

```text
A → B
B проснулся
B → A
A проснулся
...
```

Поэтому обычный `Scheduler` должен дополняться логикой пробуждения.

Сообщение хранит политику:

```text
WakePolicy
├ NEVER
├ NEXT_TURN
├ BATCH
└ IMMEDIATE
```

Примеры:

```text
STATUS            → NEVER
normal REPORT     → BATCH
child completed   → BATCH
blocking QUESTION → IMMEDIATE
new TASK          → IMMEDIATE
```

UI при этом получает live status напрямую из runtime и не требует пробуждать LLM.

---

# 95. AwaitSet: объединять несколько результатов перед пробуждением менеджера

Если Manager делегировал три задачи:

```text
T1
T2
T3
```

не нужно будить его три раза.

Создаётся:

```text
AwaitSet
members: T1,T2,T3
condition: ALL_COMPLETED
wake: Manager
```

Планировщик ждёт программно:

```text
T1 completed
T2 completed
T3 completed
        ↓
one Manager wake
```

Это может резко уменьшить количество запросов в больших иерархиях.

---

# 96. Стабильный Agent prompt и tool surface помогают KV cache

Набор возможностей агента должен быть узким, но по возможности стабильным в течение Session.

Постоянное изменение:

```text
tools list
system prompt
PTC SDK
```

может уменьшать повторное использование provider KV cache.

Поэтому текущую Task и Artifact Manifest лучше добавлять как динамический хвост, а базовую AgentDefinition держать стабильной.

Это ещё один аргумент против перестройки набора tools после каждой мелкой задачи без необходимости.

# 97. Метрики экономии должны быть частью TeamRun

Нужно считать не только токены.

На уровне Agent / Task / TeamRun полезно хранить:

```text

outputTokens

PTCSubcalls
```


# 104. Inbox и Artifact attachment

Message не должен копировать большое содержимое.

Вместо:

```text
Message.content = 200 KB report
```

лучше:

```text
Message

- ART-44
```

Получатель увидит короткое сообщение и Artifact Manifest.

Полное содержимое читается только при необходимости.

# 105. `task_commit` должен одновременно фиксировать результат и артефакты

Завершение задачи не должно требовать дополнительного Summarizer Agent.

Один рабочий ход может закончиться структурированным действием:

```text
task_commit({
  status: "completed",
  summary: "...",
  artifacts: [...],
  evidence: [...]
})
```

Host внутри одной транзакции:

```text
закрывает authoritative TaskAttempt
создаёт/привязывает ArtifactVersion
обновляет Task
разблокирует dependents
append Event
```

Это экономит отдельный LLM-вызов на «подведение итогов».

# 106. Жизненный цикл и удаление Artifact

Так как версии immutable, обычное «удалить файл» лучше не использовать как основную семантику.

Возможные состояния:

```text
ACTIVE
SUPERSEDED
ARCHIVED
TOMBSTONED
```

Физический blob удаляется только Garbage Collector, когда:

```text
нет живых ArtifactVersion references
+
истёк retention period
+
blob не закреплён архивным Run/Project Knowledge
```

Это защищает историю TeamRun.

---

# 107. Восстановление после перезапуска

После полного рестарта не нужно восстанавливать память из model context.

Алгоритм:

```text
1. Открыть orchestrator.sqlite.
2. Восстановить TeamRun state.
3. Связать AgentRuntime с DSH Session IDs.
4. Проверить незавершённые TaskAttempts.
5. Проверить ожидающие Messages / AwaitSets / Decisions.
6. Проверить Artifact refs и blobs.
7. Построить TaskContextPacket только когда конкретный Agent снова понадобится.
```

То есть отсутствие старого prompt целиком не является катастрофой.

# 108. Итоговая архитектура памяти

```text
                     TeamRun
                        │
       ┌────────────────┼─────────────────┐
       │                │                 │
       ▼                ▼                 ▼
   State Store     Artifact Store     Event Journal
   (SQLite)        metadata + blobs   (SQLite)
       │                │                 │
       └────────────────┼─────────────────┘
                        │
                   Memory View
                        │
                TaskContextPacket
                        │
                        ▼
                   DSH Agent
                        │
                       PTC
                        │
               many mechanical ops
                        │
                        ▼
                 one useful result
```

Главный принцип:

> **Система должна хранить факты и материалы сама. Модель должна получать только тот кусок памяти, который нужен для следующего содержательного решения.**

А принцип экономии:

> **Не будить модель ради работы, которую можно выполнить кодом; не делать несколько модельных ходов там, где один PTC-run может выполнить серию механических действий.**

# 110. Текущий общий вывод

Желаемая система — это не просто «команда субагентов».

Это **визуальный конструктор и исполняющая среда для устойчивых иерархических команд DSH Agent**, где:

- каждый агент является настоящей отдельной DSH-сессией;
- каждому можно задать модель и ограничения;
- подчинение и общение задаются явно;
- работа хранится в виде задач и отдельных попыток;
- все важные сообщения и решения являются устойчивыми объектами;
- состояние команды не зависит от памяти одного Lead;
- команда может быть сохранена, запущена повторно, поставлена на паузу и изменена;
- интерфейс показывает одновременно структуру команды и её живое состояние;
- критические знания и результаты хранятся вне модельного контекста в Tasks, Messages, Decisions, Artifacts и Event Journal;
- большие результаты не засоряют context, а превращаются в адресуемые Artifact;
- Context Builder выдаёт агенту только релевантный рабочий набор;
- Scheduler и Wake Scheduler стараются не будить модель без необходимости;
- PTC используется как основной способ выполнять много механических операций за один содержательный модельный ход;
- DSH отвечает за исполнение агентов и их Session;
- наш плагин отвечает за организацию, ответственность, память команды и координацию.

Orca является ценным образцом **дисциплины управления работой**, но не образцом технической реализации для нашего случая.

NanmiCoder AgentTeams является более близким практическим референсом: он показывает, как постоянные DSH Sessions, событийный планировщик, Task/Attempt, устойчивая почта, восстановление и безопасное переназначение могут работать внутри самого DSH.

`dsh-Visual-Workflow` является главным текущим референсом для визуального слоя: строгие ноды и связи, `Template → Instance → Run`, канонический документ графа, ревизии, валидатор, живые состояния, постоянный Agent за нодой, GraphPatch и двусторонняя синхронизация UI/runtime.

При этом его центральную модель «Parent LLM сам интерпретирует граф и вызывает следующие ноды» переносить не следует. В нашей системе точное состояние, зависимости, владение задачами и планирование должны контролироваться обычным программным кодом.

Наша система должна быть проще Orca там, где DSH уже даёт надёжные внутренние примитивы, использовать практические механизмы NanmiCoder AgentTeams для исполнения и взять у Visual Workflow зрелую модель node-based интерфейса и данных, не превращая LLM в источник истины об оркестрации.

Итоговый принцип:

> **DSH отвечает за существование, Session и исполнение агента; наш плагин — за организацию, ответственность, устойчивую память, артефакты, задачи, попытки, коммуникации, решения и жизненный цикл команды. Контекст модели — только временный рабочий кэш, а визуальный холст — управляемая проекция этой системы, не отдельный источник истины.**
