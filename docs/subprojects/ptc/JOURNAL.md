## 2026-09-30 — Этап 5: Worker mutation MVP

Первоначальный task snapshot `origin/preview` — `ee1ceba2dad3c831fef4cd070c65f5fbc8fdf4c8`; перед публикацией задача перенесена на продвинувшийся `origin/preview` `2414e89659d41d1baf01fb0cae0b1534b5a08434`. Worker experimental Leader получил explicit `postman-worker-mutation` revision 2: `read/glob/grep/web_fetch/web_search/write/edit`. Только exact Worker с текущим Host task context и обычной видимостью соответствующего инструмента вызывает mutation из QuickJS; production Worker/Bridge и дети Worker PTC не получают, Leader остаётся read-only. Существующий Stage 4.5 resolver теперь проверяет `write/edit.file_path`: relative от `context.worktree`, absolute outside / `..` escape / pre-existing symlink-junction outside reject до Host dispatch; future target использует canonical ближайшего существующего предка. До и после async guard и после ToolRuntime settlement сверяются исходный task context и полномочия. Диспетчеризация идёт через штатный `ctx.tools.execute` с exact Worker Agent, rootCallId, parent token и subCallId; DSH read-before-edit, createIfAbsent/replaceIfVersion, schema/permission/abort и stale semantics не заменены адаптером. Успешный effect не откатывается при последующей ошибке программы; нет транзакции, rollback или retry; недождавшийся Host call остаётся pending/unknown. Shell/jobs/report доступны ordinary Worker снаружи PTC, внутри PTC их нет. Stage 5A adversarial namespace isolation остаётся deferred / not required for MVP. Проведены автоматические QuickJS → ToolRuntime tests, не live acceptance; Stage 6 — отдельная команда, установленный Harness не менялся.

## 2026-09-30 — Этап 5A: исследование и решение отложить hardening для MVP

Только локальный исследовательский Windows/Node prototype использовал rooted HANDLE и `NtCreateFile`-style операции; в `ptc-adapter` его не подключали, Worker PTC `write/edit` не включали, native dependency в product не переносили. Удержание parent HANDLE закрыло конкретную старую junction-подмену после pinning. 14/14 исследовательских тестов завершились по ожиданиям, но некоторые намеренно подтвердили оставшиеся ограничения — это не Stage 5A PASS. Для строгой adversarial boundary не решены доверенное закрепление identity task root до его возможной подмены и атомарное «replace directory entry только если existing target всё ещё имеет проверенную identity/version». `dsh-fs-sandbox` не является абсолютным решением такой boundary.

Решение пользователя: Stage 5A — deferred / not required for MVP, поскольку ordinary Worker уже имеет shell и обычные filesystem tools; не расширять MVP ради OS-level защиты от конкурентно враждебного ordinary Worker. Stage 5 может продолжаться отдельно на Host-side границе worktree с ограниченной моделью угроз из [PTC_CONTRACT.md](PTC_CONTRACT.md), но всё ещё не реализован. Если понадобится изоляция недоверенных Worker, вернуть rooted/descriptor mutation или sandboxing ordinary Worker отдельным security project. Исследовательский прототип не является частью продукта.

## 2026-09-30 — Этап 4.5: Host-side Worker PTC filesystem boundary

Stage 4 Worker live-приёмка: настоящий Worker `ptc_execute`, корректный namespace, отсутствие Node globals и `write/edit/shell/report/notify_parent/postman_*` внутри PTC, настоящий QuickJS → Harness glob/read/grep, continuable follow-up, три Worker и selective stop, отсутствие PTC production Worker — PASS. Но relative `read("plugins/dsh-ptc/src/runtime.js")` прочёл файл в `.dsh`/session cwd вместо Host-bound task worktree. Stage 5 mutation поэтому остановлен до security/operational этапа 4.5.

Baseline regression с двумя деревьями (`INSTALLATION_MARKER` / `WORKTREE_MARKER`) на реальном QuickJS → ptc_execute → ToolRuntime до исправления вернул `INSTALLATION_MARKER`. Причина: DSH `read` задаёт базу из `agent.session.header.cwd`; `glob/grep` запускают ripgrep от session cwd, а per-call scoped-root API в ToolRuntime нет. Исправление только в Postman Host adapter: exact live Worker/Leader slot → current task context → canonical root/target → переписанные аргументы read/glob/grep → обычный `ctx.tools.execute`. Absolute/traversal/junction escapes fail closed; перед каждым filesystem call контекст повторно подтверждается, старой программе новый root не выдаётся. Два Leader с разными worktree и три Worker одного Leader покрыты адресными тестами. `web_fetch/web_search`, ordinary Worker и Leader PTC без изменений. `write/edit` и shell внутри PTC не добавлены; live model acceptance, установка, merge и promotion не проводились.

На момент этого PR живая Worker-приёмка ещё не запускалась; позднее её результат и обнаруженный дефект записаны выше. Установленный Harness этим PR не менялся.

## 2026-09-29 — Исправления после проверки PR №245

Обрыв дочернего pipe обрабатывается на самих потоках и завершает запуск без падения родителя; ожидающие записи отклоняются. Бюджет ответа Host-функции теперь терминален, служебная оболочка отделена от лимита JSON-значения профиля. Снимок эффектов различает не начатые и незавершённые функции, учитывает завершения во время очистки; повторный `dispose` ждёт то же завершение. Ошибка очистки исключает `ok`. Добавлены адресные регрессионные сценарии; на Windows / Node v24.21.0 пакетные тесты 30/30 и проверка установленного архива с QuickJS/WASM прошли.
