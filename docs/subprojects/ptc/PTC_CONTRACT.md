# Контракт ПТС-ядра v1 и экспериментального подключения

## Область и API

`plugins/dsh-ptc` — самостоятельный пакет без побочной регистрации; экспериментальное подключение расположено отдельно в Postman-плагине. Экспорт: `validatePtcProfile(input)` (возвращает глубоко ограниченный неизменяемый снимок или бросает `TypeError`), `DEFAULT_LIMITS`, `MAX_LIMITS` и `createPtcRuntime()`. Runtime предоставляет `run({program, language='javascript', profile, bindings, signal})` и идемпотентный `dispose()`. Ошибки допуска и исполнения выражаются объектом результата, а не повтором программы. Каждая программа — новый процесс, новый QuickJS runtime/context. Нет persistent REPL, восстановления, повтора и edit-run. Импорт без побочных эффектов.

`bindings` — собственные свойства простого объекта, имена из проверенного `profile.tools`. Для каждого имени обязательно наличие собственной функции; лишние функции не передаются ребёнку. Таблица функций и профиль снимаются в копию до запуска. Функция получает ровно один JSON-аргумент и `{signal,runId,callId}`; `signal` — сигнал данного запуска, который прерывается при завершении. Нет глобального реестра функций и выбора Agent по модельному `agentId`. Адаптер этапов 2/4/5 строит разрешённую таблицу из фактического Agent и вызывает публичный `ctx.tools.execute` с `agent: exec.agent`, `parent: exec.token`, `rootCallId: exec.rootCallId` и сигналом вызова. Само ядро этих полномочий не подтверждает.

## Экспериментальный адаптер Harness: только Leader

Точный живой верхнеуровневый postman-leader-ptc получает обычный ptc_execute: текущая композиция, отсутствие дочернего происхождения/ненулевой глубины и ctx.agents.get(agent.id) === agent. Глобальная регистрация скрыта от остальных через pilot allow и non-Leader deny без исключений для детей; тело повторно отвергает прямой вызов. Общий preset не включает run_code/edit_run_code; production Leader, любые Worker, Secretary, Sol Worker и Bridge не получают ПТС. Модель задаёт `program`, краткое `description` с причиной остановки, обязательный `boundary`, необязательные `yield_on_success` и `language`, но не профиль/владельца.

PTC-first профиль `postman-leader-supervisor` revision 8 включает `todo_write`, `create_goal/get_goal/update_goal`, `read/grep/web_fetch`, `postman_task_prepare/postman_task_restore/postman_input_files`, `postman_bridge/postman_bridge_status/postman_bridge_list`, `postman_worker/postman_worker_interrupt/postman_worker_stop/postman_worker_list/postman_worker_compact/postman_worker_fresh/postman_secretary/postman_secretary_ledger`. При недоступности обязательных `read/grep` — явный отказ; остальные пересекаются с текущей ordinary visibility `schemas(agent)/get(name,agent)`. Leader: `maxWallMs=300000`, `maxToolCalls=256`, `quickjsMemoryBytes=67108864`, `maxTotalBridgeBytes=16777216`, `maxConcurrentToolCalls=1`. `maxOutputBytes=DEFAULT_LIMITS.maxOutputBytes=524288` (512 KiB для результата и отдельно для суммы logs), `maxMessageBytes=1048576`, depth/nodes и остальные защитные ограничения сохранены. Штатный Host ToolRuntime guard запрещает model-direct вызов этих имён только exact top-level `postman-leader-ptc` при `parent === undefined`; вложенный вызов с parent outer token идёт штатным `ctx.tools.execute` с exact Agent/rootCallId. Прямыми остаются `ptc_execute`, `skill`, `ask_user_question`, `exit_plan_mode`, `read_image`, `postman_yield`. Production `postman-leader` остаётся direct-mode без PTC; нет нового supervisor authority, Code Mode, shell, write/edit или обхода ordinary visibility. Skill v26 определяет routing и human approval до подготовки/делегирования; Worker report и Bridge READY — новые события, не polling внутри программы. Guidance сериализует только имена и параметры видимых функций; результат — компактный JSON для следующего решения Leader.

Trusted helper prelude предоставляет `ptc.expectStatus(result, allowedStatusesOrVisiblePostmanToolName)` (объект с собственным строковым status, непустой список точных непустых строк либо имя видимого prepare/Worker/interrupt/Bridge из Host-maintained success table; возвращает исходный объект либо бросает ошибку неизвестного статуса), `ptc.utf8Bytes(text)` и `ptc.jsonBytes(value)` без дополнительных tools. `readAllText`, `readMany`, `mapTextFiles` и `grepMany` доступны только при видимости соответствующих ordinary tools. Последовательные вызовы остаются внутри одного PTC исполнения; helper не обходит ToolRuntime или Worker filesystem guard.

`readAllText({file_path,page_limit?,max_bytes?,max_chars?})` допускает по умолчанию 4 MiB UTF-8 текста на файл внутри PTC; старый `max_chars` остаётся дополнительной границей совместимости. В Postman adapter внутренние страницы используют полный `ctx.fs.streamText` после успешного ordinary `read` через тот же ToolRuntime (visibility, schema, pre/approval/guard/around/body/post, исходный Agent и Worker worktree guard сохранены). Его bounded карточка и признаки усечения не меняются; raw text остаётся только в текущем внутреннем ответе. Продолжение определяется фактическим UTF-16 offset полученного фрагмента, включая часть длинной строки, с явным EOF, проверками прогресса, стабильной версии провайдера и размеров; shell и файлового кэша нет. Отказ доступа, заменённый post-policy result или невозможность продолжить не выдаются за полный текст. Legacy line-page путь standalone prelude по-прежнему проверяет номера строк и стабильный totalLines и отвергает усечение ordinary read. Это текст по линиям, не побайтное копирование: финальный newline не гарантируется. `readMany({files,page_limit?,max_bytes_per_file?,max_chars_per_file?,max_total_bytes?})` сохраняет прежний массив `{file_path,text}`, но ограничивает совокупный UTF-8 JSON с escaping и metadata (default 480 KiB с запасом для outer JSON). Явный `max_total_bytes` допускает больший внутренний массив, а не больший output.

`mapTextFiles(options, mapper)` последовательно читает файл, вызывает локальную функцию `mapper({file_path,text})` и сохраняет только её JSON-совместимый результат до следующего чтения. Те же файловые границы и byte limits, совокупный mapper JSON по умолчанию ≤480 KiB. Mapper предназначен для механического извлечения/сокращения, не скрытого модельного summarization. Возврат исходного полного `text` напрямую, во вложенном объекте/массиве или большой строковой обёртке отклоняется; пустой источник не считается нарушением. Для сырых файлов внутри программы используется `readMany`; предпочтительно механическое сокращение, но действительно нужные модели сырые данные можно вернуть в пределах штатного output. **Read large internally, return compact** — предпочтительный способ работы, не новый маленький потолок; final result ≤512 KiB, сумма logs отдельно ≤512 KiB. Результаты 40/80/150 KiB допустимы при обычных JSON limits. `grepMany({queries})` проверяет аргументы и `{matches:Array}`, не вводя отдельного retained-result byte limit. Точный размер JSON включает экранирование. `jsonBytes` отвергает holes/extra fields/accessors/toJSON/exotic data вместо молчаливого преобразования.

Архитектура Postman, этап 1, отменяет Worker PTC. Все Worker (под Leader и Sol), Secretary и Sol Worker работают direct; adapter отвергает assignment role=worker. Только exact experimental Leader получает профиль. Старые exported Worker profile/path helpers оставлены для совместимости модулей, не активируют runtime authority. Canonical skills и FAST soft 12 / hard 15 budget внедряются Host в каждом child request, включая cold resume; Worker/Secretary используют codex/gpt-6-luna/low, Sol — gpt-6.1-sol/xhigh. Полный контракт команды — plugins/dsh-postman-harness/README.md и postman/POSTMAN_BRIDGE_FLOW.md.

Среда проверки: DSH 0.1.1-rc.2, Node v24.21.0, quickjs-emscripten@0.32.0, Windows. Штатный ToolRuntime.execute(ToolExecutionInput) принимает точный Agent, opaque parent и rootCallId, проверяет видимость, аргументы, pre-execute/guard/approval/post-execute и переносит отмену; обычный внешний инструмент не держит блокировку внутренних вызовов. Сквозной тест исполняет настоящее ядро и read/grep, а также определения get_goal/web_fetch с контролируемым локальным HTTP-ответом, без модели.

Гостю передаётся только канонический публичный JSON ToolExecutionSuccess.value, не отрисованная карточка, приватные meta, execution или Agent. Ошибки диспетчера бросаются в гостевой callback. Итог содержит статус ядра, value, logs и effects. Начатые внутренние вызовы получают связанные tool/code-dispatch-start и tool/code-dispatch; зависший инструмент на остановке программы получает запись об неизвестном исходе и effects.pending, а его Promise остаётся учтён ядром без бесконечного ожидания. Эти события не являются доверенным terminal Postman.

Смена пресета/профиля, disposal либо замена Agent отзывает назначение и отменяет живой запуск. Перед передачей каждого вызова повторно проверяются поколение назначения, ревизия, живость, текущие права и отмена, включая ожидавшие вызовы; tools/change отменяет запуск при отзыве используемого права. Остановка программы не доказывает остановку уже начатого инструмента. Runtime общий на срок жизни плагина, каждый запуск создаёт новый QuickJS-процесс. Для Leader по-прежнему не включены glob/web_search/write/edit; Worker PTC имеет только названный mutation MVP profile без shell/jobs/report/read_image или privileged capabilities. Живые проверки Leader этапа 3 частичны; Stage 4 Worker live-приёмка выявила неверную файловую базу и привела к этапу 4.5. Live-проверка исправления не проводилась.


Возвращаемые формы существующих helpers явные: readAllText → string; readMany → Array<{file_path,text}>; mapTextFiles → Array<mapper JSON>; grepMany → Array<{query,result:{matches:Array}}>. Ordinary read/glob/grep возвращают объекты с lines/paths/matches, не iterable arrays. grepMany предварительно проверяет весь список запросов и форму matches, без нового отдельного retained-result byte limit. Плохая форма evidence не превращается в пустой успех.

Внутри одного исполнения читай источник/диапазон один раз и переиспользуй локальный текст для всех заранее известных проверок. Helpers уже читают страницы последовательно без повторов и не держат файлового кэша. После write/edit и при необходимости внешней свежести новое чтение проходит через ordinary tool и worktree/observation checks; между programs данные не сохраняются.

## Program-First и каноническая дисциплина

Единственный подробный обязательный protocol — [plugins/dsh-postman-harness/lib/ptc-discipline.js](../../../plugins/dsh-postman-harness/lib/ptc-discipline.js), исходный приложенный файл без переписывания. Adapter автоматически внедряет `POSTMAN_PTC_DISCIPLINE` v3 в runtime/system section exact назначенного и реально доступного Postman PTC Leader либо exact Host-admitted PTC Worker; отдельный round для чтения не требуется. Production Leader/ordinary Worker, Bridge, посторонние агенты и native DeepSeek Harness PTC/Code Mode (`run_code`, `edit_run_code`, `dsh-ptc-plus`) не получают этот capability/protocol и не изменяются.

Один model decision программирует весь безопасный детерминированный этап до следующей реальной границы. Обязательный `boundary`: `semantic_decision`, `user_input`, `external_event`, `approval_boundary`, `task_complete`. `description` поясняет, почему этап заканчивается там; Host нормализует пробелы и сохраняет первые 160 Unicode code points для диагностики. Длинная непустая служебная строка не отклоняет программу; пустая/нестроковая по-прежнему недопустима. Заранее известный переход между tool operations остаётся внутри программы с exact status validation; неизвестный результат возвращает управление модели. Полные нормативные правила не дублируются в skill/guidance.

`boundary: external_event` у Leader автоматически вызывает штатный `exec.concludeTurn()` после хотя бы одного exact accepted producer: `postman_worker → POSTMAN_WORKER_TASK_ACCEPTED`, `postman_worker_interrupt → POSTMAN_WORKER_INTERRUPT_TASK_ACCEPTED` или `postman_bridge → POSTMAN_BRIDGE_ACCEPTED`. Один `postman_task_prepare → TASK_CONTEXT_READY` producer не создаёт и WAIT не вызывает. `yield_on_success` сохранён для совместимости; отсутствие или false не отключает auto-conclude. Auto-yield применяется только для runtime `ok`, без cleanupError/abort/revocation, nested failure, `needsModelDecision:true`, pending/unknown/unsettled effects и неизвестного/refused prepare/Worker/Bridge acceptance: все принятые внутренние вызовы подтверждённо completed и коррелированы с Host по уникальному callId и имени, а не только по счётчикам. QUEUED/RUNNING принятого Bridge job — внешняя работа, не pending nested dispatch. Маркер nested conclude применяется только после полного безопасного результата программы. Обычный `concludeTurn` в AgentLoop — мягкая граница: очередь next-step продолжала тот же turn даже после маркера (реальный Bridge эпизод: Worker settled notice после уже обработанного report). Поэтому только после authoritative успешного outer `tools/result` адаптер помечает exact Leader turn; на следующем ordinary pre-step сначала выполняются все policies, затем принятые queued messages/context сохраняются в той же durable inbox, а пустой enter завершает уже concluded turn. В новом turn сообщения обрабатываются штатно, ровно один раз; при pending next-turn переносом владеет AgentLoop. Rejection/post-execute veto/revocation не обходятся. Новое внешнее событие всё ещё может немедленно открыть новый model turn — это не служебный round для yield; удаления уведомлений нет. `error`, `limit-exceeded`, отмена, failed/not-started/unknown effects не уступают ход автоматически, даже если гость перехватил вложенную ошибку. Нет нового ожидателя: тот же conclude/yield и event-driven возобновление от Worker report / Bridge READY; polling запрещён. Worker сохраняет ordinary report и не может запросить Leader auto-yield.

На каждый фактический запуск adapter пишет `postman/ptc-run` через штатный Cordis logger `postman-ptc`, **не session event**: sessionId, role, description, boundary, status, durationMs, nestedToolCalls, toolCounts, resultBytes (UTF-8 JSON value для ok, иначе 0), yieldRequested/yieldApplied, limitCode при limit-exceeded, underbatchedCandidate при одном dispatch и oversizedResultCandidate при resultBytes >64 KiB или отказе maxOutputBytes; descriptionNormalized при нормализации и yieldBlockedReason при отказе автоматического завершения. Program, аргументы, файлы и содержимое результата не записываются. Сам oversizedResultCandidate — диагностика, не enforcement; enforcement принадлежит профилю и двум сторонам runtime. Existing tool/code-dispatch events остаются. Native vocabulary не расширяется: штатной регистрации сторонних event types нет, projection registry её не заменяет. Реальный Jsonl round-trip и cold resume exact Worker после PTC проверены в двух независимых Node процессах; первый resumed request содержит PTC, discipline и max, повторное PTC исполнение успешно.

Полномочия PTC по-прежнему являются подмножеством ordinary authority агента; approval, routing, Bridge grants и Worker task worktree остаются прежними. Нового scheduler/workflow/DSL/REPL/retry/rollback/реестра нет.

## Текущая файловая политика Worker PTC

Luna и Sol используют task worktree как базу относительных файловых путей, но не как дополнительную границу доступа. Внешние абсолютные пути, `..` и ссылки передаются обычному DSH ToolRuntime и файловому провайдеру: чтение разрешено штатной политикой, запись зависит от `read-only` / `workspace-write` / `danger-full-access`. Exact Worker/Leader authority, идентичность task context и отзыв доступа, schema/visibility, observation/stale checks, Postman artifact и Git guards сохраняются. Leader ранее не ограничивался этой границей и не меняется; native Harness PTC не затронут. Ниже описаны исторические этапы 4.5/5: их дополнительное ограничение «только task worktree» отменено.

## Исторический этап 4.5: прежняя файловая граница Worker PTC (не активна)

Baseline Stage 4 live подтвердил namespace, настоящий `glob/read/grep`, продолжение Worker, адресную остановку одного из трёх и отсутствие PTC production Worker; но относительный `read` использовал session cwd (`.dsh`), а не Host-bound task worktree. Причина: штатный DSH `read` использует `agent.session.header.cwd`, `glob/grep` запускают ripgrep из того же cwd; `ctx.tools.execute` переносит исходного Agent и не принимает отдельного scoped root. Mutation-этап остановлен до устранения этой границы.

Только Worker PTC `read/glob/grep/write/edit`: непосредственно перед вложенной диспетчеризацией adapter сверяет exact Agent/Leader через существующий `liveSlot` и получает тот же текущий task context по идентичности объекта; программа не может указать root. Файловые аргументы реальных схем (`read/write/edit.file_path`, `glob/grep.path`, включая отсутствие search path) разрешаются от `context.worktree`, сравниваются с canonical root через OS `path.relative` и проверяются `realpath` существующего пути либо ближайшего существующего предка. Absolute outside, нормализованный `..` escape и directory junction/symlink outside отвергаются до `ctx.tools.execute` с явной диагностикой. При потере или замене context следующий filesystem call старой программы отвергается без переключения на новый root. Вызов внутри границы по-прежнему исполняется обычным ToolRuntime с исходным Agent, parent token и rootCallId. Search tools запускают ripgrep без `--follow`; проверено на directory junction fixture, что рекурсия не выходит за root.

Будущий несуществующий target проверяется через canonical существующего предка, включая реальный Worker PTC write в тестах. Обычные Worker tools и Leader PTC path semantics не меняются. Этот Host-side guard не является OS sandbox и не закрывает конкурентную замену ссылок между проверкой и открытием.

## Исторический этап 5: граница mutation и Stage 5A (не активны)

Stage 5 реализован: Host связывает filesystem mutation с текущим `context.worktree` от exact trusted Worker → Leader → task context binding, а не с session cwd или заданным программой root. Перед guard и непосредственно после его async проверки, до dispatch, сверяются identity того же task context, exact Worker и текущие права; после settlement действует общая revocation logic (`PTC_ACCESS_REVOKED`). Absolute outside, нормализованный `..` escape и существующий symlink/junction escape (в том числе у предка future target) отклоняются до mutation dispatch с failed effect и без побочного эффекта. Далее неизменённые content/old_string/new_string/replace_all поступают через `ctx.tools.execute` с исходным Worker Agent, parent token, rootCallId и subCallId. Штатные DSH schemas, права, fs-observation-policy, createIfAbsent/replaceIfVersion, stale handling, literal edit и отмена принадлежат ToolRuntime/провайдеру. `PTC authority ⊆ ordinary Worker authority`: скрытый ordinary write/edit недоступен PTC. Нет транзакции, rollback или автоматического retry; уже completed effect сохраняется при последующей ошибке программы, запущенный, но не settled Host call остаётся pending/outcome unknown.

Эта Host-side граница защищает от обычных ошибок и обходов пути, но не является OS-level sandbox против другого конкурентно враждебного ordinary Worker той же пользовательской сессии, которому отдельно доступны shell и штатные filesystem tools. Для MVP физическая невозможность перенаправления PTC mutation таким Worker через перестановку filesystem namespace **не требуется**: Stage 5A — deferred / not required for MVP, не PASS. `dsh-fs-sandbox` также не принимается за абсолютную границу для этой угрозы. Если live acceptance или будущая модель доверия потребует изоляции недоверенных Worker друг от друга, rooted/descriptor mutation либо sandboxing ordinary Worker составят отдельный security project. Исследовательский Windows/Node prototype на rooted HANDLE и `NtCreateFile`-подобных операциях не подключался к `ptc-adapter`: pinning parent HANDLE закрыл конкретную старую junction-подмену после закрепления, но остались доверенное закрепление identity task root до возможной подмены и атомарная условная замена directory entry только при прежней identity/version existing target. 14/14 исследовательских проверок завершились согласно ожиданиям, часть из них намеренно воспроизводила эти ограничения; это не доказательство Stage 5A и не product implementation.

## Профиль v1

Чистый JSON с ровно пятью ключами: `schemaVersion:1`, `id` (ASCII буква/цифры/дефис, до 64), `revision` (1…1000000), `tools` (до 64 имён, включая пустой массив), `limits` (ровно все перечисленные ниже поля). Имя функции: `[A-Za-z_][A-Za-z0-9_]*`, до 64 символов; дубли, wildcard, `__proto__`, `prototype`, `constructor` запрещены. Размер канонической JSON-копии профиля ≤8192 байт. Неправильные типы, лишние/отсутствующие поля, NaN/Infinity/строковые числа и значения вне диапазона отвергаются. Профиль не содержит код, роль, системный промпт, модули, исполняемый путь, окружение или навыки.

Значения по умолчанию относятся к лабораторному стенду, не обоснованы как production-пределы агентных сетевых функций. Числа — безопасные целые; минимум в таблице, максимум сервисного владельца и значение примера:

| Поле | Единица | Мин | Пример | Макс |
|---|---:|---:|---:|---:|
| maxProgramBytes | UTF-8 байт | 1 | 262144 | 262144 |
| maxWallMs | мс календарного времени | 100 | 120000 | 300000 |
| quickjsMemoryBytes | байт QuickJS heap | 8388608 | 33554432 | 67108864 |
| maxStackBytes | байт QuickJS stack | 65536 | 524288 | 1048576 |
| maxToolCalls | вызовов | 0 | 64 | 256 |
| maxConcurrentToolCalls | вызовов | 0 | 4 | 8 |
| maxQueuedToolCalls | вызовов | 0 | 16 | 32 |
| maxMessageBytes | байт полезного JSON-кадра | 1024 | 1048576 | 1048576 |
| maxTotalBridgeBytes | байт обоих направлений с заголовками | 2048 | 8388608 | 16777216 |
| maxOutputBytes | байт результата и логов отдельно | 0 | 524288 | 524288 |
| maxLogEntries | записей | 0 | 256 | 256 |
| maxValueDepth | уровней JSON | 1 | 32 | 32 |
| maxValueNodes | узлов JSON | 1 | 10000 | 10000 |

Нуль разрешён только как отсутствие функций, очереди, логов или вывода. Параллельность ≤ общего числа вызовов; при разрешённых вызовах она положительная; очередь ≤ общего числа. Вывод+2048 ≤ кадра, программа+8192 ≤ кадра, кадр+4 ≤ бюджета. Значения за пределом не повышаются автоматически. На общем Postman runtime одновременно максимум 10 процессов (11-й — `limit-exceeded/maxProcesses`, освобождённый слот используется следующим запуском), без очереди запусков; старт ≤3 с (или меньший срок профиля), подтверждение остановки: мягкая остановка ≤750 мс, затем принудительная ≤750 мс. Неразрешённые Host Promise ограничены 64 на экземпляр сервиса, включая результаты завершённых запусков.

## Язык и граница исполнения

`javascript` по умолчанию — тело асинхронной функции с `await` и явным `return` JSON. `typescript` — только удаляемые аннотации через Node `stripTypeScriptTypes({mode:'strip'})` внутри дочернего процесса; синтаксис, требующий трансформации, не поддержан. Экспорт и модули не поддержаны. Диагностика в файле `ptc-program.js` смещена на строку обёртки (исходная строка программы +1); TypeScript wrapper также прибавляет строку. `undefined` не JSON и даёт `invalid-output`, `null` допустим.

Ребёнок — фиксированный Node entry `src/executor.mjs`, запущенный без shell, без наследования Node execArgv и с минимальным окружением, cwd — отдельный временный каталог. В QuickJS нет Host `process`, `require`, `fetch`, сети, файлов, Node-таймеров, std/os и загрузчика модулей. Доступны стандартные вычисления JS, `tools.<имя>(json)` и ограниченный `console`. `Function` внутри QuickJS не переводит вычисление в Node. QuickJS-движок закреплён `0.32.0`; обычные функции возвращают QuickJS Promise, `executePendingJobs()` обслуживает очередь, Asyncify не используется.

## Протокол и завершение

Один запуск — один `runId`, числовые последовательные `callId`. Версия `v:1`; кадр — 4-байтовая big-endian длина, затем UTF-8 JSON. Сообщения: parent `start` → child `ready` → `call` / parent `reply` / `log` → child `done`. Принимающая сторона проверяет размер до JSON.parse, UTF-8, версию, направление, ID, поля, порядок и общий бюджет. Сторонний/повторный вызов отвергается до Host-функции; собственные права повторно проверяются на каждом `call`. Обратное давление учитывается записью с callback; ошибка/закрытие самого потока отклоняет ожидающие записи и завершает запуск, не аварийно завершая родителя. Служебная оболочка проверяется отдельным фиксированным бюджетом глубины/узлов, а `arg`/`value` — пользовательским бюджетом профиля; размер полного кадра проверяется после JSON-экранирования. Совокупный бюджет включает кадры обоих направлений. `stderr` имеет отдельный предел 4096 байт. Служебный отказ при переполнении канала может завершиться закрытием без терминального кадра; родитель сохраняет свою первичную причину.

Данные — только JSON с ограничением байт, глубины, узлов; нет BigInt, undefined, функций, циклов, getters/toJSON, специальных объектов, опасных ключей и молчаливого преобразования нечисловых чисел. Один descriptor-only codec `dsh-ptc/json` используется на Host, в приватном сериализаторе QuickJS и `ptc.jsonBytes`; он сериализует проверенную копию, не исполняя getters/toJSON. Диагностика содержит только путь от `value`, тип и причину (например, `value.files[2].testEvidence: undefined is not JSON-compatible.`), без значений полей. Несовместимый final JSON даёт `invalid-output`; несовместимые аргумент/log дают `runtime-error/invalid-json`; настоящие byte/depth/node нарушения — `limit-exceeded` с `maxMessageBytes`, `maxOutputBytes`, `maxValueDepth` или `maxValueNodes`. Путь и причина проходят через done/outer результат, effects ранее выполненных операций сохраняются, автоматического повтора нет. Родитель проверяет гостевое значение снова тем же codec. Логи — массив JSON-строк, не бесконтрольный вывод в stdout.

Результат `{status, value?, error?, logs, effects, cleanupError?}`. Статусы v1: `ok`, `invalid-input`, `syntax-error`, `runtime-error`, `invalid-output`, `protocol-error`, `limit-exceeded` (код поля), `cancelled`, `process-error`, `cleanup-error`, `unawaited-calls`. Это локальные статусы ядра, не Postman. `effects` — фактический снимок принятых вызовов с `completed`, `failed`, `pending`; принятый, но не запущенный callback отмечается `not-started` и не входит в `pending`. Превышение бюджета ответа Host-функции завершает запуск и закрывает допуск новых вызовов, даже если гостевая программа перехватывает ошибки. `ok` не совмещается с ошибкой очистки; при прежнем сбое первичный статус сохраняется. Ошибка после выполненной функции не откатывает её эффект. Результат программы с незавершённым callback — `unawaited-calls`, не полный успех.

Отмена до старта не создаёт процесса. Внешний календарный таймер охватывает всё, включая TypeScript; QuickJS interrupt — вспомогателен. Abort/dispose закрывает новые вызовы, отменяет сигнал начатых, не ожидает некооперативные Promise бесконечно, завершает ребёнка и сохраняет снимок эффектов. Поздние отклонения обрабатываются, но не доставляются повторно. Повторный запуск не повторяет уже выполненные функции. `kill()` не является подтверждением выхода — ожидается событие `close`; при недоказанной остановке `cleanupError` и занятый слот сохраняются, а успех не объявляется. При аварии самого родителя эта гарантия не распространяется на Host-вызовы и дочерний процесс. Синхронный блокирующий доверенный callback остаётся блокирующим на основном потоке.

## Пределы защиты и среда

QuickJS ограничивает полномочия программы, отдельный процесс ограничивает последствия сбоя исполнителя. Это не доказанный OS sandbox: нет отдельного пользователя, контейнера или защиты от уязвимости QuickJS/Node. Предел памяти QuickJS/WASM не является строгим пределом всего процесса ОС/V8. Тесты на пользовательской Windows подтверждают функциональность и ограниченные превышения, но не доказывают containment произвольного native exploit. При запуске из установленной копии требуются все пакетные `src/` и транзитивный WASM из lockfile. Сетевой загрузки при `run()` нет.
