# Пробуждение Почтальона через GitHub Issue

## Назначение

Это отдельный инфраструктурный этап, а не реализация всего Почтальона:

```text
Web ChatGPT
  → изменение тела GitHub Issue
  → событие issues.edited
  → GitHub Actions
  → self-hosted Windows runner с меткой postman
  → postman/github-wakeup.ps1
  → %LOCALAPPDATA%\DSH\Postman\signals\REQ_*.json
```

Механизм не запускает содержимое Issue и не использует частый REST-опрос.

## Строгий протокол Issue

Используется только заголовок, начинающийся ровно с `POSTMAN `, с одним выбранным форматом:

```text
POSTMAN REQ_<id>
```

`<id>` допускает от 1 до 80 символов `A-Z`, `a-z`, `0-9`, `_` и `-`; служебные слова `POSTMAN` и `REQ_` должны быть написаны именно в таком регистре. Полный шаблон:

```text
^POSTMAN (REQ_[A-Za-z0-9_-]{1,80})$
```

Тело Issue состоит из служебного заголовка и ответа. Между ними обязательна пустая строка:

```text
request_id: REQ_PROBE_001
status: WAITING
protocol_version: 1

```

После завершения Web ChatGPT заменяет заголовок и добавляет ответ:

```text
request_id: REQ_PROBE_001
status: READY
protocol_version: 1

Полный ответ Web ChatGPT.
```

Служебный заголовок может содержать только `request_id`, `status` и `protocol_version`. `request_id` проверяется регулярным выражением `^REQ_[A-Za-z0-9_-]{1,80}$`; версия должна быть `1`; статус — `WAITING` или `READY`. Решение о пробуждении принимается только по полю `status` в заголовке, поэтому строка `status: READY` внутри ответа не является сигналом.

Заголовок Issue и `request_id` тела должны совпадать. Номер Issue хранится отдельно и никогда не используется как `request_id`.

## Workflow и runner

Workflow [`postman-wakeup.yml`](../.github/workflows/postman-wakeup.yml) слушает только `issues: edited`. Быстрый фильтр проверяет заголовок, наличие текста `status: READY` и отсутствие `pull_request`. Окончательная проверка всегда выполняется локальным обработчиком.

Runner должен быть зарегистрирован для `AndrewVerhoturov1/dsh-workspace` с системными метками `self-hosted`, `Windows`, `X64` и пользовательской меткой `postman`. Runner размещается вне рабочего дерева, предпочтительно в `C:\Users\andre\.postman-runner`. Обработчик вызывается только как известный файл репозитория; никакая команда из Issue не передаётся PowerShell.

## Локальный сигнал

При корректном событии обработчик атомарно создаёт или заменяет:

```text
%LOCALAPPDATA%\DSH\Postman\signals\REQ_PROBE_001.json
```

Запись сначала создаётся во временном файле в той же папке, затем перемещается или заменяется атомарной операцией. Пример содержимого:

```json
{
  "protocolVersion": 1,
  "requestId": "REQ_PROBE_001",
  "issueNumber": 5,
  "repository": "AndrewVerhoturov1/dsh-workspace",
  "status": "READY",
  "response": "Полный ответ",
  "githubUpdatedAt": "2026-08-27T20:00:00Z",
  "receivedAt": "2026-08-27T20:00:02.0000000+00:00",
  "bodySha256": "...",
  "deliveryKey": "..."
}
```

Ответ является данными. Он сохраняется как текст и не исполняется.

## Идемпотентность

Ключ доставки строится из `request_id`, номера Issue, `issue.updated_at` и SHA-256 исходного тела. Повтор того же события читает существующий сигнал и возвращает `SIGNAL_DUPLICATE`, не создавая второй логический результат. При новом содержимом той же Issue используется тот же файл `REQ_<id>.json`, но его содержимое безопасно заменяется атомарно. Внутри процесса записи защищены именованной локальной блокировкой.

## Границы безопасности

- не используются `Invoke-Expression`, `iex`, `eval` и запуск команд из Issue;
- не вызывается `Start-Process` с пользовательским текстом;
- принимаются только известные поля события и три поля служебного заголовка;
- события другого репозитория, pull request, повреждённый JSON, неверный номер Issue, неверный `request_id`, несовпадающий заголовок и тело или неверная дата отклоняются;
- unrelated Issue и заголовки, не начинающиеся с `POSTMAN `, игнорируются;
- никакая интеграция напрямую с памятью агента или внутренней базой DSH не выполняется.

## Проверка

Локальные проверки обработчика:

```powershell
pwsh -NoProfile -File .\postman\test-github-wakeup.ps1
```

Проверяются успешный READY, WAITING, обычная Issue, неверный `request_id`, повреждённый заголовок, ложный READY в ответе, pull request, несовпадение идентификаторов, повтор события и обновление версии ответа.

Synthetic E2E выполняется только после публикации workflow в `main`:

1. создать отдельную Issue с заголовком `POSTMAN REQ_PROBE_001`;
2. установить тело в WAITING-вариант выше;
3. изменить её тело через GitHub API или `gh` на READY-вариант выше;
4. не запускать `github-wakeup.ps1` вручную;
5. дождаться запуска `Postman Wakeup` и проверить в Actions run id, job id, runner, время начала, время завершения и результат;
6. проверить файл в `%LOCALAPPDATA%\DSH\Postman\signals\` и совпадение ответа;
7. повторить идентичное изменение или rerun и убедиться, что второй логический сигнал не создаётся;
8. вернуть Issue в WAITING и удалить сигнал `REQ_PROBE_001.json` перед пользовательской проверкой Web ChatGPT.

В текущем этапе штатный адаптер возобновления агента не подключается. Если в Harness не найден документированный API/очередь, следующий слой обозначается как `HARNESS_WAKEUP_ADAPTER_PENDING`; durable local signal остаётся точкой пробуждения.
