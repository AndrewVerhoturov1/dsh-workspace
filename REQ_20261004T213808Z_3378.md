## User intent

Исследование для Carcassonne Web, этап 1 «Система и готовый набор тайлов». Пользователь утвердил этот первый шаг до архитектуры и реализации. Нужна полноценная браузерная hot-seat игра в будущем, но сейчас только формальная система полного базового набора тайлов и Tile Lab. Изучи первичные правила базового Carcassonne и надёжные каталоги тайлов. Не реализуй дополнения и не включай River, Inns & Cathedrals, Traders & Builders, Abbot только потому, что они бывают в коробке. Самостоятельно установи состав базовых изданий, полный список уникальных типов, количества каждого, начальный тайл, совместимость сторон, дороги, города, поля, монастыри, щиты и их значение, внутреннюю топологию и структурно зависимые допустимые места миплов. Сравни существенные различия изданий: количества, иллюстрации против логики, реальные изменения соединений и полей, правила определения полей и финального подсчёта, если отличаются. Мы не вправе молча выбрать издание: выдай понятное сравнение для пользователя и рекомендуемые варианты, но не фиксируй выбор. Для кандидатов в базовые наборы дай проверяемые таблицы типов и экземпляров, сумму, учёт начального тайла и исключённых дополнений. Обязательно разберись в независимых дорогах на перекрёстках/деревнях, раздельных городах, соединённых и разделённых полях, контактах полей с городами, щитах и монастырях. Сформулируй необходимые будущей игре свойства логической модели без окончательного TileSpec, рендера или художественной геометрии. Источник истины — логика, не коммерческая картинка. Для каждого важного утверждения/таблицы укажи URL, источник и уровень подтверждения; неполное, противоречивое или недоступное свидетельство обозначь явно. Нельзя выдавать визуальное угадывание за подтверждённую топологию. Оригинальную коммерческую графику не копировать в будущие ассеты. Достаточный результат: исследование с источниками, сравнение изданий, точный подтверждённый каталог там, где он установлен, и явные вопросы/неопределённости для следующих ворот. Ответ нужен содержательный и по-русски, для дальнейшего представления в браузере. Не утверждай прохождение автоматических тестов или приёмки. Работа строго по принципам https://github.com/AndrewVerhoturov1/dsh-workspace/blob/main/docs/workflow/TASK_CONTRACT.md : только текущая задача, минимально достаточная работа, без расширений и соседних задач, проверки пропорциональны, фактические результаты отличать от планов, после достаточного результата остановиться.

## Execution contract

- Этот task-файл self-contained; выполнить `User intent` буквально.
- `repository` и `base_commit` — только transport/correlation metadata.
- GitHub использовать только как READ source, если он действительно нужен для user intent.
- Не commit, не push, не открывать PR/issues и не изменять GitHub.
- PostmanAsk ожидает текстовый transport result: не создавай и не возвращай result ZIP/attachment.
- Если раздел Input files выше указывает native POSTMAN_INPUT_<REQ>.zip, это обязательный input текущей задачи и его нужно получить/прочитать по Input retrieval contract.

## Answer author discipline

- External Web — исследователь и автор итогового ответа; выполнить `User intent` буквально и в его границах.
- Исследовать достаточно для надёжного ответа, но не превращать вопрос в аудит всей темы; предпочитать качество релевантных источников их количеству.
- Не повторять поиск без причины и не уходить в соседние темы.
- Не создавать repository changes, patch, implementation package или ZIP; результат — только текст.
- После достаточного ответа остановиться.

## Result contract

- Сначала полностью выполнить задачу и подготовить итоговый непустой текст.
- Финальный assistant response должен содержать ровно один BEGIN marker и один END marker текущего request_id.
- До BEGIN и после END не должно быть другого видимого текста.
- Между markers поместить весь итоговый ответ; Markdown и code blocks внутри разрешены.
- Не повторять transport markers внутри тела ответа.
