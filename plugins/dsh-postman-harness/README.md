# dsh-postman-harness

Плагин внутренней почты Harness для этапов M1–M6.

Плагин создаёт отдельного LLM-backed агента POSTMAN с постоянным идентификатором `postman-harness-session`. После внедрения службы `sessionPersistence` он сначала проверяет сохранённую запись через `inspect()`, восстанавливает существующую сессию через `ctx.agents.resume()`, а при точной ошибке «сессия не найдена» создаёт её через `ctx.agents.create()`. Другие ошибки persistence не переводятся в создание пустой сессии. Для сообщений используются только публичные API `ctx.agents.get()` и `Agent.followup()`. Внешние почтовые ящики, SQLite, HTTP, UI Automation и браузерная автоматизация не используются.

Для M1–M3 сохраняется ограниченная таблица `message_id` старого probe-протокола. Для M4–M6 используется `PostmanRuntime` на встроенном `node:sqlite`: `%LOCALAPPDATA%\DSH\Postman\postman.db` и `logs\postman.jsonl`. `postman_async_send` атомарно создаёт `MSG_*` и `REQ_*`, получает владельца из `exec.agent.id` и сразу возвращает `POSTMAN_ACCEPTED`. POSTMAN создаёт отдельную GitHub Issue и отправляет delivery-contract через существующий ChatGPT Desktop bridge в режиме подтверждения отправки. READY из `postman/github-wakeup.ps1` поступает через durable signal и `markExternalReady()`, после чего Runtime будит POSTMAN и маршрутизирует результат по сохранённому `origin_agent_id`.

Инструмент `postman_runtime_synthetic_ready` доступен только при `DSH_POSTMAN_ALLOW_SYNTHETIC_READY=1`; в обычном режиме он не регистрируется. Подробности M6 описаны в [документации GitHub Integration](../../docs/postman-github-integration-m6.md) и [плане проверок](../../docs/postman-github-integration-m6-tests.md). Общая схема и граница гарантии exactly-once остаются в [документации асинхронной маршрутизации](../../docs/postman-async-routing.md).
