# dsh-mobile («Рядом» v6)

Мобильный Web-интерфейс для установленной DSH 0.1.1-rc.2, без второго сервера, новой авторизации или замены настольного интерфейса. Из принятого v6 перенесены компактные чаты, создание, переписка, Task, вопросы, результаты и действия; реальных данных макет не содержит.

## Сборка и тесты

В корне репозитория:

    node plugins/dsh-mobile/scripts/build.mjs
    node --test plugins/dsh-mobile/tests/*.test.mjs

Внутри каталога плагина: npm run check.

Сборка не требует новых зависимостей: создаёт lib/index.js и lib/client.js. Браузерная регистрация использует штатный загрузчик версии rc.2 и установленный React.

## Активация в фактическом Web-профиле — только отдельным разрешённым этапом

**В этой задаче действующая DSH не изменялась.** Проверен штатный маршрут установленного CLI 0.1.1-rc.2: `dsh plugin --profile web add` вызывает `pnpm add` в каталоге `$DSH_HOME/profiles/web`, затем автоматически согласует список `dsh.profile.bundles` по `dsh.bundle.patch`. Глобальный npm-пакет DSH переустанавливать не требуется.

1. После публикации Worker разместить собранный плагин в используемом основном дереве, например `C:/Users/Andrew/.dsh/plugins/dsh-mobile` (не в task worktree).
2. Отдельно согласовать выполнение команды на пользовательском ПК:

       dsh plugin --profile web add "link:C:/Users/Andrew/.dsh/plugins/dsh-mobile"

   Команда изменяет зависимости и bundle-слои пользовательского профиля; здесь **не выполнялась**. Для другого `DSH_HOME` указать полный путь к его опубликованному плагину. Не нужно редактировать `profiles/web/package.json` глобальной npm-установки.
3. Применение обновлённого профиля к уже работающему Host потребует отдельного разрешения. Не запускать второй GUI4173.
4. Открывать `/mobile` на существующем доступном Web Host: `GET /mobile` → `302 /?mobile=1`. Без `mobile=1` десктоп не изменяется. Сетевой доступ Android/VPN здесь не настраивался.

Основание: установленные `dsh/lib/bin.js`, `dsh/lib/plugin-*.js` и `dsh/lib/profile-boot-*.js`. Личные настройки и реальный профиль пользователя не читались.

## Поведение и соответствие API

* Список, поиск и группы: службы sessions.list, workspaces.list и sessions.search (последний зависит от включённого индекса сообщений на Host).
* Создание: sessions.create(agentPreset + workspaceId или cwd), затем до первого сообщения sessions.selectModel(provider, model, reasoningEffort) и sessions.rename. «Без проекта» не регистрирует Workspace; Host всё равно назначает свой рабочий cwd.
* Переписка, текущий поток, старая история: готовые Session bindings с getSnapshot и loadOlder, переподключение штатного DSH. Нет дополнительного WebSocket или самостоятельного reconnect.
* Отправка: session.prompt с queue или steer. Неизвестный результат отправки не повторяется автоматически. Остановка: session.cancel или subagents.interrupt; эти операции не гарантируют завершения всех фоновых задач. «Продолжить» отправляет новый запрос.
* Вопросы: PendingWait.respond с исходным rpcId и полным набором ответов, без подмены вопроса обычным сообщением.
* Task: полные дочерние каталоги, рекурсивное дерево, переход к прямому родителю, режим только чтения для one-shot. Повторный запрос continuable идёт через subagents.prompt.
* Модель и размышления: `sessions.models`/`sessions.selectModel` для обычных сессий. Установленный Host применяет новый выбор к конкретному Agent и **также пытается сохранить его как новый default**; полной изоляции общих предпочтений модельного провайдера этот API не гарантирует.
* **Управление дочерними агентами исключено из области этой реализации по явному решению пользователя.** Не добавляются parent-owned model/effort controls или `/compact` для child Session и не расширяется Host API. Обычные чаты сохраняют доступные им выбор модели/размышления и `/compact`; действие адресуется только выбранной сессии и не перенаправляется в root или child обходным путём.
* `/compact` обычного чата: `session.command('/compact')`; контекст — реальная проекция `contextPressure`, отсутствие значения `—`.
* Архив: штатный archiveSession не удаляет историю и не останавливает Agent. Возврат — POST /mobile/api/unarchive, который удаляет только выбранный ID из общего архивного набора через сериализованные методы установленного WorkspaceRegistry. Другие записи и привязки не меняются.
* Результаты: Markdown как React-текст (без опасного HTML); HTML-предпросмотр в iframe с sandbox и дополнительной CSP sandbox на прямом URL; изображения/PDF ограниченного размера; внешние HTTP(S) ссылки.
* Перезапуск: подтверждение пользователя, существующий POST /api/dsh-restart. HTTP 202 означает только принятие запроса. Не объявлять успех по одному 202 или переподключению.

## Безопасность файлов и сети

Для папок разрешены только уже зарегистрированные Workspace корни и их канонические подкаталоги. GET /mobile/api/list и GET /mobile/project/<workspaceId>/<relative-path> проверяют идентификатор зарегистрированного Workspace, каждую часть пути через lstat, итог через realpath. Запрещены .., символические ссылки, скрытые/служебные каталоги и распространённые пути с секретами. Только разрешённые форматы файлов до 2 МиБ. Не создаётся whole-disk picker.

Сетевой фильтр воспроизводит существующие Host/Origin проверки установленной rc.2; это не аутентификация пользователя. Не публиковать Host в недоверенную сеть. Tailscale, VPN и настройка удалённого доступа — отдельная операция.

Android localhost — это телефон, а не Windows Host. Мобильный интерфейс явно отклоняет ссылки localhost для внешнего предпросмотра, не поднимает произвольный прокси. Для сайта нужен конкретный доступный Android частный HTTP(S) адрес; ссылка открывается напрямую.

## Границы приёмки

Unit-тесты с синтетическими данными и проверка установленного rc.2-контракта не равны пользовательскому Host/Android PASS. Реальная мобильная приёмка возможна только после отдельного разрешённого развёртывания. Тесты не запускают model calls и не требуют credentials.
