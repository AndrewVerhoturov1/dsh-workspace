# Политика репозитория

Этот документ задаёт обязательные правила работы с Git и GitHub в `dsh-workspace` для людей и агентов.

Цель политики — не допускать накопления временных веток, смешивания независимых задач, случайной потери экспериментов и постоянного загрязнения рабочего дерева локальными данными.

## 1. Единственная постоянная ветка

`main` — единственная долгоживущая рабочая ветка репозитория.

Любая другая ветка считается временной и должна закончить жизнь одним из трёх способов:

1. полезная и проверенная работа: `PR → squash merge → удалить ветку`;
2. незавершённая или отклонённая работа, имеющая историческую ценность: `annotated archive tag → закрыть PR без merge → удалить ветку`;
3. ненужная работа без исторической ценности: удалить ветку после проверки отсутствия уникальных нужных данных.

Ветки нельзя использовать как постоянные архивы, резервные копии или хранилище «на всякий случай».

## 2. Обязательная проверка перед созданием любой новой ветки

Перед созданием **любой** новой ветки агент или разработчик обязан выполнить проверку состояния репозитория.

Минимальная проверка должна включать:

- текущую локальную ветку и `HEAD`;
- все локальные ветки;
- все фактические ветки `origin`;
- открытые pull request, если они относятся к текущей работе;
- рабочие деревья (`git worktree`), чтобы не удалить используемую ветку;
- наличие незавершённых временных веток предыдущих задач.

Рекомендуемые команды локальной проверки:

```bash
git status --short --branch
git branch --show-current
git rev-parse HEAD
git for-each-ref refs/heads --format="%(refname:short)|%(objectname)|%(upstream:short)|%(upstream:track)"
git ls-remote --heads origin
git worktree list --porcelain
```

Если кроме `main` обнаружена временная рабочая ветка, **новую ветку создавать запрещено до решения её судьбы**.

Агент обязан:

1. остановить создание новой ветки;
2. объяснить пользователю, какая временная ветка осталась и что в ней находится;
3. предложить правильный способ завершения:
   - проверить и слить через PR;
   - сохранить точным `archive/*` tag и удалить ветку;
   - удалить как уже поглощённую или ненужную после доказательной проверки;
   - оставить её активной и продолжить текущую задачу вместо создания новой;
4. дождаться решения пользователя, если выбор не следует однозначно из ранее утверждённого плана.

Запрещено создавать новую ветку только потому, что старая «пока не мешает».

### Условие допуска к созданию новой ветки

Новая ветка разрешена, когда одновременно выполнено следующее:

- `main` синхронизирован с ожидаемым `origin/main`;
- нет незакрытых временных веток предыдущих задач либо пользователь явно решил их оставить;
- существующие открытые PR не создают неоднозначности о том, где должна продолжаться работа;
- локальные пользовательские изменения обнаружены и не будут затронуты;
- новая ветка создаётся от заранее проверенного commit текущего `main`.

## 3. Одна задача — одна ветка

Каждая ветка должна иметь одну чёткую цель.

Нельзя смешивать в одной ветке:

- независимые исправления;
- эксперимент и production-реализацию;
- крупную документацию и несвязанное изменение runtime;
- dependency repair и функциональную разработку «заодно».

Если во время работы обнаружена отдельная проблема, которая не блокирует текущую задачу, её нужно зафиксировать и выполнить позже в отдельной ветке.

## 4. Новая задача начинается от актуального `main`

Нельзя использовать старую feature/experiment ветку как основу новой независимой задачи.

Перед началом новой задачи:

1. завершить судьбу предыдущей временной ветки;
2. проверить актуальный `main`;
3. создать новую ветку от точного проверенного `main`.

Запрещены цепочки вида:

```text
feature/x
→ feature/x-fix
→ feature/x-v2
→ feature/x-final
```

Если направление разработки изменилось принципиально, сначала нужно закрыть или архивировать старую работу, затем начать новую ветку от `main`.

## 5. Один milestone — один PR

Законченный milestone не должен оставаться в ветке в ожидании следующего milestone.

Правильная схема:

```text
main
→ feature/p0
→ PR
→ squash merge
→ удалить feature/p0
→ feature/p1 от нового main
```

Это сохраняет `main` как последовательность проверенных этапов и не создаёт долгоживущих рабочих веток.

## 6. Ограничение активных implementation-веток

Для одного направления разработки обычно должна существовать не более чем одна активная implementation-ветка.

В частности, для Postman по умолчанию допускается:

```text
main
+
одна активная postman/* implementation branch
```

Вторая implementation-ветка того же направления создаётся только после явного решения, зачем необходима параллельная работа.

## 7. Эксперименты

Экспериментальные ветки используют префикс:

```text
exp/*
```

Эксперимент обязан закончиться решением.

Если эксперимент успешен:

- полезная реализация оформляется как нормальная проверяемая работа и попадает в `main` через PR;
- экспериментальная ветка удаляется.

Если эксперимент не становится production-кодом, но имеет историческую ценность:

- создаётся **annotated tag** вида `archive/*` на точный commit SHA;
- проверяется локальный и удалённый peeled target тега;
- PR закрывается без merge, если он существовал;
- экспериментальная ветка удаляется.

Если ценности нет — ветка удаляется после проверки.

## 8. Архивы — только tags, не branches

Исторические снимки сохраняются annotated tags вида:

```text
archive/<описание>-YYYY-MM
```

Архивный tag должен указывать на точный commit SHA и после публикации проверяться на `origin`.

Архивные tags нельзя переписывать force-операциями.

После доказанного архивирования исходная временная ветка должна быть удалена.

## 9. Pull request

Функциональные изменения попадают в `main` через PR, если пользователь явно не разрешил отдельное административное изменение напрямую в `main`.

Предпочтительный способ объединения коротких feature/milestone веток — `squash merge`.

После успешного merge head-ветка должна быть удалена сразу. Рекомендуется держать включённым GitHub-параметр автоматического удаления head branches после merge.

Закрытый без merge PR не должен оставлять бессрочно активную ветку: её нужно архивировать или удалить по правилам выше.

## 10. `main` — известная рабочая точка старта

`main` должен оставаться состоянием, от которого безопасно начинать следующую задачу.

Нельзя переносить в `main`:

- эксперимент с известным blocker;
- временные diagnostics dumps;
- локальные пользовательские настройки;
- зависимости, состояние которых не проверено;
- незавершённый transport/runtime только для сохранения истории.

Перед merge implementation PR необходимо как минимум проверить относящиеся к изменению тесты, `git diff --check` и отсутствие случайно добавленных секретов или локальных данных.

## 11. Локальные данные не являются исходным кодом

Пользовательская конфигурация, runtime state, attachments, browser state, журналы, результаты тестовых прогонов и diagnostics не должны попадать в commits без отдельной явной причины.

Особенно защищать:

- `settings.yaml` — локальное пользовательское состояние, пока пользователь явно не решил иначе;
- `attachments/`;
- browser/Playwright state;
- логи и `.jsonl` результатов;
- временные `.tmp-*` файлы;
- локальные handoff/диагностические материалы.

Агент не имеет права автоматически очищать такие данные ради «чистого `git status`».

Долгосрочная цель — физически отделять runtime/user data от Git working tree либо помещать их в явно игнорируемое локальное пространство.

## 12. Обязательная preflight-проверка перед изменениями

Перед существенными Git-изменениями агент обязан зафиксировать:

```bash
git status --short --branch
git branch --show-current
git rev-parse HEAD
git rev-parse main
```

Для операций с ветками дополнительно проверяются локальные и удалённые refs и `git worktree`.

Если обнаружены посторонние локальные пользовательские изменения, они должны быть сохранены без автоматического `stash`, `restore`, `reset` или commit.

## 13. Запрещённые destructive-операции по умолчанию

Без явного разрешения пользователя запрещены:

```text
git reset --hard
git clean
git push --force
git push --force-with-lease
git gc / git prune как часть обычной уборки
git branch -D для непроверенной ветки
перезапись существующего archive tag
```

Force deletion ветки допустим только в узкой подтверждённой cleanup-операции, когда уникальная работа доказанно сохранена или patch-equivalent уже находится в `main`.

## 14. Правило для агентов: не размножать ветки

Один агент в рамках одной задачи не должен самостоятельно создавать каскад новых веток.

Если текущая ветка оказалась неверным направлением:

1. остановить работу;
2. определить, что из неё нужно сохранить;
3. предложить пользователю merge/archive/delete;
4. только после решения выполнить обязательный branch-creation preflight;
5. создать новую ветку от актуального `main`.

## 15. Завершение задачи включает уборку refs

Задача считается полностью завершённой не только после успешных тестов или merge.

Нужно также подтвердить:

- судьба рабочей ветки определена;
- merged branch удалена;
- abandoned valuable branch сохранена archive tag и удалена;
- нет случайно созданной следующей временной ветки;
- пользовательские локальные данные не затронуты.

## 16. Принцип по умолчанию

Если есть сомнение между «создать ещё одну ветку» и «сначала разобраться с уже существующей» — сначала нужно разобраться с существующей.

Короткая формула политики:

```text
main — единственная постоянная ветка
новая задача — новая ветка от актуального main
перед новой веткой — обязательный аудит временных веток
одна задача — одна ветка
один milestone — один PR
merged → delete
abandoned valuable → archive tag → delete
ветки не являются архивами
локальные пользовательские данные не трогать
```
