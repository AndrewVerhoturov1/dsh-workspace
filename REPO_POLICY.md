# Политика репозитория

Обязательные правила Git/GitHub для `dsh-workspace`. Процедурные команды и примеры — в [Preview Branch Workflow](docs/workflow/PREVIEW_BRANCH_WORKFLOW.md). Подробности Postman — в [postman/README.md](postman/README.md), пакетов реализации — в [workflow](system/implementation-package-workflow.md) и [правилах подготовки](system/implementation-package-authoring.md). При работе с такими подсистемами читай их документы по необходимости; эта политика не заменяет их границы доверия.

## Ветки, рабочие деревья и данные

- `main` — стабильная постоянная ветка; `preview` — постоянная интеграционная. Обычные задачи: временная ветка от **exact current `origin/preview`** → PR в `preview`. Прямой task PR в `main` запрещён. `preview → main` — отдельная операция после явного разрешения пользователя.
- `C:\Users\andre\.dsh` (main) и `C:\Users\andre\.dsh-preview` (preview) — постоянные worktree. Не удалять, не очищать, не перепривязывать к временной ветке, не использовать для временной реализации. Создавай отдельный worktree.
- `settings.yaml`, `attachments/`, browser state, секреты, учётные данные, логи, diagnostics и временные/runtime-файлы — пользовательское состояние, а не материал для автоматической уборки или commit. Не перезаписывай несвязанные изменения пользователя.

Исключение для [временных Postman inputs](postman/POSTMAN_INPUT_FILES.md): отдельная Host-managed `transport/postman-inputs` содержит только явно выбранные временные файлы и не является task branch, не merge-ится и не получает обычный task PR; cleanup — non-force commit без обещания удаления истории.

## Один канонический Git-снимок

Перед новой веткой выполни `git fetch --prune origin` и сними **один** переиспользуемый снимок задачи: `git status --short --branch`, текущие ветка и `HEAD`, все локальные и фактические remote refs (включая exact `origin/preview`), `git worktree list --porcelain`, связанные PR с base/head/state и ownership ресурсов. Для допуска новой ветки проверь также все незавершённые локальные и удалённые временные ветки. Сними поля снимка адресными командами (они не требуют отдельной системы учёта):

```bash
git status --short --branch
git branch --show-current
git rev-parse HEAD
git for-each-ref refs/heads refs/remotes/origin --format="%(refname:short)|%(objectname)|%(upstream:short)|%(upstream:track)"
git ls-remote --heads origin
git worktree list --porcelain
```

Состояние PR проверяй для текущей задачи; [процедура](docs/workflow/PREVIEW_BRANCH_WORKFLOW.md) описывает дальнейшие действия.

Переиспользуй снимок, пока входы не изменились. `fetch` обновляет remote refs; `commit` — `HEAD`/status; `push` — remote refs/PR; merge, rebase и cherry-pick меняют `HEAD` и состояние ветки; создание, переключение или удаление ветки/worktree меняет соответствующие refs и список worktree. Изменение PR и внешние изменения GitHub/дерева также инвалидируют затронутую часть. Обновляй **только затронутые поля**, а полный снимок повтори лишь при неизвестном охвате. Чтение, анализ, TODO и загрузка навыка снимок не инвалидируют.

Независимый чужой PR, branch или worktree — часть аудита, **не глобальная блокировка**. Блокирует только конфликт ownership/identity/resource именно данной задачи: тот же запрос или ветка, занятый worktree, неоднозначная перезапись либо риск для чужих данных. Не убирай чужую работу ради preflight. Новая обычная ветка допустима, когда exact `origin/preview` и ownership доказаны, пользовательские изменения не затронуты и отдельный worktree будет создан от проверенного SHA. Иная база допустима лишь для явно административной migration/bootstrap или release-операции.

Перед необратимым или разрушительным действием **отдельно** получи свежие адресные доказательства затрагиваемых refs/worktree/данных, точной цели и ownership. Старый снимок сам по себе не даёт разрешения удалять или переписывать. При изменении входов освежи относящиеся к действию поля, а не весь независимый аудит.

## Изоляция задачи и срок жизни ветки

Одна логическая задача → одна временная ветка/отдельный worktree; один законченный обозримый milestone → один PR в `preview`. Не смешивай несвязанные исправления и не создавай цепочки `feature/x-fix-v2` вокруг одной незаконченной задачи. Новую отдельную проблему запиши для следующей задачи. Экспериментальные ветки используют `exp/*` и должны закончиться решением.

После принятия: `PR → squash merge в preview → удалить временную ветку`. Ценную отклонённую работу сохраняй **annotated** `archive/*` tag на exact SHA: проверь локальный и удалённый peeled target, закрой PR без merge и удали временную ветку. Ненужную работу удаляй только после проверки отсутствия уникальных нужных данных. Ветки не служат архивом или резервной копией; archive tags не переписывать force-операцией. Постоянные refs не участвуют в обычном cleanup.

## Проверка и публикация

Проверки соразмерны изменению; действующий PASS при неизменных входах не повторяй. Перед принятием task PR в `preview` проверь относящиеся к изменению тесты, `git diff --check` и отсутствие случайных секретов/локальных данных. `preview` должен оставаться пригодным для запуска и старта следующей задачи: известные blockers, временные diagnostics и непроверенное состояние в него не переносить.

Локальный агент публикует только намеренные проверенные изменения своей задачи:

`изменения → проверка → явное добавление файлов задачи → commit → push текущей task branch → проверка remote SHA → создать/обновить один PR с base=preview`.

До успешной синхронизации локальный результат не считается завершённым: `local HEAD == origin task branch HEAD`. Не делай `git add -A` по загрязнённому дереву и не включай чужие изменения. Если публикация либо проверка SHA не удалась, сообщи `BLOCKED_SYNC` с local/remote SHA и причиной; не удаляй локальные commit/branch. До следующей независимой задачи результат должен быть опубликован либо явно отклонён пользователем.

Исключение `GitHub READ ONLY` сохраняется для внешнего или аналитического агента с таким контрактом: он не пишет в GitHub, а возвращает результат предусмотренным способом. После локального применения и отдельного решения о публикации commit/push/PR выполняет локальный агент. Подготовка/применение пакета не означает автоматического решения о публикации или merge.

## Merge и перенос в main

Обычный task PR с base=`preview` сливается через `finalize-task-pr` после отдельной команды пользователя и принятого решения о готовности; метод — squash, затем безопасная уборка временных ресурсов. Исполнитель merge не является повторным reviewer; правила и предохранители — в навыке.

`main` меняется только отдельным `preview → main` PR: exact head=`preview`, base=`main`, явное разрешение пользователя на проверенное состояние и точный marker в PR body:

`MAIN_GO_APPROVED_BY_USER: yes`

Используй `promote-preview-to-main`. Метод — **merge commit, не squash**. Перед merge докажи current `origin/preview`. После merge remote `preview` можно синхронизировать с новым merge commit только безопасным non-force fast-forward при доказанных exact refs; при сдвиге refs — warning/blocker без rewrite. `main` и `preview`, а также их постоянные worktree, не удаляются.

## Запреты и отчёт по стадии

По умолчанию запрещены `git reset --hard`, слепой `git clean`, автоматический stash, force push (включая `--force-with-lease`), обычная уборка через `git gc/prune`, переписывание archive tag, force deletion непроверенной ветки и удаление постоянных worktree. Узкая подтверждённая уборка временной ветки возможна, только когда её уникальная работа доказанно сохранена либо уже эквивалентно интегрирована. Сохраняй несвязанные пользовательские данные.

**Реализация/PR:** отчитайся о repository, task branch, task base SHA, local HEAD, origin task branch HEAD и `Synchronized: YES/NO`; commit, push, PR number/base/state и `GitHub synchronization status: SYNCED | BLOCKED_SYNC`. Отчёт относится к уже произошедшим действиям.

**Merge:** только исполнитель merge дополнительно сообщает `Merge performed` и `Final origin/preview SHA`.

**Promotion:** только исполнитель promotion дополнительно сообщает `Final origin/main SHA` и результат синхронизации `preview`.

Не требуй от исполнителя реализации доказательства будущего merge или promotion. Полное завершение временной ветки после отдельного merge/отказа включает подтверждение её судьбы и сохранности постоянных refs/worktree и пользовательских данных.
