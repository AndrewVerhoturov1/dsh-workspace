# Postman Bridge — исполнение и доставка

Host исполняет явную команду Leader, сохраняет факты, доставляет результат и обслуживает таймер. Маршрут, повтор, восстановление и достаточность результата определяет Leader. [DevSpace Flow](POSTMAN_DEVSPACE_FLOW.md) описывает основной маршрут; [Current Flow](POSTMAN_CURRENT_FLOW.md) и [Ask Flow](POSTMAN_ASK_FLOW.md) — резервные Direct/Web маршруты.

## Роли и инструменты

Верхнеуровневый `postman-leader` и совместимый `postman-leader-ptc` получают обязательный `ptc_execute` для management tools. Прямыми остаются доступные `skill`, `ask_user_question`, `exit_plan_mode`, `read_image`. Leader не получает shell, write/edit, generic delegation или прямую отправку Postman.

Leader владеет Secretary ×1, обычными Worker ×2 и Sol ×1; Sol — собственными обычными Worker ×2. Worker/Secretary используют `codex / gpt-6-luna / low`, Sol — `gpt-6.1-sol / xhigh`. FAST assignment budget 8..100, default hard60/soft48; отдельный budget каждого назначения, без общей квоты токенов команды. Compact сохраняет Session/ID, fresh создаёт новую сессию с сохранением аудита. Отчёт и закрытие — разные факты; качество отчёта оценивает parent.

Sol выполняет собственные инженерные вызовы и управление своими Worker через PTC. `report` и `notify_parent` остаются прямыми. Worker и Secretary не получают PTC или делегирование. Secretary ведёт существующий private ledger независимо от Git.

`ptc_execute` требует только `program`; `description` необязателен. `wait_for_event:true` завершает ход по решению лидера; Host не доказывает право ждать. Адресное событие или пользовательское сообщение возобновляет работу. Отказ/ошибка вложенного инструмента возвращается как данные, предыдущие эффекты не переигрываются. Справка: [PTC patterns](../.agents/skills/postman-leader/PTC_PATTERNS.md).

## Рабочий каталог и Git

Host не готовит ветки/worktree, не синхронизирует проект, не восстанавливает Git и не требует закрытия прежней задачи. Worker, Secretary, Sol и Bridge работают с назначенным каталогом либо каталогом сессии. Обычная папка не требует origin или GitHub.

Для реального изменения репозитория Leader поручает Worker подготовку временного worktree и Git-операции по [REPO_POLICY.md](../REPO_POLICY.md). Сохранённые REQ, результаты, отозванные задания и пользовательские файлы не переназначаются и не очищаются.

Scope, read-only и Computer Use — инструкции исполнителю. Host сохраняет фактические права ОС/подключений, принадлежность задания и явный отзыв, но не добавляет запрет по пересечению папок или отсутствию Git-контекста.

## Основной DevSpace маршрут

```text
Leader → postman_bridge({message:'@PostmanDevspace ...', lane_id?})
       ← admission + bridgeJobId + laneId
Host → persistent Luna своей линии + Direct/Web → конкретный REQ
ChatGPT → DevSpace/доступные инструменты → местный bell или текст
Host → сохраняет результат и адрес беседы → POSTMAN_BRIDGE_READY
Leader → postman_bridge_status({bridge_job_id}) → результат для решения
```

До трёх текущих DevSpace исполнений на Leader; сохранённая беседа и старая неопределённая запись сами по себе слот не занимают. Одна линия имеет один текущий REQ. `lane_id` продолжает ту же принадлежащую Leader Luna/ChatGPT-беседу. Luna остаётся связисткой без новых инструментов и прав; её сообщение coordinator не даёт ей права отправить задание самостоятельно.

Готовый отчёт доступен независимо от доступности Luna. Дополнительный разбор Luna не является условием доставки. Адрес беседы сохраняется при получении, включая необычное завершение. Поздний bell относится к прежнему REQ и не заменяет результат следующего.

## Резервные Direct/Ask/Image

Leader вызывает `postman_bridge` с точным `@Postman`, `@PostmanAsk` или `@PostmanImage`. Host создаёт fresh one-shot transport child `codex / gpt-6-luna`, maxDepth=1, без наследования истории. Его allowlist: `skill`, `postman_send_current_turn`, `postman_current_turn_status`, `postman_ask_validate_reply`.

Child получает точное новое model-authored поручение как current user message, загружает соответствующий навык и вызывает `postman_send_current_turn()` без аргументов. Host читает trusted terminal непосредственно из exact child scope; prose Luna не является authority. Транспортная публикация REQ/RESULT не управляет Git рабочего проекта. Public input staging требует отдельного явного разрешения; private inputs этого разрешения не дают.

Для текстового `deliveryMode=inline` authority — `assistantText`; для `file` — проверенный `resultFile`. Child не восстанавливает большой файл в контекст, Leader читает нужные части при необходимости. Native image result не создаёт implementation grant.

## Наблюдение, управление и отправки

`postman_bridge_status`, `postman_bridge_list`, `postman_team_status` только наблюдают. Они не создают REQ, не отправляют сообщения, не запускают Luna и не отзывают права. Устаревшие управляющие параметры status удалены. Чужой job не раскрывает данные.

`postman_devspace_control({bridge_job_id,action:'steer'|'preempt'|'stop'|'status',...})` и `postman_bridge_stop({bridge_job_id})` адресуют собственное задание. После выгрузки используются сохранённый адрес и фактическая доступность управления; отсутствие оперативного handle не равно отсутствию задания. `QUEUED` и `STOP_REQUESTED` не являются доказательством выполненного Send/Stop или прекращения Bash.

Каждая новая отправка требует явной команды Leader; Host не классифицирует ошибку по тексту и не строит цепочки восстановления. В одном вызове — одна попытка Send. Старый Send/UNKNOWN сообщается как факт, не запрещая последующую явную команду. Перед повтором Leader проверяет результаты, историю беседы и процессы, чтобы не повторить уже выполненное.

Механическое исключение — действующий DevSpace таймер 15/30/45 минут: сначала результат; при необходимости один распознанный Stop, ожидание готового composer и продолжение. Максимум три подтверждённых напоминания, общий deadline прежний. Скрытая история и число сообщений не служат дополнительным доказательством права продолжить собственную беседу.

## Долговременные данные и ограничения

В существующем реестре сохраняются exact owner, job/REQ/child/lane, адрес беседы, факты отправки/отмены и результаты. Старые Git-поля читаются как история, не управляют допуском. Выгрузка не запускает прежнюю команду и не превращает неизвестный исход в успех или активную работу.

Host блокирует чужую принадлежность, запрещённый роли инструмент/обход PTC, новое действие явно отозванного задания и превышение технического предела. Host самостоятельно не удаляет, не сбрасывает и не перезаписывает пользовательские данные. Ошибки нативного инструмента и схемы остаются локальными результатами.

Возможный старый writer, пересечение путей, отсутствие Git-метаданных, непроверенный отчёт и прежняя доставка — краткие факты в существующем ответе. Они не требуют подтверждения и отдельного пробуждения модели.

## Вложения и implementation package

[postman_input_files](POSTMAN_INPUT_FILES.md) закрепляет владельца, точный набор файлов и отправку без Git-контекста. Host создаёт native attachment по выданным дескрипторам; child не строит binary payload и не делает ручную загрузку.

Trusted `RESULT_DURABLE` сохраняет Leader-owned grant по exact REQ с ZIP/SHA до освобождения операции. Отдельно авторизованный Worker вызывает `implementation_artifact_apply({requestId, worktree})` с явно выбранным каталогом. Host сверяет принадлежность и SHA, запускает существующий runner, без требования опубликованного HEAD и Host-prepared дерева. Runner сохраняет непосредственные проверки применения.

PASS runner при неизменных входах не требует повторного запуска тех же targeted tests. FAIL возвращается с диагностикой; неизвестные dirty файлы сохраняются. Git-публикация, merge и stable preview требуют соответствующих отдельных полномочий по REPO_POLICY.

Изменение исходников и PR не обновляют активный Host. Установка, контролируемое переключение сессии и живая приёмка выполняются отдельным согласованным этапом; `preview` требует отдельного stable GO.
