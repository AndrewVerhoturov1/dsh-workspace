# PostmanDevspace — этап 1 и продолжаемая связь этапа 2

Внешнее сообщение — обычное человеческое обращение, GitHub-ссылка на задание, GitHub-ссылка на [правила](SKILL.md) и обязательство прочитать оба документа. В нём нет REQ, локальных путей, режима, bell-команды или текста задачи. Эти данные находятся в опубликованном задании `tasks/<bridgeJobId>.md`; REQ остаётся внутри файла. Постоянные SKILL/AGENTS/REPO_POLICY/TASK_CONTRACT читаются по доступным SHA-pinned GitHub-ссылкам. Недоступная обязательная ссылка — явный INSTRUCTION_UNAVAILABLE без Send/обхода. Приватные native inputs не публикуются.

Отдельный `postman_bridge({message:'@PostmanDevspace ...',devspace_mode:'READ_ONLY'|'WRITE_TEST'})` допускается только живому top-level Postman Leader. Host создаёт временную one-shot Luna и сохраняет owner/job/child/REQ/mode/channel в существующем приватном registry. `READ_ONLY` разрешает чтение prepared task worktree; `WRITE_TEST` дополнительно позволяет безвредную запись только в отдельной Host-private тестовой папке. Это ограничение поручения, **не песочница shell DevSpace**. Полноценные Git writes не разрешены.

Host публикует только задание в `transport/postman-devspace` через существующий GitHub transport publisher. `assignment.md` и publication receipt сохраняют его exact identity, `task.md` содержит короткое внешнее сообщение. Immutable task URL заменяет видимый REQ как browser anchor; owner/channel/binding сохраняются. Cold restore переиспользует публикацию, а crash до receipt сверяется по тому же job path без blind overwrite. Main, preview и репозиторий задания этим не меняются. Persistent Luna/lane принадлежит точному Leader; native inputs передаются по сохранённым грантам. signal.ps1 публикует атомарный REQ-bound bell done/need-decision/blocked с optional Message/Report. Bell идемпотентен; управляющие steer/preempt/stop адресуют конкретный собственный чат.

Bell имеет приоритет над final/ZIP/текстовой диагностикой. ReportRef ограничен назначенной папкой; чужой report отбрасывается без потери bell, отсутствие/произвольный текст отчёта не блокирует delivery. Host не исполняет message. Capability/job/REQ/owner/Luna и canonical channel проверяются до handoff. Result редактирования и отчёт остаются приватными; в Git идут только source/узкие tests/skill.

`DEVSPACE_SIGNAL_RECEIVED` / `DEVSPACE_DIAGNOSTIC` → trusted terminal → READY → exact status. READY/DELIVERED не означают инженерный PASS. Owner/lane/Luna/conversationRef определяют право продолжить беседу независимо от успешности старого REQ или видимости его anchor. UNKNOWN/PROVEN_NOT_SENT сохраняются; сначала наблюдение чата, затем отдельный новый REQ/корректирующее продолжение без слепого повтора side effects. После исходной ошибки Host выполняет три durable recovery attempts, останавливается при успехе и оставляет Leader выбор после исчерпания. Restart не повторяет подтверждённый прежний клик.

DevSpace CHECK примерно на 15/30/45 минутах допускает один распознанный Stop собственного чата даже при ACTIVE_TOOL/UNKNOWN; явный preempt/stop Leader допускается в любой момент. Положительно наблюдённое новое user-поручение запрещает старому REQ Stop/Send; скрытая старая история сама по себе не запрещает управление. Проверка выполняется перед UI действием, bell имеет приоритет. После Stop Host ждёт настоящей готовности composer, продолжая ожидание и после 10 секунд, и отправляет одно короткое продолжение с проверкой прогресса. Stop генерации не доказывает окончания Bash; конфликтующие записи не запускаются без безопасного разведения областей. Legacy 10/20/30/40/50 не меняются.

До трёх recovery attempts включают сбои до URL/REQ/Luna и временный/неоднозначный инструментальный BLOCKED. Известный чат наблюдается; без чата создаётся новая собственная попытка, при неизвестной старой записи — в отдельной папке. NEED_DECISION/permission/scope требуют решения. После исчерпания `recover:true` по исходному bridgeJobId адресует последнюю попытку без дублирования. После archive `reconcileWriter:true` того же status tool снимает residual только по Host native proof; старый неотслеживаемый процесс остаётся EXIT_UNPROVEN. Полный контракт — [POSTMAN_BRIDGE_FLOW](../POSTMAN_BRIDGE_FLOW.md#durable-recovery-и-observation).

Bell вызывается **из настоящего DevSpace Bash** готовой командой `pwsh -NoProfile -NonInteractive -File <native-script-path> done|need-decision|blocked`. Optional `-Message`/`-Report` допускают русский многострочный текст; каждый аргумент заключён в Bash single quotes, апостроф экранирован `'"'"'`, а не PowerShell `&`/удвоением кавычки. Отчёт любого формата необязателен; missing report — warning, не gate. Без bell завершённый текст с точными POSTMAN_RESULT_BEGIN/POSTMAN_RESULT_END из задания передаётся как UNKNOWN; неверные/чужие/повторные/неполные маркеры явно отмечаются RESULT_MARKERS_INVALID с сохранением исходного текста. Доступный частичный при таймауте — PARTIAL; это не DONE/PASS и не требует ZIP/Ask envelope/schema. Cold recovery сохраняет событие и корреляцию прежнего REQ, передаёт доступный trusted terminal и не подменяет новый результат поздним старым bell.

Existing dedicated browser, Send proof, same-chat recovery и serialized reminder intent переиспользованы. Это не второй browser transport. Report parsing не является prerequisite. DevSpace App/MCP в новом conversation нужно доказать настоящим read. Unit tests с fake page не доказывают live MCP, write/bell, same Luna delivery или deployment.

## Этап 3: маршруты исполнения

`postman_task_prepare({read_only:true})` создаёт owned read-only контекст без Git branch/push. Только Devspace `READ_ONLY` может использовать эту область. Для `WRITE_ISOLATED` сначала штатный Host prepare (clean task branch/worktree); разрешённые правки и тесты — только в назначенном worktree, без самовольных Git commit/push/PR и без обязательного ZIP. Режим `WRITE_TEST` использует прежнюю Host-private test folder. `WRITE_APPROVED_TARGET` не включён без отдельного утверждённого Host grant; DevSpace shell сам по себе не песочница.

## Этап 4: после перезапуска и диагностика

При сохранённом REQ и местном bell восстанови прежнего Leader через штатный `postman_task_prepare` (с тем же read_only-режимом, если он использовался). Host безопасно пробует передать событие прежней продолжаемой Luna, только после подтверждения её идентичности. В ответе prepare появляется `devspaceReconciliation` с фактическими `recovered/unresolved`; `POSTMAN_BRIDGE_READY` и `postman_bridge_status` доставляют только уже доказанный terminal. `coldBellRecovery=intent` и `coldReadyWake=intent/unknown` означают неопределённый side effect: автоматический resend/followup запрещён. Старые browser/Direct процессы не запускаются заново только из-за местного сигнала; чужие каналы не читаются. При отсутствии Luna или полномочия — сообщить Leader `OUTCOME_UNKNOWN`, сохранить файлы и расследовать отдельно.

Runtime диагностика: `postman_team_status` (owner Luna/активный job), `postman_bridge_list` (REQ и состояние), `postman_bridge_status` (подтверждённый terminal), `postman_devspace_control({action:'status',bridge_job_id})` для фактических Stop/Send receipts. `QUEUED` не равен отправке, `DELIVERED` не равен проверенной задаче. Старый ZIP/Ask/Image должен оставаться независимым. Откат установки — только из резервной копии изменённых source/skill-файлов; не удалять приватные `event.json`/binding и не очищать REQ.

## Проверка/активация

Целевые новые suites: `node --test lib/postman-devspace.test.js` из Harness plugin и `python -m unittest postman.devspace.tests.test_devspace` из repo. Дополнительно относящиеся старые Direct/Bridge/observer/Ask/native-image suites и `git diff --check`. Source изменения в task worktree не обновляют активный Host. Установка/перезапуск, live новый режим и публикация — отдельное согласованное действие Leader; постоянные worktrees, REPO_POLICY и permissions не меняются.
