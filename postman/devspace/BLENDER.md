# Blender MCP — прямой доступ ChatGPT и работа в фоне

**Состояние проверки на 24 октября 2026 года.** Внешний ChatGPT напрямую обращался к Blender MCP через OpenAI Secure MCP Tunnel. Туннель переведён с ручного запуска в скрытый фон Windows; отдельной проверкой подтверждён автоматический запуск одного нового клиента после сбоя. Это описание **проверенной установки**, а не обещание непрерывной доступности или автоматической активации после обновления Git. Степень подтверждения — [таблица возможностей](../POSTMAN_DEVSPACE_CAPABILITIES.md#blender-mcp--живая-приёмка-24-октября-2026).

## Подключение и границы

- В текущем каталоге внешнего ChatGPT подтверждён namespace `mcp__Blender_Postman__`: `get_scene_info`, `execute_blender_code` и `look`. Прямой вызов прочитал сцену, изменение положения объекта подтвердилось повторным чтением; `look` вернул **настоящее просмотренное изображение**. После перевода туннеля в фон прямые `get_scene_info` и `look` снова прошли. Реальные имена, схемы и доступность инструментов нужно проверять в **каждом** подключении.
- Локальный `bpy`/SDK и `tunnel-client dev proxy` допустимы для обслуживания и диагностики, но **не заменяют прямую приёмку** ChatGPT → `mcp__Blender_Postman__`. Нельзя подменять её проверкой через Bash, Orca или VUDA. Для визуальной приёмки необходимо рассмотреть свежий `ImageContent`, а не только текст результата.
- Проверенные версии: Blender **5.2.3 LTS**, `mcp-for-blender` **2.2.4**, addon **1.8**, protocol **15**, `tunnel-client` **0.0.16**. Blender addon слушает raw TCP на `127.0.0.1:9877` — **это не HTTP MCP endpoint**.
- В `mcp.command` Windows нужно применять путь с прямыми слешами либо корректно экранированными обратными: при разборе команды клиент поглощал обычный одиночный `\`. Исправление отдельно прошло `initialize` и обнаружение инструментов.
- `execute_blender_code` может менять сцену и файлы; safe mode **не является полной песочницей**. Перед изменением прочитай состояние сцены, сохрани открытую пользовательскую работу и не выходи за согласованную область проекта.

## Установленная работа в фоне Windows

Частная установка расположена под `%LOCALAPPDATA%\DSH\integrations\blender-mcp`. Здесь хранится действующий профиль `blender-local`, а не новый туннель или отдельная служба.

- Человек **один раз локально** ввёл runtime API key в скрытом поле `Provision-BlenderTunnelBackground.ps1`. На диске хранится только **Windows DPAPI CurrentUser ciphertext**, файл и частный каталог защищены ACL без наследования: доступ текущего пользователя и SYSTEM. Открытый ключ/токен не пересылают в чат, журналы или Git; содержимое защищённого хранилища, частные профили и журналы, идентификаторы, PID, изображения и файлы сцен **не включают в исходный Git-репозиторий**.
- `Run-BlenderTunnelBackground.ps1` извлекает ключ во время запуска **того же Windows-пользователя**, передаёт его только в окружение дочернего `tunnel-client`. Существующий `launch-mcp.cmd` очищает переменные ключей перед MCP-процессом. Открытый ключ не передаётся в аргументах и не записывается в файлы или журналы.
- Одно задание Планировщика Windows: `BlenderMCP-Background-Tunnel`. Пользовательский `InteractiveToken`/`Limited`, `Hidden` и неинтерактивный запуск PowerShell; **AtLogOn + TimeTrigger каждую минуту без Duration** (неограниченное повторение), `MultipleInstances=IgnoreNew`, `ExecutionTimeLimit=PT0S`, запуск и продолжение на батарее разрешены. `RestartOnFailure=3/PT1M` сохранён, но на этом ПК его фактическое поведение не обеспечило восстановление.
- Почему добавлен минутный TimeTrigger: при ненулевом выходе клиента штатный `RestartOnFailure` не сработал; аналогичный отказ наблюдали на отдельной задаче без ключа и сети при выходах `-1` и `1`. Само по себе это **не доказывает**, что причина именно в значении `-1`. После добавления триггера к **той же** задаче один контролируемый выход целевого клиента был восстановлен **следующим штатным срабатыванием**, без `Start-ScheduledTask`, без ввода ключа и без дубликатов. Новый клиент дал HTTP **200** на `/healthz` и `/readyz`. Собственный цикл, наблюдатель, вторая служба и дополнительные зависимости не вводились.
- В пользовательском сеансе Windows проверено `EnumWindows`: у цепочки нового фонового клиента не было видимых окон. Две оставшиеся консоли прежних операций скрыты адресно **без завершения процессов и потери буферов**.

## Безопасное управление

**Сначала только прочитай состояние** в PowerShell текущего пользователя:

```powershell
Get-ScheduledTask -TaskName 'BlenderMCP-Background-Tunnel'
Get-ScheduledTaskInfo -TaskName 'BlenderMCP-Background-Tunnel'
```

Если задание включено или выполняется, **не запускай** `Connect-BlenderTunnel.ps1`, второй `tunnel-client run`, новый профиль или второй туннель. Минутный триггер сам может запустить клиент; `IgnoreNew` защищает только экземпляры **этой** задачи, а не независимые ручные процессы.

Для **намеренной остановки** прежде выключи будущие запуски, затем останови задание:

```powershell
Disable-ScheduledTask -TaskName 'BlenderMCP-Background-Tunnel'
Stop-ScheduledTask -TaskName 'BlenderMCP-Background-Tunnel'
```

После этого **проверь фактическое завершение** именно процесса `blender-local` и его дочерней цепочки. `Stop-ScheduledTask` и состояние `Ready` сами по себе **не доказывают**, что всё дерево процессов завершилось. Для адресной проверки без чтения секретов можно просмотреть процессы `tunnel-client.exe` и только их аргументы профиля:

```powershell
Get-CimInstance Win32_Process -Filter "Name='tunnel-client.exe'" |
  Where-Object { $_.CommandLine -match 'blender-local' } |
  Select-Object ProcessId, ParentProcessId, Name
```

Проверяй принадлежность и актуальность PID перед действиями. **Не останавливай VUDA, пользовательский Blender или другие туннели.** Ручной старый клиент допускается только когда фоновое задание **отключено** и целевого процесса больше нет.

Чтобы штатно вернуть фоновый режим, сначала убедись в отсутствии второго `blender-local`, затем из того же сеанса пользователя:

```powershell
Enable-ScheduledTask -TaskName 'BlenderMCP-Background-Tunnel'
Start-ScheduledTask -TaskName 'BlenderMCP-Background-Tunnel'
```

После запуска проверяй `Running`, один целевой клиент, его loopback `/healthz` и `/readyz`. Не угадывай старые PID или динамический порт HTTP-контроля. Если задача уже выполняется, заново её не запускай. Если ключ отозван/истёк, без отдельного безопасного обновления дальнейший запуск не заработает: автоматического обновления ключа **нет**.

## Ограничения доказательства и применения

- Настройка **AtLogOn** проверена по определению задачи, запуск через Планировщик проверен вручную, а периодический триггер восстановил один целевой процесс. **Настоящие logout/login и перезагрузка Windows не выполнялись**.
- Доступность зависит от включённого ПК, пользовательского сеанса Windows, действительного ключа, связи с OpenAI и **отдельно работающего Blender** с установленным дополнением на loopback `9877`. Автозапуск самого Blender **не добавляли**.
- Один успешный автоматический перезапуск не означает универсальную надёжность при любом сбое, сне, выключении ПК или проблемах сети.
- Изменение этих исходных документов **не применяет** навык к уже работающему Host/Leader/ChatGPT: публикация, merge, установка/перезапуск и новые SHA-pinned правила Host происходят отдельно. Для следующего REQ проверяй фактически закреплённую Host версию инструкций.
