# PostmanDevspace: основной маршрут

Host исполняет явные команды Leader и доставляет факты. Он не выбирает восстановление, другого исполнителя или смысловую приёмку. Общие роли и ограничения — [Bridge Flow](POSTMAN_BRIDGE_FLOW.md).

## Линии и Luna

```text
Leader ─ Secretary (факты и private ledger)
  ├─ lane A → persistent Luna A → ChatGPT A → REQ → bell/text
  ├─ lane B → persistent Luna B → ChatGPT B → REQ → bell/text
  └─ lane C → persistent Luna C → ChatGPT C → REQ → bell/text
```

`postman_bridge({message:'@PostmanDevspace ...'})` возвращает `bridgeJobId`, `laneId`; `lane_id` адресно продолжает существующую беседу. До трёх текущих исполнений на Leader, один текущий REQ на линию. Сохранённая беседа и старая неопределённая запись сами по себе слот не занимают. Legacy Bridge имеет отдельную техническую ёмкость.

Luna остаётся продолжаемым субагентом-связисткой без shell/browser/файловых инструментов. Host отправляет поручение сам; coordinator followup не разрешает model-authored Send. Luna сообщает или дополнительно разбирает полученные факты для Leader. Готовый результат сохраняется и доступен независимо от её состояния.

## Каталоги и инструкции

Рабочий каталог выбирает Leader через `workspace_root`, без него используется каталог сессии. Обычная папка, Git без origin и другой Git-хостинг не требуют подготовки Host. Для правки репозитория Worker подготавливает временный worktree по REPO_POLICY и передаёт путь; Host ветками и синхронизацией проекта не управляет.

`workspace_access`, scope и режим — инструкции исполнителю, фактические права ОС/подключения остаются прежними. READ_ONLY запрещает исполнителю изменение файлов, кроме выданного bell. WRITE_TEST предназначен для частной папки результата, WRITE_ISOLATED — для назначенного рабочего дерева, WRITE_APPROVED_TARGET — для назначенного каталога. Эти названия не создают дополнительную файловую песочницу Host. Пересечения путей и возможные старые writers сообщаются Leader, который выбирает порядок и рабочую область.

Writer binding сохраняет exact owner/REQ и адрес инструментальной операции. Для записи используй выданный `postman-writer:<jobId>`, не подбирай чужой. Нативные права и явный отзыв конкретного задания действуют. Файлы транспорта, runner, DevSpace и VUDA находятся в установленном DSH, независимо от рабочего проекта.

Computer Use по умолчанию разрешён в границах задачи; явный `computer_use:'deny'` сохраняется. ChatGPT сам выбирает доступные инструменты. Host не требует target adapter и не обещает наличие capability. Внешний ChatGPT обращается к VUDA через подключённый `VUDA Local`; местным агентам доступен прямой VUDA MCP без туннеля, если разрешён роли. Правила — [VUDA.md](devspace/VUDA.md) и [инструкции исполнителя](devspace/SKILL.md).

## Входы и результат

Leader получает дескрипторы через `postman_input_files` и передаёт `--input-files-json <JSON>`. Private bytes превращаются в native image attachment или ZIP входов. GitHub input publication требует отдельного разрешения и не является обязательным транспортом.

Каждая отправка имеет собственный immutable REQ. Bell имеет приоритет; завершённый текст без bell доступен как `text_fallback`, без выдуманного инженерного PASS. Для исследовательского текста со ссылками Leader может явно попросить обычный ответ без местного bell. Факт доставки текста не доказывает вызов веб-инструмента.

Host сохраняет результат и адрес беседы до дополнительного разбора Luna. `POSTMAN_BRIDGE_READY` сообщает о доступном `postman_bridge_status({bridge_job_id})`; `DONE_REPORTED`, доставка и приёмка различаются. Поздний bell обновляет только собственный REQ. Отсутствие идеального отчёта не препятствует доставке.

## Одна настоящая картинка

Leader вызывает существующий Bridge через PTC:

```js
await tools.postman_bridge({
  message: '@PostmanDevspace Сгенерируй одно изображение: маяк у моря на рассвете.',
  image_mode: true,
  devspace_mode: 'READ_ONLY'
})
```

В ChatGPT уходит только визуальный текст после маркера. Этот режим не публикует GitHub-задание, не прикладывает входные файлы и не добавляет bell/инструкции/напоминания. Legacy `@PostmanImage` и обычный DevSpace не меняются. В одном REQ — одна попытка Send; UNKNOWN означает только наблюдение без повторной отправки.

После `POSTMAN_BRIDGE_READY` Leader читает `postman_bridge_status({bridge_job_id})`. Из точного следующего generated response загружается оригинал штатной кнопкой Download image, не preview/currentSrc и не снимок экрана. Decode проверяется до сохранения неизменных bytes. Результат содержит owner/job/REQ/chat, `assistantIdentity`, `resultImage`, MIME, размеры, длину, SHA-256 и отдельные `sendState/generationState/saveState/deliveryState`. При `SAVED/READY_FOR_LEADER_READ` Leader открывает точный `resultImage` прямым штатным `read_image`. Генерация без доказанного оригинала — не сохранённая/доставленная картинка; автоматической загрузки повторно нет.

## Отправки, таймер и управление

После ошибки Host возвращает факты, не запускает восстановительную цепочку и не классифицирует текст `BLOCKED`/тайм-аут. Leader решает наблюдать, продолжить, создать новый REQ или сменить исполнителя. Перед повторным Send он проверяет историю, результаты и процессы; UNKNOWN не означает отсутствие выполненных действий. В одном вызове — одна попытка Send; старая неопределённость не запрещает новую явную команду.

`postman_devspace_control({bridge_job_id,action:'steer'|'preempt'|'stop'|'status',...})` адресует точное собственное задание. `QUEUED` не равно `SENT_CONFIRMED`/`STOP_UI_PROVEN`. После выгрузки используются сохранённый адрес и фактическая доступность управления. UI Stop не доказывает остановку Bash.

Действующий таймер сохранён: через 15 минут без завершённого ответа сначала проверить результат; если нужно, один раз нажать распознанный Stop, дождаться настоящей готовности composer и отправить продолжение. Ожидание composer не обрывается через 10 секунд. Максимум три подтверждённых напоминания, следующий срок — через 15 минут после подтверждённого предыдущего; общий deadline не продлевается. В рамках одного UI-действия неизвестный исход клика не повторяется вслепую. Приоритет результата, принадлежность беседы и явный отзыв остаются.

Status/list только наблюдают: не отправляют, не запускают Luna, не меняют права. После restart старые Send не переигрываются; существующий результат читается без обязательного восстановления субагента. Закрытие/отмена собственного исполнителя не означает успех задачи и не чистит файлы.

## Проверка и установка

Проверяются работа без Git, явное продолжение собственного UNKNOWN, адрес после необычного завершения, ready без Luna, поздний bell, чтение после выгрузки, реальные лимиты параллельности, owner/role/revoke, timer Stop → Continue и резервные маршруты. Synthetic/unit результаты не означают live GUI PASS.

Исходники/PR, установка и активный runtime — разные состояния. Установка и переключение выполняются отдельным согласованным этапом; merge и stable `preview` — отдельные решения по REPO_POLICY. Исторические возможности и пределы прежних проверок находятся в [таблице](POSTMAN_DEVSPACE_CAPABILITIES.md).
