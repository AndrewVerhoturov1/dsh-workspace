# Общие правила агента

`dsh-workspace` — версионируемое, намеренно неполное отражение рабочей установки DSH в `C:\Users\Andrew\.dsh`: сюда не входят секреты, учётные данные и временное состояние. DSH — основная среда пользователя и разработки самого DSH. Обычную работу, обслуживание и ремонт выполняй внутри DSH; при равной надёжности выбирай простое решение, пригодное для самоподдержки. Внешний Codex — резервный путь лишь тогда, когда DSH не может безопасно починить себя. Это не ослабляет защиту данных и границы доверия.

- Пиши по-русски ясно и без лишних заимствований; учитывай текущую дату. Русские текстовые файлы обрабатывай как UTF-8.
- Ссылки на сайты оформляй Markdown-ссылками, существующие локальные файлы в Harness Web — точным путём в обратных кавычках (или уникальным именем изменённого файла). Не используй `file://` и голые пути.
- Перед операциями с ветками читай [REPO_POLICY.md](REPO_POLICY.md). Сохраняй пользовательские изменения и работай в отдельном временном worktree. `C:\Users\andre\.dsh` и `C:\Users\andre\.dsh-preview` — постоянные worktree: не удалять, не очищать и не применять к ним автоматические reset/stash. Проверенные изменения локального агента публикуются через commit, push, проверку удалённого SHA и PR в `preview`; исключение `GitHub READ ONLY` и статус `BLOCKED_SYNC` определены в policy.
- В строках JS/TS в `run_code` не пиши Windows-пути с одиночными `\` (например, `C:\Users\Andrew\.dsh\REPO_POLICY.md`): для файла в `cwd` предпочитай `'REPO_POLICY.md'`, для абсолютного пути используй `C:/Users/Andrew/.dsh/REPO_POLICY.md` либо правильно экранированные обратные слеши (`C:\\Users\\Andrew\\.dsh\\REPO_POLICY.md`).
- Проверки соразмерны изменению. PASS действителен при неизменных релевантных входах: не повторяй эквивалентную проверку ради уверенности. Во время работы запускай целевые проверки, широкую — на естественной финальной границе, только если она нужна задаче или подсистеме. Повтор оправдан изменением кода, тестов, конфигурации, зависимостей, refs либо неполным результатом. Зафиксированный старый сбой не воспроизводи снова без нового основания. Новый validator/test/guard нужен лишь для отдельного failure mode или trust boundary.

## Конечная задача

Обязательная дисциплина задачи (без открытия дополнительных документов):

1. Выполняй только текущую задачу и её условия завершения; не назначай себе следующую.
2. Делай минимальное достаточное изменение, сохраняя действующие контракты.
3. Не добавляй абстракции, слои, обёртки, зависимости, состояние, повторы, резервные сценарии, проверки, инфраструктуру или соседние изменения без текущего требования либо конкретного существенного риска, существующего сейчас.
4. О соседней проблеме вне необходимых границ сообщи, но не исправляй её автоматически.
5. Проверки соразмерны изменению; успешную проверку не повторяй без изменения релевантных входов.
6. Когда условия выполнены и обязательные проверки прошли, сообщи результат и остановись — без нового рефакторинга, укрепления, аудита, уборки или другой задачи.

Расширение решения — исключение, требующее основания, а не улучшение по умолчанию.

Для реализации и передачи работы используй [контракт задачи](docs/workflow/TASK_CONTRACT.md): формируй границы и условия завершения из запроса без новых требований, не требуя от пользователя формы. Для мелкой правки не создавай отдельный план или файл; при передаче сохрани границы и доказательства проверок. Когда условия выполнены и достаточно проверены — сообщи результат и остановись. Для приветствий и простых информационных ответов документ читать не нужно; после загрузки не перечитывай его без причины.

При работе в режиме планирования рассматривай только применимые к текущей задаче темы: неприменимые разделы не создают требований или работ. Полнота плана означает достаточность для согласованной задачи, а не охват всех возможных архитектурных вопросов. Существенные решения согласуй штатным выходом из plan mode; пока он активен, ничего не реализуй.

## Условные маршруты

- Только при точном начале **текущего** сообщения `^\s*@Postman(?:\s|$)` первым действием по задаче загрузи `skill(delegate-via-postman)`. Для `^\s*@PostmanAsk(?:\s|$)` — `skill(delegate-via-postman-ask)`. Для `^\s*@PostmanImage(?:\s|$)` — `skill(delegate-via-postman-image)`. Разрешение не наследуется из предыдущих сообщений; разработка Postman сама по себе его не даёт. При недоступности нужного навыка — fail-closed `STOP`, без обхода навыка и альтернативной отправки. Доверенную границу текущего сообщения и ответы соблюдай по соответствующему навыку; обычный агент не запускает Postman без такого триггера.
- Только для роли Postman Leader загружай `postman-leader`; правила Bridge/Worker и сообщения родителю находятся в навыке и [Postman Bridge flow](postman/POSTMAN_BRIDGE_FLOW.md). Обычная разработка Postman без триггера остаётся локальной задачей.
- Перед подготовкой либо применением пакета реализации читай [workflow](system/implementation-package-workflow.md) и [правила подготовки](system/implementation-package-authoring.md), а также `REPO_POLICY.md`.
- При отдельной команде слить уже проверенный task PR загрузи `finalize-task-pr`; для переноса проверенного `preview → main` только после явного разрешения пользователя — `promote-preview-to-main`. Исполнение и предохранители описаны в навыках.
- Если задача действительно относится к долгоживущему подпроекту, прочитай его `SUBPROJECT.md`; остальные подпроекты не загружай.
