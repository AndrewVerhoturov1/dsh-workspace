# Общие правила агента

`dsh-workspace` — версионируемое, намеренно неполное отражение рабочей установки DSH в `C:\Users\Andrew\.dsh`: сюда не входят секреты, учётные данные и временное состояние. DSH — основная среда пользователя и разработки самого DSH. Обычную работу, обслуживание и ремонт выполняй внутри DSH; при равной надёжности выбирай простое решение, пригодное для самоподдержки. Внешний Codex — резервный путь лишь тогда, когда DSH не может безопасно починить себя. Это не ослабляет защиту данных и границы доверия.

- Пиши по-русски ясно и без лишних заимствований; учитывай текущую дату. Русские текстовые файлы обрабатывай как UTF-8.
- Ссылки на сайты оформляй Markdown-ссылками, существующие локальные файлы в Harness Web — точным путём в обратных кавычках (или уникальным именем изменённого файла). Не используй `file://` и голые пути.
- Перед операциями с ветками читай [REPO_POLICY.md](REPO_POLICY.md). Сохраняй пользовательские изменения и работай в отдельном временном worktree. `C:\Users\andre\.dsh` и `C:\Users\andre\.dsh-preview` — постоянные worktree: не удалять, не очищать и не применять к ним автоматические reset/stash. Проверенные изменения локального агента публикуются через commit, push, проверку удалённого SHA и PR в `preview`; исключение `GitHub READ ONLY` и статус `BLOCKED_SYNC` определены в policy.
- Проверки соразмерны изменению. PASS действителен при неизменных релевантных входах: не повторяй эквивалентную проверку ради уверенности. Во время работы запускай целевые проверки, широкую — на естественной финальной границе, только если она нужна задаче или подсистеме. Повтор оправдан изменением кода, тестов, конфигурации, зависимостей, refs либо неполным результатом. Зафиксированный старый сбой не воспроизводи снова без нового основания. Новый validator/test/guard нужен лишь для отдельного failure mode или trust boundary.

## Условные маршруты

- Только при точном начале **текущего** сообщения `^\s*@Postman(?:\s|$)` первым действием по задаче загрузи `skill(delegate-via-postman)`. Для `^\s*@PostmanAsk(?:\s|$)` — `skill(delegate-via-postman-ask)`. Разрешение не наследуется из предыдущих сообщений; разработка Postman сама по себе его не даёт. При недоступности нужного навыка — fail-closed `STOP`, без обхода навыка и альтернативной отправки. Доверенную границу текущего сообщения и ответы соблюдай по соответствующему навыку; обычный агент не запускает Postman без такого триггера.
- Только для роли Postman Leader загружай `postman-leader`; правила Bridge/Worker и сообщения родителю находятся в навыке и [Postman Bridge flow](postman/POSTMAN_BRIDGE_FLOW.md). Обычная разработка Postman без триггера остаётся локальной задачей.
- Перед подготовкой либо применением пакета реализации читай [workflow](system/implementation-package-workflow.md) и [правила подготовки](system/implementation-package-authoring.md), а также `REPO_POLICY.md`.
- При отдельной команде слить уже проверенный task PR загрузи `finalize-task-pr`; для переноса проверенного `preview → main` только после явного разрешения пользователя — `promote-preview-to-main`. Исполнение и предохранители описаны в навыках.
- Если задача действительно относится к долгоживущему подпроекту, прочитай его `SUBPROJECT.md`; остальные подпроекты не загружай.
